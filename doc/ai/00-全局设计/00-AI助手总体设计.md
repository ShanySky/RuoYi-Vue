> 文档类型：长期总体设计 / Living Architecture
> 
> 当前基线日期：2026-09-19
> 
> 适用仓库：`ShanySky/RuoYi-Vue` + `ShanySky/RuoYi-Vue3`
> 
> 默认开发分支：前后端 `chatgpt/ai-agent-assistant`

> 使用原则：本文描述 AI 助手长期总体设计。阶段文档负责说明某一阶段为什么做、如何实施和如何验收；仓库当前代码始终是实现状态的最终事实来源。

## 1. 产品定位

本项目最核心的产品目标，不是“给 RuoYi 增加一个 AI 聊天助手”，也不是为了技术形式上的“AI 框架”本身，而是：

> **让 AI 真正理解业务，并帮助用户以最快、最自然的方式完成真实业务目标。**

在一个业务系统中，用户真正关心的是“我要完成什么事情”，而不是“我要进入哪个菜单、点击哪个按钮、填写哪个字段”。因此，AI 最终需要能够理解：

- 用户用自然语言表达的真实业务意图。
- 业务规则、业务原则和约束条件。
- 一项业务从开始到完成的业务流程。
- 业务流程在系统中对应的页面、字段、按钮、接口、数据和操作。
- 当前用户在这条业务流程中实际有权完成哪些事情。

理想体验是：

    用户表达业务目标
        ↓
    AI 理解业务意图与业务规则
        ↓
    AI 理解完成该目标所需的业务流程
        ↓
    AI 找到系统中对应的页面 / Action / API / 数据能力
        ↓
    在权限和安全边界内帮助用户完成整个业务过程

因此，“把 RuoYi 逐步演进成 AI 时代的软件开发框架”是实现上述产品目标的**技术战略和基础设施方向**，而不是最高目标本身。

传统 RuoYi 提供菜单、权限、CRUD、代码生成、业务页面和后台管理等软件开发基础能力；本项目在这些基础上增加 AI 原生能力，使未来基于 RuoYi 开发的业务系统，可以更低成本地构建这种“AI 理解业务并帮助用户完成业务”的产品。

RuoYi AI 助手既是当前系统中的应用级 AI Agent，也是这套 AI 原生业务软件开发框架的首个完整运行载体和验证入口。

后续所有架构设计都应接受同一个检验：

> **这项设计是否让 AI 更准确、更高效、更安全地理解并完成用户的真实业务目标？**

如果某项设计只是让技术架构看起来更完整，却不能服务于这一核心产品诉求，应谨慎引入。

它同时承担两类工作：

1. 普通对话、解释、分析与辅助决策。
2. 理解用户意图后，通过系统明确注册、受控、可审计的能力操作 RuoYi 页面和业务流程。

AI 助手不是浏览器自动化机器人。生产运行机制不依赖 DOM Selector、鼠标坐标、Playwright 或任意 JavaScript 注入，而是通过结构化 Page Capability / Tool 协议与现有业务页面协作。

最终目标不是为每个页面重新做一套 AI 业务逻辑，而是在不破坏 RuoYi 原业务架构的前提下，让 AI 成为现有系统的一种新的交互入口。

## 2. 产品愿景：从 AI 助手到虚拟员工，再到自进化系统

本项目的产品演进不应只停留在“AI 帮助人操作系统”。

长期愿景分为三个递进层级：

### 2.1 第一层：AI 辅助人完成业务

用户仍然是主要发起者。

AI 负责：

- 理解用户自然语言表达的业务目标。
- 理解业务规则、业务流程和约束。
- 找到系统中对应的页面、操作、接口和数据能力。
- 在权限和安全边界内，帮助用户更快完成业务。

这一层，AI 的角色是“业务助手”。

### 2.2 第二层：AI 作为虚拟员工自主承担业务

更进一步，系统中应能够存在真正的虚拟员工。

虚拟员工可以：

- 拥有自己的身份。
- 拥有岗位、角色和职责范围。
- 接收明确任务。
- 响应业务事件或计划任务。
- 理解完整业务流程。
- 主动调用系统能力完成工作。
- 在授权范围内独立做出允许的业务决策。
- 只有在权限不足、高风险、规则要求或无法判断时请求人类介入。

这意味着未来系统中的业务主体不再只有人类用户：

    业务系统
    ├─ 人类员工
    └─ 虚拟员工

两者都通过受控身份、权限和业务规则使用系统能力。

### 2.3 第三层：系统具备持续自我改进能力

终极愿景是在虚拟员工基础之上，让系统逐步具备“发现问题、设计改进、实施、验证、发布、观察、再优化”的闭环能力。

它不仅能够完成既有业务，还能够持续发现：

- 当前业务流程中的低效、缺口和不合理环节。
- 页面、接口、数据结构和业务功能中的不足。
- 提示词、技能（Skill）、模型上下文协议（MCP）、插件（Plugin）和工具体系中的不足。
- AI 自身工作方式、上下文策略、模型选择和任务编排中的不足。

长期改进闭环可以形成：

    发现问题
      ↓
    记录证据与真实运行反馈
      ↓
    分析根因
      ↓
    设计改进方案
      ↓
    审核
      ↓
    开发 / 修改配置 / 修改提示词 / 技能 / MCP / 插件
      ↓
    构建、测试与真实验证
      ↓
    受控发布 / 部署
      ↓
    观察真实运行效果
      ↓
    评估是否真正解决原问题
      ↓
    进入下一轮改进

改进对象包括两类：

1. **业务系统本身**：页面、接口、数据结构、业务流程、功能和自动化规则。
2. **AI 自身能力**：提示词、技能、MCP、插件、工具、工作流程、模型策略、上下文策略以及必要时的代理代码。

“改进任务”长期应成为系统中的一等对象，使每次自我改进都能够记录问题来源、证据、方案、审核、代码或配置变更、测试结果、发布结果、运行反馈和下一轮决策。

### 2.4 自主程度必须循序渐进

自我改进能力不能从一开始就直接等同于“AI 可以随意修改并上线系统”。

合理演进应是：

1. AI 发现问题并提出建议，由人类决定。
2. AI 设计方案，人类审核后由 AI 实施。
3. AI 设计、AI 审核、AI 实施，人类批准发布。
4. 低风险、成熟范围内的改进可以自动发布，高风险改进继续要求人类审批。
5. 只有在机制、验证和治理足够成熟的范围内，才允许形成更高程度的自治闭环。

### 2.5 能力来源必须保持开放

为了支撑虚拟员工和未来的自进化系统，AI 的能力来源不能固定在当前页面能力或单一工具体系中。

长期需要能够继续接入：

- 技能（Skill）。
- 模型上下文协议（MCP）。
- 插件（Plugin）。
- 页面、后端接口、数据库和环境执行框架（Harness）。
- 以及未来出现的其他标准化能力扩展机制。

当前阶段不提前建设完整的技能市场、MCP 管理平台或插件平台，但底层设计不应假设“AI 能力只能来自当前工具注册表或页面能力”，也不应把具体能力来源写死在代理运行时或代理编排层中。

长期原则是：

> 能力来源可以持续扩展，但所有能力进入系统后，都必须经过统一的身份、权限、风险、治理和审计边界。

### 2.6 自主不等于无限权限

虚拟员工和自进化系统必须像真实员工和真实研发流程一样受到治理，而不是成为超级管理员或无限制后台代理。

长期至少需要具备：

- 独立身份。
- 岗位 / 角色。
- 职责边界。
- 权限范围。
- 可自主决定的事项。
- 必须审批 / 请示的事项。
- 操作记录。
- 业务审计。
- 必要的人类接管和停止机制。
- 对代码、配置、提示词、技能、插件和发布行为的完整变更审计与回滚能力。

### 2.7 框架与产品愿景的关系

“把 RuoYi 演进成 AI 时代的软件开发框架”是技术战略。

这个技术战略最终要服务三个层级的产品：

1. AI 深度辅助人类用户完成业务。
2. 虚拟员工在系统中自主承担业务职责。
3. 系统持续发现问题并优化业务系统与 AI 自身能力。

如果某项框架设计无法帮助这些目标更低成本、更安全、更可靠地实现，应谨慎增加其复杂度。

## 3. 核心设计原则

1. **业务系统仍是权威层。** AI 不绕过原 Service、API、权限、数据范围、校验和操作日志直接更新数据库。
2. **AI 权限不超过当前登录用户。** 页面能力和后端业务接口都必须继续服从当前用户权限。
3. **受控能力优先。** 页面操作通过结构化 Capability / Tool 注册完成，不给模型任意 DOM、任意脚本或超级管理员能力。
4. **Conversation 属于应用，不属于页面。** 页面只是当前工作环境，路由切换、AI 主动导航和刷新不应天然终止会话。
5. **同一 Conversation 最多一个活动 Run。** Stop、Steering、Tool Result、Compaction 和 WRITE 必须服从同一运行生命周期。
6. **完整历史与运行上下文分离。** 数据库保存完整消息和执行事实；Runtime 可以使用 Checkpoint、裁剪和压缩后的上下文视图。
7. **安全边界不能只依赖 Prompt。** Prompt 负责指导模型，权限、Tool Policy、Run 状态和 WRITE 确认必须由代码和后端规则保证。
8. **沿现有架构持续演进。** 除非确有必要，不重新建设第二套 AI 框架。
9. **真实运行优先。** Agent、Tool、权限和页面能力应尽量通过真实全栈运行验证，而不是只做静态检查。
10. **不过度设计。** 为未来留清晰接口，但不提前建设尚无真实需求的复杂平台。

## 6. Conversation、Run 与 Message

### 5.1 Conversation

Conversation 是用户级、后端持久化的应用对象。

它应保存：

- 所属用户。
- 当前模型和 reasoning。
- 标题、状态、最后活动时间。
- Message 历史。
- 当前或历史 Run。
- Checkpoint。
- Pending Tool。

Conversation 不绑定某个 Vue 组件生命周期。页面切换、刷新或重新登录后，可以根据系统策略继续访问历史 Conversation。

### 5.2 Run

Run 表示一次从用户最新意图出发的 Agent 执行。

当前核心状态包括：

- `RUNNING`
- `WAITING_TOOL`
- `COMPACTING`
- `CANCEL_REQUESTED`
- `CANCELLED`
- `SUPERSEDED`
- `COMPLETED`
- `FAILED`

长期要求：

- 同一 Conversation 最多一个活动 Run。
- Stop 后旧 Run 不再产生新的 Tool / WRITE。
- Steering 创建新 Run，并安全 supersede 旧 Run。
- Tool Result 返回时重新校验 Run 是否仍有效。
- WRITE 执行前后均检查运行状态。
- Run 生命周期已由 `AiRunStatus` + `RunLifecycleService` 收敛为显式状态机，状态转换通过期望前态 + CAS 统一约束。

## 7. Agent Runtime

### 6.1 当前实现

当前主线已经建立 RuoYi 自己的 `AgentRuntime` SPI，由 `SpringAiAgentRuntime` 负责适配 Spring AI `OpenAiChatModel` 和 OpenAI-compatible Provider；Conversation、Run、Tool Loop、权限与能力治理仍由应用层控制。

这一实现已经满足当前聊天、Tool Calling、Prompt Cache、Reasoning 和 Compaction 需要。

### 6.2 长期边界

业务 Agent 编排不应永久依赖某个具体 Provider 或 Spring AI 实现细节。

长期建议边界：

    AgentRuntime
    └─ SpringAiAgentRuntime

以后只有出现真实需求时才增加新的 Runtime Adapter。

已确认方向：

- 不接入 Codex Harness。
- 如未来确实需要更完整 Harness，优先 SDK 内嵌式方案，由 Spring Boot 管理生命周期。
- 如果没有合适的内嵌 SDK、又确有独立 Harness 需求，可重新评估 Pi Agent。
- 不因为未来可能更换 Runtime，就提前建设复杂多 Runtime 平台。

## 8. Agent Turn 与 Tool Loop

一次 Turn 输入可以是：

- 新用户消息；或
- 一个 Pending Tool 的 Tool Result。

典型流程：

    User Message
      ↓
    Conversation
      ↓
    Start Run
      ↓
    Assemble Prompt / Context
      ↓
    Model Call
      ├─ MESSAGE → Complete Run
      └─ TOOL_CALL
            ↓
         Persist Pending Tool
            ↓
         Browser executes registered capability
            ↓
         Tool Result
            ↓
         Re-check Run / Page Instance / Permission
            ↓
         Continue same Run

当前仍保持单次只接受一个前端 Tool Call，避免并行浏览器工具造成状态和 WRITE 竞争。未来只有出现明确场景时再扩展并行 Tool。

## 9. Stop 与 Steering

Stop 和 Steering 属于 Agent 核心能力。

### Stop

停止意味着终止当前 Run 的后续执行，不只是隐藏 Loading。

已经完成的不可逆业务写入不会伪装成回滚；尚未开始的 Tool / WRITE 不得继续执行。

### Steering

用户可以在 AI 工作时继续补充或纠偏。

新的用户指令：

1. 写入真实 Conversation 历史。
2. 创建新 Run。
3. 旧 Run 进入 `SUPERSEDED`。
4. 新 Run 基于真实历史、已完成 Tool Result 和最新用户意图重新规划。

不允许同一 Conversation 同时存在两个真正执行 Tool / WRITE 的 Run。

## 10. Context、Checkpoint 与 Prompt Cache

### 9.1 三层上下文

长期保持三层：

1. **原始消息与执行历史**：数据库完整保存。
2. **Checkpoint / Compaction Summary**：长会话的可继续工作状态。
3. **Runtime Context View**：某次模型调用真正发送的上下文。

Compaction 不删除原始事实，也不能把未完成 Tool / WRITE 压缩成已成功。

### 9.2 Prompt Cache

Prompt Cache 是 Runtime 默认应利用的成本优化，不作为普通管理员开关。

Prompt 组织应尽量保持：

1. 稳定 System Rules。
2. 稳定 Tool / Capability 约束。
3. Checkpoint。
4. 历史消息。
5. 高变化 Page Runtime Context。
6. 最新用户消息或 Tool Result。

Provider 不支持特定缓存参数时允许安全降级。

### 9.3 Token Budget

当前已有工作上下文预算和自动压缩阈值。长期应逐步引入更可靠的 TokenEstimator；Provider/tokenizer 不可用时保留启发式估算作为 fallback。

## 11. Page Capability

Page Capability 是 AI 与现有业务页面之间的语义适配层。

它提供的不是 DOM，而是：

- Page Metadata。
- Query Fields。
- Form Fields。
- Options / Dict。
- Validation Rules。
- Table / Selection Context。
- Available Actions。
- Permission。
- Action Invocation。
- Result / Error。

当前协议标记为 `ruoyi-semantic-page-v1`。

后续应把版本字段和必需字段正式化，保证未来协议升级可兼容。

### 10.1 能力覆盖分级

未来页面接入不要求一上来所有按钮全部 AI 化，建议按能力等级理解：

- **Level 1：可理解** —— AI 能读取页面字段、查询结果和当前状态。
- **Level 2：可交互** —— AI 能查询、筛选、打开和填写表单。
- **Level 3：可执行** —— AI 能提交保存、删除、状态变更及其他真实业务动作。

新业务页面优先建立正确 Capability 边界，再按业务价值提升覆盖等级。

### 10.2 页面适配代码

Page Capability 应是独立适配层。长期不建议把大量 AI Schema、Context 和 Action 配置持续堆入大型业务 `.vue` 文件。

后续架构加固可逐步把页面 AI 适配迁移到独立模块，同时继续复用页面真实 handler 和业务 API。

## 12. 跨页面连续工作

AI 可以通过语义导航完成跨页面任务。

导航必须：

- 使用 Vue Router。
- 只到当前用户可访问且系统允许接入 AI 的页面。
- 页面切换后等待新 Capability Instance ready。
- 旧 `pageInstanceId/pageVersion` 的 Tool 立即失效。
- Conversation / Run / Checkpoint / Steering 在导航过程中持续存在。

页面不是 Agent 的所有者，只是当前 Capability Provider。

## 13. 权限与安全

安全边界至少包含：

1. 前端仅上报当前页面实际注册能力。
2. 服务端 Tool / Capability Policy 决定最终模型可见的描述、Schema、权限和风险级别。
3. 当前登录用户权限决定 Capability 是否可用。
4. 原业务 API 的 `@PreAuthorize`、数据范围、校验和日志继续作为最终防线。
5. WRITE / DANGEROUS_WRITE 按宿主确认流程处理。
6. Token、密码等敏感数据不得进入 Page Context 或日志。
7. 页面实例、Run、Conversation、User 必须相互校验。
8. Prompt 不是安全边界。

未来可以按真实业务需求细化风险策略，但不提前建设复杂通用规则 DSL。

## 14. Provider、Model 与 Reasoning

当前系统采用 OpenAI-compatible Provider。

模型生命周期区分：

1. Provider 远端发现模型。
2. 用户明确加入系统模型目录。
3. 系统启用模型。
4. 系统默认模型。
5. 用户个人默认模型。

系统级允许范围始终高于用户偏好：管理员下线模型后，用户配置必须安全回退。

Reasoning 使用 Provider 原始枚举作为 API / DB 值，前端负责中文展示；不同模型支持档位应通过能力信息决定，不能假设所有模型一致。

## 15. Prompt 管理

System Prompt 与 Compaction Prompt 属于系统级配置，普通用户不可修改。

Prompt 必须：

- 支持恢复默认。
- 校验允许的模板变量。
- 记录版本信息。
- Run 记录实际使用的 Prompt 版本。

当前主线已经通过 `ai_prompt_version` 保存按版本唯一的完整正文，Run 继续记录实际使用的 Prompt 版本；审计可以根据版本引用还原历史正文。迁移前已经被覆盖且没有事实副本的旧正文不做伪造恢复。

## 16. 前端 AI Assistant

AI Assistant 是应用级 Shell，而不是某个业务页面组件。

长期职责分层建议：

    AiAssistant Shell
    ├─ Composer
    ├─ MessageList
    ├─ RunStatus
    ├─ Confirmation
    ├─ History
    └─ User Settings
          ↓
       Global AI Store
          ↓
       Agent API / Capability Registry

当前 `AiAssistant/index.vue` 已承载较多职责。后续优先拆职责，不改变用户已验证的浮窗、Dock、Stop、Steering、历史、设置和 Tool 状态体验。

## 17. 状态持久化与多 Tab

状态分层继续保持：

- MySQL：Conversation / Message / Run / Checkpoint / Pending Tool 等 Source of Truth。
- Pinia：当前前端镜像。
- `sessionStorage`：当前 Tab 的 activeConversationId、Draft 等恢复入口。
- `localStorage` 或本机缓存：适合设备级的 UI 偏好。

多个 Tab 可以拥有不同 active Conversation，但同一 Conversation 的服务端“最多一个活动 Run”规则不变。

## 18. 管理与审计

系统级“AI 管理”和用户级“我的 AI 设置”必须分层。

管理员能力包括：

- AI 服务。
- 模型管理。
- Prompt 管理。
- 页面能力。
- 会话策略。
- 会话审计。

会话审计使用独立权限，只读查看，不允许管理员从审计页继续、重试、接管其他用户 Run 或触发 Tool / WRITE。

## 19. 数据与迁移

AI 数据独立放在 `ai_*` 表中，不修改 RuoYi 原业务表语义。

随着阶段增多，应逐步形成清晰的 AI fresh install schema + 有序 migration 规则，避免后续出现大量无法判断执行顺序的阶段 SQL。

## 20. 测试策略

测试分三层：

1. **Unit / Integration**：验证 Run 状态转换、幂等、Tool Result、Page Instance、权限和 Compaction 边界。
2. **Fullstack E2E**：验证 MySQL、Redis、Spring Boot、Vue、业务 API、页面 Capability 和 Agent Loop 的真实闭环。
3. **Real Provider**：验证真实 GPT / OpenAI-compatible Provider 的 Tool、Reasoning、Cache 和长上下文行为。

代码改完、编译成功或进程启动都不能单独代表 AI 功能完成。

## 21. 长期能力演进阶梯

本项目长期目标是把 RuoYi 演进为 AI 时代的软件开发框架。AI 能力不应长期停留在“操作当前页面”，而应逐步形成更高层级、同时仍然可治理的系统操作能力。

这是一条**长期方向**，不是当前 Phase 3.5 的实施范围；每一层是否进入正式阶段，仍需根据当时真实需求重新设计和验收。

### 20.1 第一层：Page Capability

当前已进入主线。

AI 通过统一页面契约理解和操作页面：

- 页面字段。
- 查询条件。
- 表格与表单。
- 标准 Action。
- 特殊业务 Action。
- 跨页面导航。

这一层以“页面天然 AI-ready、业务事实单一来源、AI 只补充 AI 专属语义”为长期原则。

### 20.2 第二层：Backend API Capability

下一层长期方向是：AI 不再必须经过页面才能完成所有任务，而可以在受控条件下直接调用 RuoYi 已有后端接口。

目标包括：

- 更高效地查询、聚合和处理系统数据。
- 对不需要 UI 交互的任务直接使用服务端能力。
- 继续复用现有 Controller / Service / 权限 / 数据范围 / 业务校验，而不是另建第二套业务后端。

核心治理原则：

- 不是“所有接口自动全部开放给 AI”。
- 系统需要能够识别真实存在的后端能力，并由 AI 治理层决定哪些接口允许 AI 使用。
- 初期由管理员控制开放范围。
- 后续如有真实产品需求，可以进一步允许用户在自己本来有权调用的能力子集内决定哪些交给 AI，但这不是当前承诺功能。

### 20.3 第三层：Database Capability

在 Backend API Capability 成熟之后，可以进一步评估受控数据库能力，使 AI 能直接完成部分查询、分析和必要的数据操作。

这一层风险显著高于页面和业务 API，因此必须把“可控”作为前提，而不是追求任意 SQL。

长期治理方向包括：

- 哪些数据库 / Schema 对 AI 可见。
- 哪些表允许 AI 访问。
- 哪些字段允许读取或写入。
- 哪些操作类型允许执行。
- 哪些高风险 SQL 类型明确禁止。
- 数据库权限仍应遵循最小权限和明确审计原则。

是否允许任意 SQL、是否允许写操作、是否需要中间语义层等问题，必须在该阶段正式启动前重新设计；当前总体设计只确认“受控数据库能力”这一长期方向，不提前锁死具体实现。

### 20.4 第四层：Harness Capability

更远期方向是让 RuoYi AI 不只是调用页面、接口或数据库，而具备 Harness-class 的环境操作能力。

目标形态可以包括：

- 系统提供的远端 / 服务器端 Harness。
- 对接用户自己的 Harness。
- 用户本地机器上的 Harness。

服务器端 Harness 与系统同处受控环境，对接相对直接；**如何安全连接并授权用户本地 Harness**，应作为该阶段的重点设计问题之一，包括连接建立、身份、能力声明、权限、生命周期和审计。

这里的目标是具备类似成熟 Coding / Agent Harness 的能力形态，并不意味着当前已经决定采用某个现成 Harness 实现。

### 20.5 贯穿四层的治理原则

无论能力升级到哪一层，都必须保持“能力可发现，但是否允许 AI 使用必须可治理”。

    Page
      ↓
    Backend API
      ↓
    Database
      ↓
    Harness

对应的治理也逐层扩展：

- 页面：哪些页面 / Action 允许 AI 使用。
- API：哪些系统接口允许 AI 使用。
- Database：哪些表 / 字段 / 操作允许 AI 使用。
- Harness：哪些环境能力、工具、资源和操作允许 AI 使用。

长期目标不是给 AI 无限权限，而是让框架能够提供越来越强的能力，同时管理员始终能够明确控制 AI 能看到什么、能调用什么、能执行到什么程度。

## 22. 后续扩展边界

### 已完成的 Phase 3.5 首批加固

- AgentRuntime SPI 收敛。
- Run Lifecycle 状态机显式化。
- Prompt 真实版本历史。

### 已确认的后续方向

- Page Capability Adapter 解耦。
- 协议版本化。
- Agent 核心状态测试增强。
- SQL migration 规范化。

### 有真实需求时再评估

- Server Tools。
- SDK 内嵌式 Harness。
- 更复杂异步执行。
- Streaming Event / SSE。
- 更丰富 Capability 类型。

### 当前不作为承诺路线图

- 多 Agent 编排。
- RAG / 向量库。
- 任意桌面软件控制。
- 任意 DOM 自动化。
- 完整 AI 运营平台。
- 动态安全规则 DSL。

这些方向可以研究，但不能仅因为“未来可能需要”就提前增加当前架构复杂度。
