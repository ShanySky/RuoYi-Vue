## 3. 三个阶段的定位

### 第一阶段：建立最小真实闭环

完成：

- Provider / Model。
- 普通聊天。
- Agent Loop。
- 当前页面 Frontend Tool。
- WRITE 确认。
- 用户管理真实业务修改。
- MySQL / Redis / Spring Boot / Vue / CI / E2E 全栈验证。

详见：`../01-第一阶段/`

### 第二阶段：从 Demo 变成可长期使用的助手 UI

完成：

- 非模态小窗 + Dock。
- 快捷设置。
- 多模型管理与实时搜索。
- 默认模型和 Reasoning。
- 同一 Conversation 后续轮次模型切换。
- 第一阶段稳定性修复。

详见：`../02-第二阶段/`

### 第三阶段：把助手提升为应用级 Agent

完成主要能力：

- Run / Stop / Steering。
- Prompt Cache。
- Context Budget / Checkpoint / Compaction。
- 统一 Page Capability。
- 多页面接入和跨页连续操作。
- 应用级 Conversation / Run / UI 恢复。
- 用户会话历史与偏好。
- AI 管理分层。
- 管理员只读审计。

第三阶段自动实现、自动验收和当时验收版本的 Real GPT 验收已经收口；原验收记录保留 R3-09 主观视觉人工确认作为最后用户侧确认项，不将其伪造为已经确认。

详见：`../03-第三阶段/`

### 4.2 本轮推进方向

用户已明确要求按以下顺序自主推进：后端接口能力 → 受控数据库能力 → 较成熟的服务端执行框架。

诉求、决策来源、授权及阶段约束统一见 [29 号文档](../06-服务端能力演进/29-AI助手服务端能力演进诉求与推进约束.md)。本轮已依次完成三个阶段和组合验收：[32 接口](../06-服务端能力演进/32-后端接口能力实施与验收工作笔记.md)、[36 数据](../06-服务端能力演进/36-受控数据库能力实施与验收工作笔记.md)、[39 执行与整体](../06-服务端能力演进/39-成熟执行框架实施与验收工作笔记.md)。最终配对版本与环境清理由 39 统一记录，不据此自动扩展为数字员工或自主进化。

历史文档中“Server Tools / Harness 延后”的结论描述的是 3.5 阶段范围，不能继续作为阻止本轮推进的依据。B7 估算精度、B8 执行管理只解决新阶段实际需要，不提前建设分布式平台或复杂自建执行框架。旧架构讨论分支不再作为当前工作入口。

## 5. 更新规则

发生以下情况时应更新本文件：

- 某项全局能力完成或状态发生明显变化。
- 某个“规划方向”被正式批准进入实施。
- 某个长期方向被明确取消。
- 总体设计发生架构级调整。

日常小修复和每次 commit 不需要在这里记录。
