# RuoYi AI 助手关键设计决策

> 文档类型：长期架构决策摘要
> 
> 当前版本：2026-09-20
> 
> 目的：记录已经形成的关键设计取舍，避免未来在缺少历史上下文时反复争论同一问题。这里不是完整 ADR 系统，只记录对长期演进真正有约束力的决定。

## D-001 生产机制不使用任意 DOM / 坐标自动化

**决策**

AI 通过结构化 Page Capability / Frontend Tool 操作页面，不把 DOM Selector、鼠标坐标、Playwright 或任意 JavaScript 当作生产 Agent 的操作协议。

**原因**

- 页面结构变化会让坐标/Selector 极不稳定。
- 无法形成清晰字段、权限、风险和审计语义。
- 容易绕开 RuoYi 已有业务流程。

**影响**

页面需要主动注册语义化能力。

**可重新评估**

可以用 Playwright 做测试；只有出现明确特殊场景时，才讨论受限浏览器自动化补充能力。

## D-002 AI 不绕过原业务 API 直接写数据库

**决策**

AI 页面操作最终继续调用 RuoYi 原业务 API / Service。

**原因**

复用：

- `@PreAuthorize`。
- 数据权限。
- 参数校验。
- 事务。
- 操作日志。
- 已有业务规则。

**影响**

Page Capability 是新的交互入口，不是第二套业务后端。

## D-003 AI 权限不超过当前登录用户

**决策**

页面工具、真实业务接口、数据库能力和环境执行均以当前 RuoYi 用户身份、权限及业务数据范围为上限；系统对 AI 的开放策略只能进一步收窄这个范围。

2026-09-20 用户补充明确：AI 调用接口和数据库的权限都不能超过使用它的用户。数据库连接账号的权限不代表业务用户权限，表、字段和行范围必须映射到真实业务授权；无法可靠映射时不开放对应能力。发现、读取详情、执行和读取成果时都要校验，权限撤销后不能沿用旧授权继续访问。

**原因**

避免 AI 成为隐式超级管理员通道。

**影响**

能力未提供通常意味着页面未接入、系统禁用或当前用户无权执行。

## D-004 浏览器只声明能力可用性，服务端保持安全权威

**决策**

浏览器可以上报当前页面有哪些 Tool，但 Tool 描述、风险级别、权限和允许 Schema 必须由服务端可信规则约束。

**原因**

不能信任修改后的浏览器客户端自行扩大 WRITE 能力。

**影响**

服务端必须维护 Capability / Tool Policy 层。

## D-005 Conversation 是应用级对象，不是页面组件状态

**决策**

Conversation 持久化在后端，页面只提供当前工作环境。

**原因**

支持：

- 正常路由切换。
- AI 主动跨页面。
- F5 恢复。
- 历史会话。
- 多 Tab。
- 长任务。

## D-006 同一 Conversation 最多一个活动 Run

**决策**

同一个 Conversation 不允许两个 Agent Run 同时真正执行 Tool / WRITE。

**原因**

避免并行规划造成重复 Tool、竞争写入和不可解释状态。

**影响**

用户追加指令通过 Steering / Supersede，而不是启动并行 Agent。

## D-007 Stop 必须是后端语义，不只是前端 Abort

**决策**

停止动作要写入 Run 状态；浏览器 Abort、Future cancel 和上游 HTTP 取消只是加速手段。

**原因**

即使上游请求结果稍后返回，也不能让已取消 Run 恢复执行 Tool。

## D-008 Steering 保留已发生事实，不伪造回滚

**决策**

新指令 supersede 旧 Run。已经完成的 READ / WRITE 作为真实历史保留；尚未执行的旧计划停止。

**原因**

Agent 必须基于系统真实状态继续，而不是假装之前副作用不存在。

## D-009 原始消息历史不因 Compaction 删除

**决策**

数据库保留完整 Conversation / Message；Checkpoint 只用于 Runtime Context。

**原因**

压缩摘要可能丢细节，且审计必须保留真实历史。

## D-010 Prompt Cache 是 Runtime 默认优化，不做普通管理员开关

**决策**

系统自动维持稳定前缀并按 Provider 能力利用 Prompt Cache。

**原因**

缓存策略属于 Runtime 实现细节，暴露普通开关会增加误配置和重复成本。

**可重新评估**

只有出现真实多租户、复杂路由或 Provider 差异需求时，再考虑高级缓存策略配置。

## D-011 当前 Agent 通信以 HTTP Turn 为主，不强制 WebSocket

**决策**

当前 Tool Loop 使用 Turn 请求 / Tool Result 推进。

**原因**

优先保证 Tool、权限、Stop、Steering 和恢复语义正确。

**可重新评估**

SSE / Streaming Event 可以作为未来体验升级，但不应破坏当前 Run 状态模型。

## D-012 Page Capability 采用显式语义协议

**决策**

页面向 AI 提供字段、选项、校验、表格上下文和动作，不上传完整 DOM。

**原因**

让模型理解“业务能力”，而不是“网页像素”。

**影响**

当前协议为 `ruoyi-semantic-page-v1`；3.5 阶段已完成正式化与前后端校验，继续以现有协议和受信页面快照为边界。

## D-013 页面 Capability 按业务价值渐进覆盖

**决策**

不把“所有页面所有按钮必须一次全部 AI 化”作为长期架构硬要求。

**原因**

全面覆盖成本很高，而且不同页面价值和风险差异明显。

**建议**

按 Level 1 可理解、Level 2 可交互、Level 3 可执行逐步推进。

## D-014 用户个人设置与系统级 AI 管理必须分离

**决策**

AI 助手中的“我的 AI 设置”只承载当前账号的个人偏好；系统级 AI 配置与治理只通过“AI 管理”正式入口维护。

系统管理员或具备相应权限的授权角色决定：

- 服务提供方（Provider）连接、基础地址和令牌。
- 系统允许使用的模型。
- 系统默认模型与系统默认思考档位。
- 模型运行参数、能力检测和连接测试。
- 系统提示词（Prompt）。
- 页面接入与页面能力治理。
- 会话策略及其他系统级 AI 治理配置。

普通用户只决定管理员允许范围内的个人偏好，例如：

- 我的默认模型。
- 我的默认思考档位。
- 字体。
- 快捷键。
- 历史入口。
- 自动继续上次会话。
- AI 助手默认打开方式。

系统级配置不得因为当前用户恰好拥有管理员权限，就再次出现在“我的 AI 设置”中形成第二入口。系统配置权限继续使用若依基于角色和权限的访问控制（RBAC），例如 `ai:config:view`、`ai:config:edit`，不得写死为只有 `admin` 用户可用。

普通用户读取系统已经启用的模型属于“消费管理员允许范围”，不等同于获得系统模型管理权限。

**原因**

- 个人设置和系统治理面向不同职责，混在同一入口会让用户误以为系统配置属于个人偏好。
- 服务令牌、系统模型启停、系统默认值和运行参数属于系统治理，不应进入普通用户设置路径。
- 保留管理员专属的第二入口会继续造成双入口、重复状态和长期维护歧义。
- 使用权限控制而不是写死超级管理员身份，可以继续支持独立 AI 管理员、运维人员等授权角色。

**影响**

- AI 助手的个人设置组件不得承载服务提供方、系统模型或其他系统治理表单。
- “AI 管理”是系统级 AI 配置与治理的唯一正式入口。
- 同一能力同时存在系统允许范围和用户个人选择时，必须先区分“系统治理事实”和“用户偏好”，再分别落到对应入口。
- 后续新增技能、模型上下文协议、知识库等能力时，也应继续区分系统级治理与用户级选择，不把两类职责重新混回个人设置。

## D-015 会话审计使用独立权限且保持只读

**决策**

能配置 Provider 的管理员不自动获得查看员工 AI 会话的权限；审计管理员也不能继续或接管他人 Run。

**原因**

AI 会话可能包含敏感业务上下文。

## D-016 现有自控执行循环只承担迁移前的必要职责

**决策**

当前主线实现仍是 Spring AI + 应用自控 Agent Loop。本轮目标已更新为接入成熟服务端执行框架，因此旧循环仅做接口、数据库阶段必需的能力接入、安全修复与迁移兼容，不继续建设将被替换的复杂编排或通用执行平台。

**原因**

原决策适用于 3.5 阶段：当时现有能力已满足聊天、工具、停止、纠偏、检查点和缓存诉求，额外常驻框架会增加部署和运维复杂度。

2026-09-20 用户明确要求推进成熟服务端执行框架，并要求控制自建简易框架的改造投入，原“当前不引入”的阶段前提已经改变。业务身份、授权、审计和真实运行事实等可保留的底座继续复用。

## D-017 成熟执行框架采用受控集成与适度适配

**决策**

优先选择成熟、许可证适合项目使用的开源执行框架，尽量随后端一起部署并由宿主管理生命周期。具体采用开发库、受控子进程或容器，由隔离要求和真实集成验证决定，不强求进入同一 Java 进程。

适配层只服务选定框架与当前场景；后续允许客户端安装与服务端同款框架，先保留身份、连接、授权和执行结果等必要边界，不建设兼容所有框架的平台。

**备选**

Pi 是本轮优先评估候选之一，尚未选定或接入。2026-09-20 用户已授权自主决定进程与集成方式，隔离执行和资源回收约束见 D-023。

原先“优先开发库内嵌”的判断服务于部署简化；本轮仍保留这一目的，并根据新增的沙盒要求调整实现取舍。

**明确排除**

Codex Harness 不作为本项目预留方向。

## D-018 不建设第二套 AI 架构

**决策**

后续继续沿 `ruoyi-ai`、Conversation、Run、Tool/Capability、AI Store 和现有 UI 演进。

**原因**

当前底座已经形成连续架构，重复建设会导致两套状态、两套协议和两套维护成本。

## D-019 安全规则不依赖 Prompt

**决策**

Prompt 可以解释规则，但权限、数据范围、Run 状态、Tool Policy、WRITE 确认和页面实例校验必须由代码保证。

**原因**

模型提示不是强制访问控制。

## D-020 真实运行验证优先

**决策**

涉及 AI Agent 的重要修改，应尽量验证真实：

- MySQL。
- Redis。
- Spring Boot。
- Vue。
- API。
- Tool Loop。
- 页面动作。
- 必要时 Real Provider。

**原因**

AI Agent 很多错误只在完整状态链和运行环境中出现。

**用户补充（2026-09-21）**

新增能力不得破坏原本正常、且不需要改动或升级的功能与处理链条。各阶段先记录既有基线，再按影响范围验证新功能与保留功能；出现本轮引入的回归，修复并复测后才可关闭阶段。具体执行约束见 [29 号文档](../06-服务端能力演进/29-AI助手服务端能力演进诉求与推进约束.md)第 6.1 节。

验收必须与诉求、关键决策和设计形成闭环：方案能够支撑上层要求，计划能够落实方案，实施与审核能够证明实际承接。阶段验收和最终整体验收都要围绕真实业务目标及关键失效风险设计测试，不能以机械调用接口、完成计划或测试数量替代结果证明。方法见 29 号文档第 6.2、6.3 节。

## D-021 不提前建设无真实需求的复杂平台

**决策**

当前不为了“体系完整”提前建设：

- 多 Agent 平台。
- RAG / 向量库。
- 动态 Tool Policy DSL。
- Prompt 审批工作流。
- 完整 AI 运营 BI。
- 分布式 Agent 调度平台。

**原因**

先保持核心能力简单、可验证、可维护。

## D-022 总体设计允许包含尚未实现但已确认的方向

**决策**

`00-AI助手总体设计.md` 可以记录明确的未来架构方向，并标记实现状态。

**原因**

总体设计应该描述“最终要建成什么”，不应退化成当前代码清单。

**约束**

远期猜想必须标记为研究方向，不能把尚未确认的想法写成既定路线。

## D-023 环境执行必须隔离，文件空间与资源必须可管理

**决策来源**

2026-09-20 用户补充明确要求：避免 AI 任意执行命令危及服务器，优先为 AI 配置独立沙盒或类似 Docker 的隔离环境，并管理文档生成所需磁盘空间和临时文件。

**决策**

- 执行环境按用户身份和任务隔离，不跨用户共享可写工作空间；命令不得直接在宿主以无限制权限运行。
- 隔离机制必须同时约束挂载、网络、凭据和进程权限，不能仅用提示词或命令名称过滤宣称安全。
- 工作空间区分临时文件与交付成果，支持用户、任务和全局配额、保留期、清理、异常残留回收及磁盘低水位保护；数量和容量限制必须在实际写入期间有效。
- 同时限制处理器、内存、进程数量、并发和执行时间；停止、失败、服务关闭及异常退出后应能终止执行并回收资源。
- 成果文件的读取、下载与保留继续服从用户权限；隔离环境不可用时关闭相应能力，不退回宿主无限制执行。

**验收边界**

容器或沙盒是实现隔离的机制，实际隔离配置、越界拒绝、配额执行与回收结果都需有测试证据。具体框架、隔离技术和配额数值在对应阶段确定，本决策不表示这些机制已实现。
