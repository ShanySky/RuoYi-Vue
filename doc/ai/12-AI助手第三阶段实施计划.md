## 1. 计划使用规则

本文件是第三阶段开发的主跟踪文档。

每个任务必须带有对应需求 ID。实施过程中：

- 不允许出现“做了一个技术改造，但不知道对应哪个用户诉求”的任务。
- 不允许为了方便开发把某条用户诉求悄悄缩小。
- 如果实际代码发现方案必须改变，要先回到 `11` 说明变化是否仍满足原诉求，再调整本计划。
- 每个阶段结束时先做“需求回看”，确认没有越做越偏，再进入下一阶段。
- 状态统一使用：`未开始 / 进行中 / 已实现 / 已验证 / 阻塞`。
- “已实现”不等于“已验证”；只有通过对应用户场景验收后才能标记“已验证”。

核心 E2E：

```text
用户：把 ry 昵称改成 A
AI：开始查询
用户：等等，改成 B，而且先不要保存
→ 旧 Run 停止
→ 不提交 A
→ 新 Run 知道用户最终要求是 B + 不保存
```

验收不能只看状态表，必须检查真实页面/数据库没有执行旧要求。

- 为通过 E2E 改测试绕开真实产品问题。
- Stop 只做视觉不做运行时取消。
- Steering 实际只是排队等待。
- Compaction 只做摘要不自动续跑。
- Cache 只设置参数不验证命中。
- Page Capability 只做协议抽象不做页面覆盖。
- 因新增 UI 把第二阶段已有设置功能删掉。

## 14. 每次阶段完成时的回报格式

后续每完成一个阶段，`13` 至少记录：

- 对应需求 ID。
- 实际修改文件/模块。
- 关键决策。
- 自动测试证据。
- 真实运行证据。
- 用户场景是否已通过。
- 已知偏差。
- 下一步。

只有“用户场景已通过”才能把对应需求状态改成“已验证”。
