## 1. 计划使用规则

本文件是第三阶段开发的主跟踪文档。

每个任务必须带有对应需求 ID。实施过程中：

- 不允许出现“做了一个技术改造，但不知道对应哪个用户诉求”的任务。
- 不允许为了方便开发把某条用户诉求悄悄缩小。
- 如果实际代码发现方案必须改变，要先回到 `11` 说明变化是否仍满足原诉求，再调整本计划。
- 每个阶段结束时先做“需求回看”，确认没有越做越偏，再进入下一阶段。
- 状态统一使用：`未开始 / 进行中 / 已实现 / 已验证 / 阻塞`。
- “已实现”不等于“已验证”；只有通过对应用户场景验收后才能标记“已验证”。

## 3. 实施顺序总览

为减少返工，本阶段按以下依赖顺序推进：

```text
A. 基线与数据模型
        ↓
B. UI/交互基础与 Reasoning 展示
        ↓
C. Run 生命周期：Stop + ESC + Steering
        ↓
D. Context Budget + Checkpoint + Auto Compaction
        ↓
E. Prompt Cache + Usage 可观测
        ↓
F. 完整语义化页面能力 + 跨页面导航
        ↓
G. Conversation 持久化、历史会话与用户偏好
        ↓
H. AI 管理模块、Prompt 管理与会话审计
        ↓
I. 全量回归、真实 GPT 验证、Public Preview、用户场景验收
```

每个阶段都采用：

`实现 → 自动验证 → 用户诉求回看 → 修复 → 再验证 → 进入下一阶段`

## 6. 阶段 C：Run 控制、Stop 与 Steering

对应：R3-02、R3-04。

- [ ] 为同一 Conversation 建立活动 Run 互斥或原子状态更新。

### C2. Stop API 与真正中断

对应：R3-02。

任务：

- [ ] 前端运行时“发送”按钮切换为“停止”。
- [ ] Stop 发起后立即更新 UI。
- [ ] 后端 cancel endpoint / run cancel 逻辑。
- [ ] 尽可能取消 Spring AI / HTTP 上游请求。
- [ ] 无法取消的迟到响应必须丢弃，不继续 Tool。
- [ ] 已产生但未执行 Tool 取消。
- [ ] pending WRITE 取消。
- [ ] 已提交完成 WRITE 只记录真实状态，不伪造回滚。

自动验收场景：

- [ ] 模型慢响应时点击 Stop。
- [ ] 后端模拟迟到响应。
- [ ] 迟到响应没有产生 Assistant 后续动作和 Tool。
- [ ] Stop 后可以立即发送下一条消息。

### C3. Steering / Supersede

对应：R3-04。

任务：

- [ ] AI running 时输入框保持可输入。
- [ ] 用户补充消息立即持久化。
- [ ] 当前 Run 原子标记 SUPERSEDED。
- [ ] 新 Run 基于完整最新 Conversation 创建。
- [ ] 多次快速补充全部按顺序保留，不丢消息。
- [ ] 新规划基于旧 Run 已经真实完成的 Tool 结果。
- [ ] 旧 Run 尚未执行的 Tool 不再继续。
- [ ] pending WRITE 确认被新补充覆盖时取消旧确认链。

核心 E2E：

```text
用户：把 ry 昵称改成 A
AI：开始查询
用户：等等，改成 B，而且先不要保存
→ 旧 Run 停止
→ 不提交 A
→ 新 Run 知道用户最终要求是 B + 不保存
```

验收不能只看状态表，必须检查真实页面/数据库没有执行旧要求。

### C4. Stop 与 ESC 联动

对应：R3-02、R3-03。

任务：

- [ ] Stop 按钮和双 ESC 进入同一后端取消逻辑。
- [ ] 不维护两套取消语义。
- [ ] ESC 只是 Stop 的快捷触发方式。

## 11. 实施中禁止的偏航

开发过程中发现以下情况时必须主动纠正：

- 为了“架构漂亮”新增大量与 R3-01 ~ R3-18 无关工作。
- 技术测试全绿，但用户场景仍不好用。
- 为通过 E2E 改测试绕开真实产品问题。
- Stop 只做视觉不做运行时取消。
- Steering 实际只是排队等待。
- Compaction 只做摘要不自动续跑。
- Cache 只设置参数不验证命中。
- Page Capability 只做协议抽象不做页面覆盖。
- 因新增 UI 把第二阶段已有设置功能删掉。
