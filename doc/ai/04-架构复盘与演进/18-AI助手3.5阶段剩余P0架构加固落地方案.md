## 1. 本轮目标

本轮只完成 Phase 3.5 剩余 P0：

1. B4：统一 Page / Action 契约与 Page Capability 适配底座，并完成一个代表页面完整迁移与真实验证。
2. B5：Tool Policy 轻量职责拆分。
3. B6：Capability Protocol v1 正式化。
4. C1：`AiAgentLoopService` 有限职责收敛。
5. B9：补关键 Agent Unit / Integration Test。
6. B10：建立 AI fresh-install schema + 有序 migration 规则。

本轮目标不是增加新的用户功能，而是把已经开始膨胀、会直接影响下一阶段扩展的边界收紧。

总体产品主线仍然是：

> AI 理解真实业务并帮助用户完成业务 → 虚拟员工能够自主承担业务 → 长期形成受治理的自我改进系统。

因此本轮只建设下一阶段真实需要的地基，不为了“架构完整”提前建设平台。

## 2. 当前真实代码判断

截至本方案形成时，专项分支从最新 AI 主线创建，当前真实实现已经具备较完整基础，不需要重建第二套机制。

### 2.1 前端 Page Capability 已有公共基座，但页面声明仍偏重

当前前端已经存在：

- `src/ai/toolRegistry.js`
- `src/ai/crudPageCapabilities.js`
- `src/ai/pageCapabilityCatalog.js`

`createAiCrudPageCapabilities` 已经统一处理：

- 标准查询 / 重置。

- 表单提交。
- 自定义业务 Action。
- Query / Form 字段快照。
- Schema、Options、Validation Rules 等部分语义。

`toolRegistry` 已经处理：

- 当前 Page Runtime。
- `pageInstanceId` / `pageVersion`。
- 权限过滤。
- 跨页面导航。
- 旧页面实例失效。

问题不在“没有公共能力”，而在于大量业务页面仍然在 `.vue` 中重复维护较长的 AI 字段、动作和适配声明。

### 2.2 Capability Protocol 已存在事实，但还没有成为正式契约

后端 `AiChatTurnRequest` 当前直接接收：

- `route`

因此 B6 的任务是把现有事实正式化，而不是重新发明另一套协议。

### 2.3 Tool Policy 已同时承担 Registry、显式策略和 Generic CRUD 推导

当前 `AiFrontendToolPolicy` 同时负责：

- 大量显式 Tool Allowlist。

- Server-side Description。
- Server-side Input Schema。
- Generic CRUD Tool 名称解析。
- 通用 CRUD Risk / Permission 推导。

这一模式安全方向正确：浏览器只声明“当前可用”，服务端继续掌握权限、风险和受信 Schema。

本轮要解决的是职责集中和继续增长的问题，不改变“服务端策略权威”这一安全边界。

### 2.4 Agent Loop 已完成 Runtime / Lifecycle 首轮解耦，但仍承担多个稳定职责

B1 / B2 完成后，`AiAgentLoopService` 已不再直接承担 Spring AI 运行时细节和 Run 状态机本体。

但当前仍然同时负责或协调：

因此 C1 已经具备“有限拆分”的真实依据，但不需要继续拆成完整 Service 图谱。

## 4. B4 + B6：统一 Page / Action 契约与 Capability Protocol v1

B4 和 B6 在工程上属于同一个基础层，应一起设计、分别验收。

### 4.1 总体原则

继续坚持：

> 页面天然 AI-ready；业务事实尽量只定义一次；AI 复用真实页面 handler、API、权限、校验和数据范围；特殊能力显式扩展。

不做：

- DOM Selector 自动化。
- 坐标点击。
- 任意 JavaScript 注入。
- 通过函数名或页面结构黑盒猜测业务语义。
- 为 AI 复制一套独立业务 API。
- 为了“自动发现”建立复杂反射 / DSL 平台。

### 4.2 Capability Protocol v1

正式协议标识继续使用：

`ruoyi-semantic-page-v1`

v1 最小契约必须明确包含以下逻辑字段：

- `capabilityProtocol`
- `pageId`
- `route`
- `pageInstanceId`
- `pageVersion`
- `pageContext`
- `frontendTools / capabilities`
- Tool Result 的 `callId / success / result / error`

原则：

1. 不要求为了形式重新包装成复杂多层 Envelope；优先在现有 Turn Request / Tool Result 结构上补齐缺失字段和集中校验。
2. 只支持当前 v1，不建设协议协商、多版本路由或兼容平台。
3. 当前没有 Page Capability 时允许普通聊天继续工作；一旦请求携带页面能力或 Page Runtime，应明确校验协议版本。
4. `pageId + route + pageInstanceId + pageVersion` 共同用于确认当前页面语义实例，旧实例不得继续提交 Tool Result。
5. 客户端 Tool Definition 仍只代表“当前页面声明可用”；风险、权限、受信 Description / Schema 继续由服务端 Policy 决定。
6. Tool Result 错误语义要统一：页面失效、权限变化、策略拒绝、业务执行错误与普通返回必须能稳定区分，至少在服务端异常 / Result Payload 层形成一致规则。
7. Protocol v1 的契约必须有自动测试，防止前后端字段在后续迭代中静默漂移。

### 4.3 Page Capability Adapter 目标形态

现有 `createAiCrudPageCapabilities` 不废弃，而是作为当前公共 CRUD 基座继续演进。

P0 目标不是建设全新 Page Framework，而是让业务页面最终只保留很薄的激活 / Runtime 绑定逻辑。

建议职责收敛为两层：

```text
业务页面真实状态 / handlers / rules / dict options
        ↓
Page / Action Contract + Runtime Bindings
        ↓
通用 Page Capability Adapter
        ↓
Tool Registry
        ↓
Capability Protocol v1
```

其中：

**Page / Action Contract** 负责稳定语义：

- pageId / pageName / route / toolPrefix。
- 标准 Query / Form 字段声明。
- 权限。
- Action 名称和语义。
- AI 专属描述、风险补充。
- 特殊 Action 的 Input Schema。

**Runtime Bindings** 负责页面真实运行对象：

- query model。
- form model。
- validation rules。
- dict / options。
- 当前 rows / total / selectedIds。
- 页面现有 handler。
- 页面现有 submit / reset / open / delete / status 等业务动作。

要求：

- Validation、Options、真实 Handler 等已经存在于业务页面的事实，应尽可能直接复用，不再复制第二份值。
- 标准 CRUD 继续由公共 Adapter 生成 Tool。
- 特殊业务动作显式声明，但实际执行必须调用页面现有 handler / API。
- AI 专属描述和 Risk 可以独立维护，因为它们本来就是 AI 治理语义，不属于普通页面业务事实。
- 不为了追求 100% DRY 强制把整个 Vue 页面改成 Metadata-driven UI。

### 4.4 AI 声明从业务 `.vue` 中减重

代表页面完成后，应达到：

- `.vue` 中不再保留大段重复的 AI Tool 构造代码。
- 页面仅保留必要的 Runtime 引用 / 激活调用。
- 稳定的 Page / Action Contract 可以放到 `src/ai` 下的页面能力模块或页面 companion module。
- companion module 不直接绕过页面状态和 handler；它通过显式 bindings 使用真实页面能力。

P0 只完成底座和一个代表页面，不批量迁移其他页面。

### 4.5 代表页面

本轮代表页面选择：

`/system/user` —— 用户管理。

原因：

- 同时包含查询、分页、新增、编辑、字段填写、提交。
- 存在真实 Validation Rules、Options 和权限。
- 同时存在 READ / UI / WRITE / DANGEROUS_WRITE 等不同风险动作。
- 存在查看、删除、状态修改、密码重置、分配角色等特殊 Action。
- 能充分验证通用 CRUD 与特殊业务动作是否能共存。
- 当前已经通过 `createAiCrudPageCapabilities` 接入，适合做“旧形态 → 新契约”的完整样板。

P0 验收要求：

- 用户管理页 AI 功能不退化。
- 页面声明明显减重。
- Query / Form / Action 契约与 Protocol v1 正常工作。
- 权限、Risk、WRITE 确认、旧 Page Instance 失效仍然有效。
- 真实 Tool Result 能继续回到同一个有效 Agent Run。

## 5. B5：Tool Policy 轻量拆分

### 5.1 保留的安全原则

`AiFrontendToolPolicy` 当前“客户端不可信、服务端策略权威”的方向必须保留：

- 客户端不能决定 Risk。
- 客户端不能扩大 Permission。
- 客户端不能通过 Description 注入模型指令。
- 客户端不能通过 Input Schema 扩大可写字段。
- Generic CRUD 只处理明确命名规则内的标准动作。
- 特殊高风险动作必须显式定义。

### 5.2 目标职责

本轮收敛为三个职责层：

```text
AiFrontendToolPolicy（Facade / Approval）
        ↓
ToolPolicyRegistry
        ├─ Generic CRUD Policy Provider
        └─ Explicit / Domain Policy Provider(s)
```

具体类名可由实施计划结合代码风格确定，但职责不能重新混回一个大构造函数。

**Facade**：

- 接收客户端 offered tools。
- 调 Registry resolve policy。
- 做权限检查。
- 输出 ApprovedTool。

**Registry**：

- 管理 Tool Name → Policy 的统一查找入口。
- 先匹配显式策略，再允许 Generic CRUD Provider 推导标准动作。

**Generic CRUD Provider**：

- 保留当前标准 suffix → permission action / risk 的推导逻辑。
- 只处理明确、可审计的标准命名空间。

**Explicit / Domain Provider**：

- 承载无法由 Generic CRUD 正确推导的特殊业务动作。
- 按实际规模做少量领域分组即可，不为了文件对称创建大量 Provider。

### 5.3 明确不做

- 数据库动态 Tool Policy。
- 可视化规则编辑。
- DSL。
- 插件式 Policy Runtime。
- 用户自定义脚本。
- 为所有页面预生成完整服务端策略表。

## 6. C1：Agent Loop 有限职责收敛

本轮不是“重写 Agent Loop”，而是让 `AiAgentLoopService` 回到更明确的 Orchestrator 角色。

### 6.1 保留在 Orchestrator 的职责

继续保留：

- 一个 Turn 的入口编排。
- Conversation / Run / Model Selection 的主流程协调。
- 调用 Context Assembler。
- 调用 Tool Coordinator。
- 调用 AgentRuntime。
- 根据 Runtime Result 决定 Message / Tool Call / Run State 的下一步。
- 统一异常收口。

### 6.2 本轮优先抽出的稳定职责

优先考虑两个已经稳定且继续增长会恶化的边界：

#### A. Prompt / Runtime Context Assembler

负责：

- 获取 System Prompt。
- Checkpoint 接续。
- Stored Message → `AgentRuntimeMessage` 转换。
- Page Runtime Context 组装。
- Runtime Overhead 组装。
- Prompt Cache Key 所需上下文信息。
- 构造 Runtime Messages / Runtime Tools 所需的稳定输入。

它不负责：

- Run 状态转换。
- Tool Result 持久化。
- Runtime 调用。
- Conversation 生命周期。

#### B. Tool Call Coordinator

负责：

- offered tools → server-side approved tools 协调。
- Tool Call 合法性检查。
- Navigation Tool 参数校验。
- Pending Tool Call 构造 / 持久化协调。
- Tool Result 接收。
- Page Runtime / Instance / Version 有效性校验。
- Tool Result 权限重新确认。
- Tool Result Payload 标准化。

它不负责：

- 页面真实业务执行；真实执行仍在前端受控 handler。
- 通用 Run 状态机；继续使用现有 Lifecycle / Run Service。
- Model 调用。

### 6.3 不继续拆的部分

除非实施时发现直接阻塞，不在本轮继续抽：

- ConversationResolver。
- ModelSelectionService。
- ResponseWriter。
- MessageAssembler。
- 通用 Event Bus。
- Command Framework。

判断标准：

> 只拆“职责已经稳定、继续增长会明显恶化”的边界，不为目标架构图完整制造类。

## 7. B9：关键 Agent Unit / Integration Test

当前 Fullstack E2E / Real Provider 验收继续保留，但本轮必须增加一层更快、更确定性的底层测试。

### 7.1 必须覆盖的核心不变量

至少覆盖：

1. Run Lifecycle 合法 / 非法状态转换。
2. WAITING_TOOL + Stop。
3. WAITING_TOOL + Steering / Supersede。
4. 重复 Tool Result 不产生第二次副作用。
5. Tool Result 返回时 Run 已停止 / Superseded。
6. 旧 `pageInstanceId` / `pageVersion` 被拒绝。
7. Capability Protocol 缺失 / 非 v1 / 字段非法时的行为。
8. Generic CRUD Policy 的 permission / risk 推导。
9. Explicit Policy 优先于 Generic 推导。
10. WRITE / DANGEROUS_WRITE 继续保持确认和权限边界。
11. Compaction 中 Stop / Steering 的关键状态不变量。
12. `clientRunKey` 重试 / 幂等关键行为。

### 7.2 测试层次

优先顺序：

- 纯规则：Unit Test。
- Service + Mapper 协调：Integration / Service Test。
- Page / Tool / Agent 闭环：现有 Fullstack E2E。
- Provider 特有行为：只有真正依赖模型语义时才跑 Real Provider。

不为了测试“完整”重建整套测试框架。

## 8. B10：AI SQL Migration 规则

### 8.1 目标

形成两个清晰入口：

1. **Fresh Install**：新环境一次得到当前完整 AI Schema / 必要初始数据。
2. **Incremental Migration**：已有环境能够按明确顺序从旧版本升级。

### 8.2 本轮原则

建议采用轻量文件规则，不引入迁移框架。

目标形态：

```text
sql/
├─ AI fresh-install schema（当前完整状态）
└─ AI ordered migrations（按时间 / 顺序可判断）
```

具体文件名由实施计划结合现有 workflow 决定，但必须满足：

- fresh-install 文件代表“当前完整 AI 状态”，不要求新环境重新执行所有历史阶段脚本。
- migration 文件一旦进入主线不随意改写已经发布的历史语义。
- 新 migration 使用稳定可排序命名，例如日期 + 序号 + topic。
- 每个 migration 明确前置版本 / 用途 / 是否幂等。
- workflow / 文档明确区分 fresh install 与 upgrade。
- 现有历史脚本不要为了目录好看就直接删除或重命名；如果仍被 CI / 用户升级路径引用，必须保留或提供明确替代。
- B3 的 `ai_prompt_version` 等已落地结构必须进入 fresh-install 当前状态。

### 8.3 明确不做

- Flyway。
- Liquibase。
- 自动 migration runner。
- 数据库版本管理后台。
- 为旧实验环境编写无法验证的复杂兼容链。

- production build。
- Vite 实际启动。
- 页面实际访问。
- `/dev-api` 实际联通后端。

### Agent / Tool Loop

- 普通聊天。
- 用户管理页 Query。
- 打开新增 / 编辑。
- Set Fields。
- WRITE Confirm。
- Submit。

### paired branch 要求
