## 1. 用户原始问题与本轮结论

本轮要解决的问题不是“把个人设置里的两个区块藏起来”，而是按照 D-014 将用户个人偏好与系统级 AI 治理彻底分离。

工作分支最终已经实现：

1. “我的 AI 设置”只保留当前账号的个人偏好。
2. “AI 服务连接”“系统模型”、服务提供方（Provider）令牌、系统模型增删/启停、系统默认值、模型运行参数、能力检测和连接测试等系统治理职责已经从快速设置组件（QuickSettings）完整移除。
3. 管理员与普通用户进入“我的 AI 设置”时看到的是同一套个人设置边界；没有通过管理员判断继续保留第二个系统配置入口。
4. “我的默认模型”“我的默认思考档位”继续使用用户偏好接口，并且模型范围只来自管理员已经开放、当前启用的模型集合。
5. 系统级 AI 配置继续只由正式“AI 管理 → AI 服务 / 模型管理”等管理页面承担。
6. 后端系统配置权限继续使用若依既有 RBAC：`ai:config:view`、`ai:config:edit`；普通用户读取 `GET /ai/config/models/enabled` 不等同于获得系统模型管理权限。
7. 本轮没有新增第二套配置接口、没有写死 `admin` 身份、没有扩大普通用户权限，也没有引入范围外 AI 架构。

因此 D-014 和 24 号方案规定的职责边界已经真实落到代码。

## 3. 前端实际实施

### 3.1 QuickSettings 收缩为纯个人设置

`src/components/AiAssistant/QuickSettings.vue` 删除约 393 行系统管理职责，最终只保留：

- 聊天字体大小。
- 双击 ESC 中断。
- 发送快捷键。
- 会话历史入口。
- 登录后自动继续上次会话。
- AI 默认打开方式。
- 我的默认模型。
- 我的默认思考档位。

同时删除了只为系统管理区域服务的：

- Provider 表单与状态。
- 系统模型列表、搜索和远端模型选择。
- Provider 加载、保存、测试模型加载。
- 系统模型添加、移除、启停、设为系统默认。
- 系统默认思考档位修改。
- 模型能力检测、测试连接。
- 模型运行参数对话框和对应状态。
- 上述功能的接口导入、组件导入、加载状态和专用样式。

最终 `reload()` 只执行：

```text
aiStore.loadPreferences()
aiStore.loadModels()
```

快速设置不再维护任何系统 AI 管理状态。

### 3.2 用户模型路径保持独立

`src/store/modules/ai.js` 的 `loadModels()` 继续调用：

```text
listEnabledAiModels()
→ GET /ai/config/models/enabled
```

因此“我的默认模型 / 我的默认思考档位”消费的是管理员已开放模型集合，不依赖：

- `GET /ai/config/provider`
- 系统管理版 `GET /ai/config/models`

用户偏好仍通过 `/ai/preferences` 读写。

### 3.3 正式 AI 管理入口保持完整

`src/views/ai/service/index.vue`、`src/views/ai/models/index.vue` 及共用 `src/views/ai/config/index.vue` 继续承担：

- AI 服务连接。
- Provider Base URL / Token / 启停。
- 远端模型加载。
- 系统模型添加、移除、启停。
- 系统默认模型、默认思考档位。
- 模型运行参数。
- 能力检测和连接测试。

因此本轮是“删除个人设置中的第二入口”，不是删除系统治理能力。

## 4. 后端最终状态

本轮没有发现需要修改后端运行时语义的理由，因此没有为了形式制造后端业务代码改动。

`AiConfigController` 当前继续保持：

- `GET /ai/config/provider`、`GET /ai/config/models`：`ai:config:view`。
- Provider 保存、模型增删/启停/默认设置/运行参数/能力检测/测试：`ai:config:edit`。
- `GET /ai/config/models/enabled`：用户侧启用模型读取，不授予系统配置管理能力。

普通用户真实 API 验收证明：

- 请求 `/ai/config/provider` 返回 403。
- 请求 `/ai/config/models/enabled` 返回 200，并包含管理员已开放的模型。
- 用户自己的默认模型 / 默认思考档位可以保存在 `/ai/preferences` 中。

最终代码树复核时，Backend 专项分支相对最新 AI 主线没有运行时代码差异；验收期间为配对前端专项分支临时修改的 Fullstack workflow 已恢复为主线长期版本。

## 6. 验收中发现的问题与修复闭环

本轮没有把第一次 CI 绿色当作完成，而是多次依据真实 Browser E2E 收紧验收脚本。

### 6.1 普通用户思考档位出现条件

第一次普通用户 Browser 验收直接等待“我的默认思考档位”，但该项只有选中的个人默认模型确认支持 reasoning 后才应显示。

处理：

- 保留产品条件渲染语义。
- 调整验收前置条件，明确先建立有效的用户默认模型/思考偏好。
- 再验证 Browser 重新加载后对应个人设置可见。

没有为了测试方便把思考档位改成无条件显示。

### 6.2 Element Plus Popper 文本/选项定位不稳定

后续验收曾把 QuickSettings 下拉选项的显示文本或 Popper DOM 作为关键定位条件，出现“接口启用模型真实存在，但浏览器定位不到特定 Popper 文本/option”的超时。

处理：

- 先用普通用户自己的 `/models/enabled` 证明系统开放模型真实存在。
- 用该用户自己的 `/ai/preferences` 保存合法个人默认模型与 reasoning。
- 在真实浏览器重新加载 QuickSettings，验证个人默认模型/思考档位能被正确加载，同时继续检查无系统管理入口和无系统管理请求。
- 不再让 Element Plus Teleport / Popper 的内部 DOM 细节决定业务验收成败。

这没有放宽权限或数据断言。

### 6.3 Runtime Settings 回归中的旧 Toast 时序

一次完整 Browser 回归在“恢复推荐设置”后读到 72K 而不是 64K。代码检查确认恢复推荐逻辑会发送 64K/75%，失败原因是 E2E 第二次保存后可能命中第一次保存仍存在的成功 Toast，从而在第二个 PUT 尚未结束时提前读系统模型。

处理：

- 不修改产品 Runtime Settings 逻辑。
- E2E 改为明确等待 `/runtime-settings` PUT 响应成功并等待对话框关闭，再读取持久化状态。
- rerun 同一 Fullstack workflow，attempt 2 Browser / visual / persistence 全部通过。

因此形成了“发现 → 定位真实原因 → 修复验收代码 → 针对性重跑 → 完整回归成功”的闭环。
