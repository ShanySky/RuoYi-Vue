## 1. 复盘结论

经过三个阶段，RuoYi AI 助手的主要架构方向是合理的，不需要推倒重来。

目前最重要的几根主梁已经建立：

- 独立 `ruoyi-ai` 模块。
- Provider / Model。
- Conversation / Message。
- Agent Tool Loop。
- Run / Stop / Steering。
- Checkpoint / Compaction。
- Prompt Cache。
- Page Capability。
- 跨页面连续操作。
- 前端全局 AI Store。
- 会话恢复、历史和偏好。
- AI 管理和只读审计。
- 继续复用 RuoYi 原业务 API、权限和数据范围。

真正的风险不是“前三阶段已经把底座做错”，而是当前几个核心扩展点开始快速膨胀。如果继续直接叠加第四、第五阶段大功能，后续维护成本可能明显加速。

因此建议在继续增加大功能前，先讨论一次 Phase 3.5 Architecture Hardening。

## 4. 目前偏重的部分

### 4.1 R3-03 双 ESC 的交互细节

双 ESC 的价值是给熟练用户一个快速 Stop 手段。

目前已经考虑：

- AI 焦点范围。
- 短时间双击窗口。
- Element Plus 内部 Overlay。
- 第一次 ESC 关闭控件时不计入中断序列。

这已经足够。

后续不要继续发展更多复杂手势。Stop 按钮才是核心，快捷键只是辅助。

### 4.2 R3-08 每模型上下文高级设置

底层保留每模型：

- Context Budget。
- Auto Compaction。
- Threshold。
- Reasoning。

是合理的。

但大多数管理员不需要频繁理解这些 Runtime 参数。

建议：

- 默认使用系统推荐值。
- 保持在“高级设置”。
- 不继续扩张普通模型管理表主界面的技术参数。

### 4.3 R3-10 / R3-12 页面全面 AI 化

Page Capability 是正确方向，但“所有页面所有按钮一次全部接入”会形成持续高维护成本。

建议未来将页面能力分级：

1. Level 1 可理解：页面字段、状态、结果。
2. Level 2 可交互：查询、筛选、打开、填写。
3. Level 3 可执行：保存、删除、状态变更和高影响动作。

框架应该允许渐进接入，而不是把 100% 页面覆盖作为每个阶段的前置条件。

### 4.4 R3-15 / R3-16 聊天产品体验

应该长期保留：

- 历史会话。
- 继续旧会话。
- 新建会话。
- 刷新恢复。
- 账号级保存。

已经实现的自动恢复、撤销恢复、历史入口偏好可以保留。

但后续暂时不建议继续快速增加：

- 收藏。
- 文件夹。
- Pin。
- 会话分支。
- 复杂工作区组织。

除非出现明确用户需求。

### 4.5 R3-17 / R3-18 企业管理能力

AI 管理和只读审计本身并不错误，长期甚至很重要。

需要控制的是不要继续提前建设：

- Prompt 审批工作流。
- 多级发布环境。
- 动态 Tool Policy DSL。
- 复杂部门 Agent Policy。
- 费用结算平台。
- BI 运营大屏。

## 5. 目前偏轻或需要补强的底层

### 5.1 AgentRuntime 抽象没有真正落地

第一阶段设计已经提出 `AgentRuntime` 边界。

但当前实际模型调用仍由 `AiAgentModelFactory` 直接创建 Spring AI `OpenAiChatModel`，Agent 编排对 Spring AI 细节仍有直接依赖。

当前没有功能问题。

长期风险是未来出现：

- 新 Provider 协议。
- Responses API / 不同 Tool Protocol。
- SDK 内嵌 Harness。
- 不同 Streaming / Runtime 行为。

时，`AiAgentLoopService` 会继续被具体 Runtime 细节污染。

建议补一个很薄的 SPI：

    AgentRuntime
      execute(AgentRuntimeRequest)

当前只有：

    SpringAiAgentRuntime

不要现在造复杂 Harness 平台。

### 5.2 Run 状态存在，但状态机不够显式

现在 Run 状态和转换散在：

- `AiRunService`。
- `AiRunMapper`。
- `AiMessageService`。
- `AiAgentLoopService`。

同时仍大量使用字符串状态。

当前可工作，但未来如果增加：

- WAITING_APPROVAL。
- WAITING_EXTERNAL。
- PAUSED。
- RETRYING。

状态转换会越来越难验证。

建议：

- `RunStatus enum`。
- `RunLifecycleService` / `RunStateMachine`。
- 明确允许的 transition。
- 将幂等和状态前置条件集中测试。

### 5.3 Prompt 有版本号，但没有真正版本历史

当前 `ai_prompt` 更新内容时只递增 `version_no`。

Run 会记录：

- system prompt version。
- compaction prompt version。

但 Prompt 更新后旧正文会被覆盖。

因此未来看到“Run 使用 v3”时，无法还原 v3 具体内容。

建议：

- `ai_prompt` 保留当前激活版本。
- 增加 `ai_prompt_version` 保存每个历史版本正文。

也可以考虑 snapshot/hash，但独立历史版本表更清晰。

### 5.4 Page Capability 与业务 Vue 页面耦合开始变重

目前很多业务页面直接内嵌：

- AI Query Field。
- Form Field Schema。
- Validation。
- AI Action。
- AI Context。
- Tool Handler。

短期接入效率很高。

长期会让业务页面同时承担业务 UI 和 AI Adapter。

建议逐步迁移到独立适配层，例如：

    src/ai/pages/system/user.js
    src/ai/pages/system/role.js
    src/ai/pages/monitor/job.js

业务页面只暴露必要状态和 handler。

不要一次性重写所有页面，可以随 Phase 3.5 和后续修改逐步迁移。

### 5.5 服务端 Tool Policy 单体开始膨胀

`AiFrontendToolPolicy` 当前同时负责：

- 特殊 Tool allowlist。
- Permission。
- Risk。
- JSON Schema。
- Generic CRUD 名称推导。

建议保持“代码规则”而不是做数据库动态规则引擎，但拆成：

    ToolPolicyRegistry
    ├─ GenericCrudPolicyProvider
    ├─ SystemCapabilityPolicyProvider
    ├─ MonitorCapabilityPolicyProvider
    └─ GeneratorCapabilityPolicyProvider

这样仍然明确、可控、可审计。

### 5.6 Capability Protocol 还不够正式

前端已经标记：

`ruoyi-semantic-page-v1`

但目前它主要还是一个标识。

建议明确 v1 契约：

- protocolVersion。
- pageId。
- route。
- pageInstanceId。
- pageVersion。
- capability definitions。
- pageContext。
- invocation result / error。

以后 v2 才有可控升级路径。

### 5.7 Context 上层定义很细，TokenEstimator 偏粗

Checkpoint Prompt 已经要求保留很多结构化信息。

但当前 Token 估算主要仍是字符数启发式。

建议：

    TokenEstimator
    ├─ Provider / tokenizer estimator
    └─ Heuristic fallback

同时 Checkpoint 固定结构可以逐步收敛到更稳定的核心栏目：

- 目标与当前状态。
- 用户最新决策。
- 已完成事实和副作用。
- Pending 状态。
- 下一步。
- 关键引用。

### 5.8 Run 执行取消目前主要是单 JVM 实现

当前 in-flight Future 保存在当前 JVM 内存。

对目前单实例 RuoYi 是合理的，不应该现在引入 MQ / 分布式执行平台。

但建议先抽：

`RunExecutionManager`

当前实现仍然使用本地 Executor / Future。

以后真的出现多实例部署需求时，再替换实现。

### 5.9 测试结构需要补第一层

当前 Fullstack E2E 和 Real GPT 验收非常强。

但 Run 状态越复杂，越需要快速、确定性的 Unit / Integration Test 覆盖：

- WAITING_TOOL + Stop。
- WAITING_TOOL + Steering。
- 重复 Tool Result。
- 旧 PageVersion。
- clientRunKey 重试。
- Compaction 中 Stop。
- Compaction 中 Steering。
- WRITE confirm 前后 Supersede。

长期建议形成：

    Unit / Integration
      ↓
    Agent state correctness

    Fullstack E2E
      ↓
    Real system closure

    Real Provider
      ↓
    Provider-specific behavior

### 5.10 SQL Migration 需要开始规范

当前已有：

- AI 基础 SQL。
- model selection。
- Phase 2。
- Phase 3。

继续 Phase 4 / 5 后，如果仍以阶段临时脚本增长，会越来越难判断新环境和升级环境该执行哪些文件。

建议整理为：

- AI fresh install schema。
- 有序 migrations。

不一定现在引入 Flyway/Liquibase；先建立清晰规则即可。

    ├─ Composer
    ├─ MessageList
    ├─ RunStatus
    ├─ Confirmation
    ├─ HistoryPanel
    └─ UserSettings
          ↓
       Global AI Store
          ↓

          ↓
    Page Capability Registry

### 后端

    AgentTurnOrchestrator
      ├─ ConversationService
      ├─ RunLifecycleService
      ├─ PromptContextAssembler
      ├─ Context / Checkpoint Service
      ├─ ToolCallCoordinator
      ├─ CapabilityPolicyRegistry
      └─ AgentRuntime
           └─ SpringAiAgentRuntime

这不是第二套架构，而是把当前已经存在的职责重新放到更稳定的边界中。

## 8. 建议的 Phase 3.5 候选优先级

### P0：进入下一大阶段前优先讨论

1. AgentRuntime SPI。
2. 拆 `AiAgentLoopService`，保留薄 Orchestrator。
3. Run State Machine / RunLifecycleService。
4. Page Capability Adapter 解耦。
5. `AiFrontendToolPolicy` 拆 Registry / Provider。
6. `AiAssistant` / `QuickSettings` 职责拆分。
7. Prompt Version History。
8. Capability / Agent Protocol 版本化。
9. Agent 核心 Unit / Integration Test。
10. AI SQL Migration 规则。

### P1：在 P0 之后逐步补

- `RunExecutionManager`。
- `TokenEstimator`。
- 更明确的 Capability Schema 契约。
- 页面接入 Level 1/2/3 管理方式。

### P2：有真实需求再做

- SSE / Streaming Event。
- Server Tools。
- SDK 内嵌式 Harness。
- 多实例 Agent execution。
- 更复杂页面操作策略。

## 9. 当前不建议做的事情

Phase 3.5 不应该变成“第四阶段功能开发”。

暂时不建议：

- 所有未来 RuoYi 页面 100% AI 化。
- 更多历史会话高级功能。
- 更多 UI 个性化。
- Tool Policy 可视化 DSL。
- Prompt 审批发布平台。
- 多 Agent。
- RAG。
- 分布式任务系统。
- 独立 Harness 部署。

## 10. 后续讨论方式

本文是一份问题清单和建议池。

建议后续逐项讨论：

1. 这项问题是否真实存在。
2. 是否需要现在处理。
3. 最小处理范围是什么。
4. 是否会破坏当前已经通过的 Agent / E2E。
5. 最终确认后再进入正式 `15-AI助手3.5阶段架构加固实施计划.md`。

没有经过讨论确认的建议，不应因为写在本文中就自动视为必须实施。

## 11. 最终判断

前三阶段没有把底座做坏。

相反，Conversation、Run、Tool Call、Page Capability、权限边界、Checkpoint 和前端应用级状态这些关键方向基本正确。

现在的主要任务不是推倒重建，而是趁核心规模仍可控时，把：

- Runtime。
- Run Lifecycle。
- Capability Adapter。
- Tool Policy。
- Prompt Version。
- 前端 Shell。

这些扩展边界收紧。

完成这次收敛后，再继续增加更强 Agent、更多业务页面或新的 Runtime/Harness，风险会明显更低。
