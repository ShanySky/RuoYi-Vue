## 1. 复盘结论

经过三个阶段，RuoYi AI 助手的主要架构方向是合理的，不需要推倒重来。

目前最重要的几根主梁已经建立：

- 独立 `ruoyi-ai` 模块。
- Provider / Model。
- Conversation / Message。
- Agent Tool Loop。
- Run / Stop / Steering。
- Checkpoint / Compaction。
- Prompt Cache。
- Page Capability。
- 跨页面连续操作。
- 前端全局 AI Store。
- 会话恢复、历史和偏好。
- AI 管理和只读审计。
- 继续复用 RuoYi 原业务 API、权限和数据范围。

真正的风险不是“前三阶段已经把底座做错”，而是当前几个核心扩展点开始快速膨胀。如果继续直接叠加第四、第五阶段大功能，后续维护成本可能明显加速。

因此建议在继续增加大功能前，先讨论一次 Phase 3.5 Architecture Hardening。


### 1.1 对当前底座的四维判断

为了避免把“功能多”误判成“架构已经做重”，当前三阶段整体应分四个维度判断：

- **架构方向：稳。** Conversation / Run / Tool Call / Page Capability / 权限边界 / Checkpoint / 全局 AI Store 这些主干方向基本正确，没有出现需要推倒重建的根本性错误。
- **模块边界：开始出现预警。** Agent Loop、Tool Policy、AiAssistant、QuickSettings 和业务页面内的 AI Adapter 已经承担越来越多职责；现在还能维护，但继续直接叠大功能会明显增加耦合。
- **数据模型：总体合理，但存在两个明显缺口。** Run / Checkpoint / Conversation / Message / Pending Tool 的分离是对的；Prompt 需要真正的版本历史，Run 生命周期需要更显式的状态转换约束。
- **扩展性：方向已留口，但 Runtime / Protocol 边界仍偏薄。** 现有架构已经可以继续扩展，但在新的 Provider、Runtime、Harness、更多页面能力继续进入之前，最好先把 AgentRuntime、Capability Protocol 等边界正式化。

因此当前最合适的动作不是删除第三阶段已有功能，也不是提前重做，而是做一次有限范围的架构收敛。

## 5. 目前偏重的部分

### 5.1 R3-03 双 ESC 的交互细节

双 ESC 的价值是给熟练用户一个快速 Stop 手段。

目前已经考虑：

- AI 焦点范围。
- 短时间双击窗口。
- Element Plus 内部 Overlay。
- 第一次 ESC 关闭控件时不计入中断序列。

这已经足够。

后续不要继续发展更多复杂手势。Stop 按钮才是核心，快捷键只是辅助。

同时，这里仍然需要做一次**低优先级的结构收敛**：当前双 ESC 不能长期作为一个孤立的特殊键盘逻辑留在大型 AI Assistant 组件中，否则后续开发者或 AI 很容易沿现有模式继续复制 `keydown`、焦点判断、时间窗口和状态变量，最终形成越来越多彼此独立的快捷键状态机。

建议在主要 P0 架构加固完成后的收尾阶段，建立一个足够薄的统一 AI 快捷键入口，例如 `useAiKeyboardShortcuts` 或等价模块：

- 快捷键定义集中在一个位置。
- 每个快捷键明确自己的生效上下文 / guard。
- 最终行为调用现有业务动作，例如双 ESC 只调用统一 `stopCurrentRun()`。
- 不建设全局通用 Keyboard Framework，也不提前设计复杂 DSL、优先级系统或可配置快捷键平台。
- 后续新增 AI 快捷键优先接入该机制，不再在 `AiAssistant` 内复制一套新的事件监听与状态逻辑。

该项应放在 Phase 3.5 的后段 / 收尾位置。即使因为时间或其他更重要问题暂时搁置，也不会影响 Agent 主链、权限、安全或后续大方向。

### 5.2 R3-08 每模型上下文高级设置

本项已完成讨论，最终决定是：**底层保留，配置界面轻量收敛；高级设置面向普通 RuoYi 管理员，而不是默认假设用户理解 Agent Runtime 内部机制。**

底层继续保留每模型：

- Context Budget。
- Auto Compaction。
- Threshold。
- Reasoning。

这些参数挂在模型级别是合理的，不改成单一全局值，也不因为降低 UI 暴露度而删除数据模型。

产品层调整原则：

- 默认 Reasoning 继续作为明确的模型配置保留。
- “工作上下文窗口”改名为更准确的“Agent 工作上下文预算”，避免被误解为 Provider 模型物理最大上下文。
- 默认使用系统推荐值，例如当前 64K / 自动压缩开启 / 75%。
- 上下文管理优先展示“自动（推荐）”；只有用户主动选择自定义时，才展开自动压缩开关和压缩阈值等 Runtime 参数。
- 增加“恢复推荐设置”，让管理员可以从不合理的手工组合安全回到系统推荐值。
- 不继续扩张普通模型管理表主界面的技术参数。
- 不为此重构数据库，不强行引入 NULL/override 三态模型。
- 不建设复杂 Model Profile、Provider Capability Database 或自动识别平台；以后只有 Provider 能可靠提供元数据或出现真实需求时再评估。

优先级暂定为 **P1，中低优先级**：它会影响管理员是否容易把 Runtime 配坏，因此值得处理；但它不属于第四阶段前必须先解决的核心地基问题。

### A3 核心诉求与不可偏离的设计目标

A3 后续所有方案、计划和实现必须先围绕以下核心诉求展开；这些内容是判断设计是否正确的第一标准，不能被具体技术方案反向替代。

**核心诉求：**

1. **页面天然 AI-ready，而不是后期 AI 改造。**  
   标准 RuoYi 页面在正常开发或由代码生成器生成完成后，应天然具备 AI 可以发现、理解和调用的基础结构与能力，不应再要求开发人员另外维护一套 AI 专用页面清单、字段清单或 Tool 清单。

2. **单一事实来源，不维护平行定义。**  
   页面、字段、按钮、权限、Action、接口等信息应尽可能来源于业务系统本来就存在的定义。新增一个标准字段、按钮或功能时，不应要求开发人员再“记得去 AI 模块登记一次”。

3. **自动发现应基于明确契约，而不是黑盒猜测。**  
   目标是通过 RuoYi 已有菜单/权限、标准页面结构、统一组件/Action 契约、代码生成模板和运行时注册机制，自动派生 AI 能力；不是通过扫描 DOM、猜按钮语义或反射任意 Vue 实现来碰运气。

4. **代码生成器应成为 AI-ready 页面生产入口。**  
   未来由 RuoYi 代码生成器生成的标准 CRUD 页面，应该同时具备 AI 所需的标准扩展点/契约。标准页面的 AI 基础接入成本应尽量接近零，只有特殊业务动作需要少量显式扩展。

5. **AI 页面管理负责“策略”，不负责重新登记系统事实。**  
   系统真实存在的页面、路由、按钮和权限应自动发现；AI 页面能力管理只保存和展示 AI 特有策略，例如是否允许 AI 接入、风险控制或以后确有需要的 AI 专属配置。不能把 `ai_page_config` 或前端 Catalog 变成另一份系统页面目录。

6. **特殊能力可以扩展，但不能破坏标准机制。**  
   角色数据权限、立即执行任务、代码生成等特殊动作允许显式扩展，但扩展机制应建立在统一底座之上，不能让每个特殊页面重新发明一套 AI 接入方式。

**目标体验：**

> 开发人员正常开发 RuoYi 页面；新增标准字段、按钮、权限或 Action 后，AI 基座能够基于统一机制自然发现并获得对应基础语义能力。开发人员不需要维护第二份 AI 清单。只有真正特殊、无法由标准契约表达的业务能力，才需要额外补充少量语义信息。

**防偏航规则：**

后续每一轮设计都必须回答：

- 这项设计是否减少了页面接入 AI 时的额外开发工作？
- 是否引入了新的重复事实来源或人工登记清单？
- 新增标准页面/按钮后，是否仍需要“记得再去 AI 那边配置一次”？
- 代码生成器生成的新页面是否天然具备基础 AI 接入能力？
- AI 页面管理是否仍只是策略层，而没有重新变成页面目录的第二份副本？
- 特殊页面扩展是否仍复用统一底座？

如果答案开始偏离上述目标，应优先调整方案，而不是继续沿已有技术设计向下推演。

### A3 最终收口结论

A3 已完成讨论，以下三条作为后续设计、计划和实现的长期约束：

1. **自动发现边界**  
   标准 RuoYi 页面、字段、按钮、权限和 Action 只要遵循统一页面/Action 契约，就应由系统自动发现并派生基础 AI 能力。特殊业务能力允许少量显式扩展。禁止为了追求“零配置”而走 DOM 扫描、函数猜测、任意反射等黑盒识别路线。

2. **单一事实来源**  
   页面、路由、字段、按钮、权限、Action 等业务事实不得为了 AI 再人工维护第二份定义。AI 可以补充 Risk、AI Description、确认要求等 AI 独有语义，但不能复制业务系统已经存在的事实。单一事实来源不等于所有信息必须物理写在一个对象里，而是同一个事实只能有一个权威来源。

3. **AI 页面管理定位**  
   AI 页面管理不是“页面/按钮登记中心”，而是“已发现能力的 AI 治理/策略中心”。系统真实存在的页面、按钮和权限来自 RuoYi 本身及统一契约；AI 管理只负责是否允许 AI 使用、风险/确认等 AI 专属策略，以及展示当前发现与接入状态。

**A3 北极星：**

> RuoYi 页面和业务 Action 应基于统一契约天然可被系统发现；业务事实只定义一次，AI 复用这些事实并只补充 AI 专属语义；AI 页面管理只负责治理已发现能力，而不承担重新登记页面和功能。

**代码生成器要求：**

RuoYi 代码生成器未来生成的标准页面，应天然符合上述契约，使“正常生成页面”与“获得基础 AI 接入能力”尽可能成为同一件事，而不是两个独立开发步骤。

### 5.3 R3-10 / R3-12 页面全面 AI 化

Page Capability 是正确方向，但“所有页面所有按钮一次全部接入”会形成持续高维护成本。

建议未来将页面能力分级：

1. Level 1 可理解：页面字段、状态、结果。
2. Level 2 可交互：查询、筛选、打开、填写。
3. Level 3 可执行：保存、删除、状态变更和高影响动作。

框架应该允许渐进接入，而不是把 100% 页面覆盖作为每个阶段的前置条件。

### 5.4 R3-15 / R3-16 会话连续性与用户偏好

本项已完成讨论，最终决定是：**现有设计总体合理，不做结构性调整，也不因为架构复盘而重做已经能够解决真实用户诉求的功能。**

保留现状：

- 历史会话及历史入口显示开关。
- 继续旧会话 / 会话切换。
- 新建会话。
- F5 / 刷新后的会话恢复。
- 账号级会话历史。
- 登录后自动恢复上次会话的可选偏好。
- 恢复后的撤销机制。
- 用户默认模型、Reasoning、字体、发送快捷键、助手打开方式等现有偏好。

唯一确认的轻微调整：

- 用户侧“恢复上次会话”统一改成更自然的“继续上次会话”。
- 对应设置文案可统一成“登录后自动继续上次会话”。
- 只调整用户心智和显示文案，不改变现有恢复、撤销和状态语义。

优先级：**低优先级 / Phase 3.5 后段或收尾项**。即使后续因更重要事项暂时搁置，也不影响 Agent 主链和整体架构。

后续冻结范围：没有真实用户需求时，不继续扩展收藏、Pin、文件夹、会话分支、复杂工作区组织等完整聊天产品能力。

### 5.5 R3-17 / R3-18 企业管理能力

本项已完成讨论，最终决定是：**当前 AI 管理和只读会话审计没有做重，现有能力保留。**

现阶段重点继续放在：

- 系统级 AI 配置。
- 页面/能力治理。
- 会话审计。
- 必要的运行诊断。

但这些是**当前阶段的重点，不是永久边界**。本项目的定位是在把 RuoYi 演进为 AI 时代的软件开发框架，因此不能因为当前暂时不需要，就在架构上提前封死运营分析、复杂策略、审批、成本管理、AI 运维等未来能力。

原则是：

> 当前不主动建设，不等于未来禁止建设；是否扩展由后续真实产品需求决定。

其中“页面能力”管理继续服从 A3 已确认的原则：系统能力自动发现，AI 管理负责治理和策略，而不是维护第二份页面登记清单。

## 6. 目前偏轻或需要补强的底层

### 6.1 代理运行时（Agent Runtime）抽象没有真正落地

**B1 最终决定：**

现在建立一层很薄的代理运行时接口（Agent Runtime SPI），目的只是隔离具体模型框架和模型调用方式，不把业务代理逻辑一起下沉进去。

职责边界：

- 代理编排层负责会话（Conversation）、运行（Run）、停止（Stop）、纠偏（Steering）、检查点（Checkpoint）、工具调用流程和业务能力调度。
- 代理运行时负责向模型发送请求、接收响应，并统一返回文本、工具调用、用量等标准结果。
- Spring AI 代理运行时负责封装 Spring AI 自己的消息、提示词（Prompt）、工具回调（ToolCallback）、模型响应（ChatResponse）和 OpenAI 聊天模型（OpenAiChatModel）等实现细节。
- 页面、后端接口、数据库、Harness 等“AI 能做什么”的能力体系，以及权限、风险和治理规则，不属于代理运行时职责。

当前只需要一个 Spring AI 代理运行时实现，不建设多运行时管理后台、动态切换平台或复杂插件体系。

优先级：**P0，属于进入下一大阶段前应完成的底座加固。**


第一阶段设计已经提出 `AgentRuntime` 边界。

但当前实际模型调用仍由 `AiAgentModelFactory` 直接创建 Spring AI `OpenAiChatModel`，Agent 编排对 Spring AI 细节仍有直接依赖。

当前没有功能问题。

长期风险是未来出现：

- 新 Provider 协议。
- Responses API / 不同 Tool Protocol。
- SDK 内嵌 Harness。
- 不同 Streaming / Runtime 行为。

时，`AiAgentLoopService` 会继续被具体 Runtime 细节污染。

建议补一个很薄的 SPI：

    AgentRuntime
      execute(AgentRuntimeRequest)

当前只有：

    SpringAiAgentRuntime

不要现在造复杂 Harness 平台。

### 6.2 运行（Run）状态存在，但状态机不够显式

**B2 最终决定：**

建立统一的运行生命周期服务（Run Lifecycle Service），由它集中定义运行状态和合法转换关系。

目标：

- 停止、纠偏、等待工具、工具结果返回、上下文压缩、完成和失败都通过统一生命周期入口改变状态。
- 明确每个状态允许进入哪些后续状态，以及转换需要满足的前置条件。
- 避免状态转换继续分散在多个服务和数据库更新语句中。
- 通过单元/集成测试验证非法转换、重复结果和竞争条件。
- 不引入通用工作流引擎，也不为了状态机建立复杂配置系统。

优先级：**P0。**


现在 Run 状态和转换散在：

- `AiRunService`。
- `AiRunMapper`。
- `AiMessageService`。
- `AiAgentLoopService`。

同时仍大量使用字符串状态。

当前可工作，但未来如果增加：

- WAITING_APPROVAL。
- WAITING_EXTERNAL。
- PAUSED。
- RETRYING。

状态转换会越来越难验证。

建议：

- `RunStatus enum`。
- `RunLifecycleService` / `RunStateMachine`。
- 明确允许的 transition。
- 将幂等和状态前置条件集中测试。

### 6.3 提示词（Prompt）有版本号，但没有真正版本历史

**B3 最终决定：**

建立真正的提示词版本历史，但不按会话或运行重复保存完整提示词。

存储原则：

- 每次提示词正文发生变化时，生成新的版本记录并保存该版本的完整正文。
- 同一个提示词版本无论被多少会话或运行使用，正文都只保存一次。
- 会话 / 运行只保存对应提示词版本记录的引用。
- 审计时通过版本引用还原当时真实使用的提示词正文。
- 对动态变量不默认保存每次完整渲染结果；仅在确有审计需要时保存必要参数、上下文摘要或校验信息。

当前不建设复杂的提示词审批、发布环境、版本工作流或完整提示词运营平台。

优先级：**P0。**


当前 `ai_prompt` 更新内容时只递增 `version_no`。

Run 会记录：

- system prompt version。
- compaction prompt version。

但 Prompt 更新后旧正文会被覆盖。

因此未来看到“Run 使用 v3”时，无法还原 v3 具体内容。

建议：

- `ai_prompt` 保留当前激活版本。
- 增加 `ai_prompt_version` 保存每个历史版本正文。

也可以考虑 snapshot/hash，但独立历史版本表更清晰。

### 6.4 页面能力（Page Capability）与业务 Vue 页面耦合开始变重

目前很多业务页面直接内嵌：

- AI Query Field。
- Form Field Schema。
- Validation。
- AI Action。
- AI Context。
- Tool Handler。

短期接入效率很高。

长期会让业务页面同时承担业务 UI 和 AI Adapter。

建议逐步迁移到独立适配层，例如：

    src/ai/pages/system/user.js
    src/ai/pages/system/role.js
    src/ai/pages/monitor/job.js

业务页面只暴露必要状态和 handler。

不要一次性重写所有页面，可以随 Phase 3.5 和后续修改逐步迁移。

### 6.5 服务端工具策略（Tool Policy）单体开始膨胀

`AiFrontendToolPolicy` 当前同时负责：

- 特殊 Tool allowlist。
- Permission。
- Risk。
- JSON Schema。
- Generic CRUD 名称推导。

建议保持“代码规则”而不是做数据库动态规则引擎，但拆成：

    ToolPolicyRegistry
    ├─ GenericCrudPolicyProvider
    ├─ SystemCapabilityPolicyProvider
    ├─ MonitorCapabilityPolicyProvider
    └─ GeneratorCapabilityPolicyProvider

这样仍然明确、可控、可审计。

### 6.6 能力协议（Capability Protocol）还不够正式

前端已经标记：

`ruoyi-semantic-page-v1`

但目前它主要还是一个标识。

建议明确 v1 契约：

- protocolVersion。
- pageId。
- route。
- pageInstanceId。
- pageVersion。
- capability definitions。
- pageContext。
- invocation result / error。

以后 v2 才有可控升级路径。

### 6.7 上下文（Context）上层定义很细，令牌估算器（TokenEstimator）偏粗

Checkpoint Prompt 已经要求保留很多结构化信息。

但当前 Token 估算主要仍是字符数启发式。

建议：

    TokenEstimator
    ├─ Provider / tokenizer estimator
    └─ Heuristic fallback

同时 Checkpoint 固定结构可以逐步收敛到更稳定的核心栏目：

- 目标与当前状态。
- 用户最新决策。
- 已完成事实和副作用。
- Pending 状态。
- 下一步。
- 关键引用。

### 6.8 运行执行取消目前主要是单 JVM 实现

当前 in-flight Future 保存在当前 JVM 内存。

对目前单实例 RuoYi 是合理的，不应该现在引入 MQ / 分布式执行平台。

但建议先抽：

`RunExecutionManager`

当前实现仍然使用本地 Executor / Future。

以后真的出现多实例部署需求时，再替换实现。

### 6.9 测试结构需要补第一层

当前 Fullstack E2E 和 Real GPT 验收非常强。

但 Run 状态越复杂，越需要快速、确定性的 Unit / Integration Test 覆盖：

- WAITING_TOOL + Stop。
- WAITING_TOOL + Steering。
- 重复 Tool Result。
- 旧 PageVersion。
- clientRunKey 重试。
- Compaction 中 Stop。
- Compaction 中 Steering。
- WRITE confirm 前后 Supersede。

长期建议形成：

    Unit / Integration
      ↓
    Agent state correctness

    Fullstack E2E
      ↓
    Real system closure

    Real Provider
      ↓
    Provider-specific behavior

### 6.10 数据库迁移（SQL Migration）需要开始规范

当前已有：

- AI 基础 SQL。
- model selection。
- Phase 2。
- Phase 3。

继续 Phase 4 / 5 后，如果仍以阶段临时脚本增长，会越来越难判断新环境和升级环境该执行哪些文件。

建议整理为：

- AI fresh install schema。
- 有序 migrations。

不一定现在引入 Flyway/Liquibase；先建立清晰规则即可。

## 12. 最终判断

前三阶段没有把底座做坏。

相反，Conversation、Run、Tool Call、Page Capability、权限边界、Checkpoint 和前端应用级状态这些关键方向基本正确。

现在的主要任务不是推倒重建，而是趁核心规模仍可控时，把：

- Runtime。
- Run Lifecycle。
- Capability Adapter。
- Tool Policy。
- Prompt Version。
- 前端 Shell。

这些扩展边界收紧。

完成这次收敛后，再继续增加更强 Agent、更多业务页面或新的 Runtime/Harness，风险会明显更低。
