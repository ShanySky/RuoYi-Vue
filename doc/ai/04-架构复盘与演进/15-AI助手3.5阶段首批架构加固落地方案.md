## 1. 本轮目标

本轮只落地已经明确确认的三个底层加固事项：

1. B1：代理运行时接口（Agent Runtime SPI）。
2. B2：运行生命周期与状态转换（Run Lifecycle）。
3. B3：提示词版本历史（Prompt Version History）。

本轮目标不是扩大 AI 功能面，而是在不改变当前已验证产品行为的前提下，把未来继续扩展 Agent、模型运行时、虚拟员工和自进化能力所依赖的几个底层边界先稳定下来。

总体产品目标仍以总体设计为最高约束：

> AI 最终要理解真实业务并帮助用户完成业务；进一步能够作为虚拟员工自主承担业务，并在成熟治理机制下逐步形成持续自我改进能力。

本轮所有技术改造都必须服务于这一主线，而不是为了形式上的“架构完整”进行无关重构。

## 2. B1：代理运行时接口

### 2.1 目标

在当前代理编排与 Spring AI 之间建立一层足够薄的代理运行时接口。

目标边界：

    代理编排层
        ↓
    代理运行时接口（Agent Runtime）
        ↓
    Spring AI 代理运行时

代理编排层应逐步只认识 RuoYi AI 自己定义的运行时请求与结果，不再直接依赖 Spring AI 的具体消息、提示词、工具回调、模型响应和模型对象。

### 2.2 代理运行时负责

- 向模型发送一次代理运行请求。
- 接收模型响应。
- 将具体模型框架返回结果转换为 RuoYi AI 自己的标准结果。
- 返回文本、工具调用、模型用量、结束原因等运行时结果。
- 在 Spring AI 实现内部封装 Spring AI 特有类型和调用方式。

### 2.3 代理运行时不负责

以下职责不得下沉到代理运行时：

- 会话管理。
- 运行状态与生命周期。
- 停止与纠偏。
- 检查点与上下文压缩业务规则。
- 页面、后端接口、数据库、环境执行框架等能力治理。
- 用户权限、工具风险和写操作确认。
- 虚拟员工职责、任务和业务流程。

一句话边界：

> 代理运行时负责“怎么和模型交互”；RuoYi AI 框架负责“AI 能做什么、允许做什么、如何安全地做”。

### 2.4 当前实施范围

当前只实现一个 Spring AI 代理运行时。

本轮不建设：

- 多运行时管理后台。
- 运行时动态切换平台。
- 复杂插件式运行时生命周期。
- 独立 Harness 平台。
- 因 B1 顺手进行的代理编排层大规模重写。

如果为隔离 Spring AI 类型必须调整现有调用签名，可以做最小必要改造，但不得借机实施尚未讨论的 C1 / D2 大规模职责拆分。

## 3. B2：运行生命周期与状态转换

### 3.1 目标

建立统一的运行生命周期服务（Run Lifecycle Service），集中管理运行状态和合法转换关系。

当前已有运行状态和实际业务行为，但状态转换仍分散在多个服务和数据更新入口中。随着停止、纠偏、工具返回、上下文压缩等能力增加，这种分散方式会增加竞争条件和非法状态转换风险。

### 3.2 本轮需要建立的边界

- 运行状态使用明确、集中定义的状态类型。
- 明确每个状态允许转换到哪些后续状态。
- 明确状态转换需要满足的前置条件。
- 停止、纠偏、等待工具、工具结果返回、上下文压缩、完成和失败等状态变化统一通过生命周期入口完成。
- 旧运行被新指令替代后，不得继续产生新的工具调用或写操作。
- 工具结果返回时必须重新确认运行仍然有效。
- 状态转换应具备幂等和竞争条件保护。

### 3.3 本轮不做

- 不引入通用工作流引擎。
- 不建设可视化状态机配置。
- 不引入消息队列或分布式运行平台。
- 不实施尚未讨论的运行执行管理器（Run Execution Manager）完整抽象。
- 不因为状态机加固而改变现有单会话最多一个活动运行的产品语义。

当前本地线程 / Future 取消机制可以继续使用；本轮只需保证它与新的运行生命周期边界正确协作。

## 4. B3：提示词版本历史

### 4.1 目标

建立真正可追溯的提示词历史版本。

当前只有版本号递增而没有完整历史正文，历史运行只能知道“用了第几版”，无法准确还原当时实际使用的提示词内容。

### 4.2 存储原则

- 提示词正文按“版本”保存。
- 每次提示词正文发生变化时，生成新的历史版本并保存完整正文。
- 同一个提示词版本无论被多少会话或运行使用，正文只保存一次。
- 会话 / 运行只保存能够唯一定位对应提示词版本的引用，不重复保存完整提示词。
- 审计时可以根据运行记录准确还原当时使用的提示词版本正文。
- 动态变量默认不按每次运行保存完整渲染后的提示词；只有存在明确审计需要时，才保存必要动态参数、摘要或校验信息。

### 4.3 本轮不做

- 不建设提示词审批流程。
- 不建设多环境发布体系。
- 不建设复杂回滚工作流。
- 不建设完整提示词运营平台。

### 4.4 与数据库迁移规范的关系

B10“AI 数据库迁移规范”尚未讨论。

因此本轮可以完成 B3 所必需的表结构和 SQL 变更，但：

- 不提前引入 Flyway、Liquibase 或新的迁移框架。
- 不擅自决定未来全部 AI SQL 的长期组织方式。
- 使用当前仓库可兼容、可验证的最小数据库变更方式。
- 后续 B10 讨论数据库迁移规范时，再统一整理长期规则。

## 5. 与尚未讨论事项的边界

### 5.1 明确不纳入本轮

以下事项尚未最终讨论完成，不得因为实现 B1 / B2 / B3 顺手落地：

- B4 页面能力适配层具体实现。
- B5 工具策略拆分。
- B6 能力协议正式化。
- B7 令牌估算器 / 检查点进一步调整。
- B8 运行执行管理器。
- B9 完整代理单元 / 集成测试体系设计。
- B10 AI 数据库迁移长期规范。
- C1 后端代理循环服务的大规模职责拆分。
- C2 前端 AI 助手组件大规模拆分。
- C3 页面能力与业务页面耦合的具体重构。
- D1 / D2 长期前后端目标结构的最终定型。
- 技能（Skill）、模型上下文协议（MCP）、插件（Plugin）、Harness、虚拟员工、自进化系统的具体功能开发。

### 5.2 已确认但本轮不抢先做的低优先级事项

A1、A2、A4 已经确认方向，但本轮不作为首批开发主线：

- 统一 AI 快捷键入口。
- 模型高级设置界面轻量收敛。
- “恢复上次会话”调整为“继续上次会话”等文案。

这些事项可以在后续 Phase 3.5 收尾时处理，避免与本轮后端底座加固并行产生无必要冲突。

## 6. 实施依赖与顺序原则

B1 和 B2 都会触及当前代理主链、运行服务和模型调用路径，建议由同一个实施会话按实施计划顺序完成，不建议拆成两个并行代码会话同时修改同一批核心文件。

B3 相对独立，但涉及数据库结构、提示词服务和运行记录，也应在同一首批加固计划中统一验证。

具体代码步骤、类名、迁移文件组织和提交拆分，由后续实施计划在重新检查当前真实代码后确定，本文不提前把实现细节锁死。

## 7. 实施前强制检查

后续实施会话开始前必须：

1. 重新检查前后端 `chatgpt/ai-agent-assistant` 当前真实分支状态。
2. 阅读总体设计、三阶段架构复盘和本落地方案。
3. 检查自本方案创建后是否已有其他会话提交了相关代码。
4. 基于当前真实代码形成独立实施计划。
5. 实施计划必须逐项对应 B1、B2、B3，并明确哪些内容属于非目标。
6. 实施前先自检计划是否越过本文边界。

如果实施过程中发现必须先决定某个“⏸ 待定”或“⬜ 未讨论”事项才能继续，应停止该部分并记录阻塞点，不得自行替代架构讨论作出长期决策。

## 8. 验证要求

本轮完成不能只以“代码写完”或“编译通过”为标准。

至少应覆盖：

- 后端完整编译。
- 新增或调整的关键状态转换测试。
- 停止、纠偏、等待工具、工具结果返回、上下文压缩等核心运行路径回归。
- Spring AI 代理运行时下现有模型调用、工具调用、Reasoning、Prompt Cache 等能力不退化。
- 提示词更新后能够保留历史正文。
- 历史运行能够准确定位到对应提示词版本。
- 数据库变更在真实 MySQL 环境中可执行。
- 条件允许时运行现有 AI 全栈端到端测试和真实 Provider 验收，确认 Agent 主链没有被架构加固破坏。

新增测试应服务于本轮改造本身，不借机实施尚未讨论的完整 B9 测试体系重构。

## 9. 完成定义

本轮首批架构加固只有同时满足以下条件才视为完成：

1. B1、B2、B3 均按本文边界落地。
2. 未主动实施任何待定 / 未讨论架构事项。
3. 当前已验证的聊天、停止、纠偏、工具调用、上下文压缩、提示词和模型能力没有明显回归。
4. 关键改造已经真实运行验证，而不是只有静态检查。
5. 实施记录能够说明每一项改了什么、验证了什么、还留下什么问题。
6. 如果某项因待定架构问题被阻塞，应明确保留为未完成，而不是自行扩大设计范围。

## 11. 分支与提交策略

为了同时保证讨论过程可追溯、实施过程可审查，并避免 `chatgpt/ai-agent-assistant` 主开发分支被大量细碎讨论提交和专项开发提交交叉污染，本阶段采用“主开发分支 + 架构讨论分支 + 专项实施分支”的工作方式。

### 11.1 分支职责

主开发分支：

    chatgpt/ai-agent-assistant

职责：

- 保存已经成熟、已经确认并准备作为后续开发基线的成果。
- 尽量保持提交历史清晰。
- 不直接承载长时间架构讨论过程中的大量细粒度文档提交。
- 不直接承载尚未完成验收的专项架构加固开发。

架构讨论分支：

    chatgpt/ai-agent-architecture-discussion

职责：

- 继续 B4～F 等架构讨论。
- 每确认一个讨论点，可以立即更新文档并提交，保证讨论结果不会因会话中断或切换而丢失。
- 允许保留较细粒度的讨论提交，因为这些提交首先服务于讨论过程的安全和可追溯性。
- 在一个自然里程碑完成后，再整理提交历史，并将成熟结果合入主开发分支。

专项实施分支：

    chatgpt/ai-agent-hardening-b1-b3

职责：

- 只实施本文已经确认的 B1、B2、B3。
- 在该分支中创建和维护后续 16 号实施计划、实现代码、数据库变更、测试和实施记录。
- 不在该分支继续推进 B4～F 架构讨论，也不自行改变 14 / 15 号文档中已经确认的边界。
- 完成开发、测试和验收后，整理提交历史，再合入主开发分支。

如果实际创建分支时需要调整名称，可以使用语义等价名称，但必须保持“讨论分支”和“实施分支”职责隔离。

### 11.2 讨论分支的提交方式

架构讨论过程中继续采用：

    确认一个关键决策
        ↓
    更新文档
        ↓
    立即提交

这样做的首要目标是：

- 避免会话中断造成决策丢失。
- 让新会话能够仅通过 Git 仓库恢复已经确认的讨论状态。
- 保证每个关键决策都有明确时间点和变更记录。

讨论过程中不要求每个提交都适合长期保留在主开发分支历史中。

当完成一个自然里程碑，例如整个 B 组、C 组或某个完整架构主题后，再统一整理讨论分支提交：

- 可以使用交互式变基（interactive rebase）。
- 根据实际内容进行合并（squash / fixup）、重命名或重新组织。
- 最终保留 1～3 个能够表达完整里程碑的有意义提交，而不是机械保留所有细粒度讨论提交。
- 整理完成后再合入 `chatgpt/ai-agent-assistant`。

在里程碑结束之前，不应频繁重写已经推送到 GitHub 的讨论分支历史，避免其他会话基于旧提交继续工作时产生混乱。

### 11.3 实施分支的提交方式

专项实施分支允许在开发过程中进行正常的细粒度提交，例如：

- 先完成 B1 基础抽象。
- 再调整现有调用链。
- 再完成 B2 状态转换。
- 再完成 B3 数据与服务改造。
- 再补测试和验收记录。

实施过程中首先保证可回溯和可验证，不为了“主分支历史漂亮”而减少必要提交。

当 B1、B2、B3 全部完成并通过验收后，再对实施分支提交进行整理。

最终合回主开发分支时，应尽量保留少量有明确语义的提交，或者采用压缩合并（Squash Merge），避免把实施过程中的临时修正、测试修复和中间状态全部带入长期主线历史。

### 11.4 跨会话的事实来源

不同 ChatGPT 会话之间不能依赖“当前会话里的临时上下文”作为长期事实来源。

跨会话可以可靠依赖的是：

- GitHub 中已经提交的代码。
- GitHub 中已经提交的文档。
- 明确指定的分支和提交。

不能假设新会话能够可靠看到：

- 当前会话尚未写入仓库的讨论结论。
- 当前会话中的临时草稿。
- 某个会话私有环境中的未提交文件或临时工作区状态。
- 只存在于模型短期上下文中的约定。

因此，架构讨论中“确认一个点就提交”的做法在讨论分支上继续保留；真正需要控制的是这些细粒度提交不要直接长期堆积在主开发分支中。

### 11.5 合并原则

无论讨论分支还是实施分支，合入主开发分支前都必须满足：

1. 对应里程碑已经形成明确结论。
2. 文档和代码与当前真实仓库状态一致。
3. 已完成必要验证。
4. 已确认没有把待定 / 未讨论事项误带入。
5. 提交历史已经整理到适合长期保留的粒度。
6. 合并后主开发分支仍能作为下一阶段的稳定开发基线。

最终工作流：

    chatgpt/ai-agent-assistant
        ├─ chatgpt/ai-agent-architecture-discussion
        │    讨论 → 细粒度提交 → 里程碑 → 整理提交 → 合并
        │
        └─ chatgpt/ai-agent-hardening-b1-b3
             计划 → 开发 → 测试 → 验收 → 整理提交 → 合并

这套策略的目标是同时满足两件事：

> 讨论过程足够安全、可恢复；主开发分支足够清晰、可维护。
