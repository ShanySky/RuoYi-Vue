## 1. 本轮目标与边界

本轮只完成 Phase 3.5 剩余 P0 地基加固：

1. **B4**：统一 Page / Action Contract 与 Page Capability Adapter 基座，只迁移 `/system/user` 用户管理代表页。
2. **B5**：将 Tool Policy 收敛成轻量 Registry + Generic CRUD + 少量 Explicit Provider。
3. **B6**：正式冻结 `ruoyi-semantic-page-v1` 最小 Capability Protocol。
4. **C1**：对 `AiAgentLoopService` 做有限职责拆分，只抽稳定的 Context Assembly 与 Tool Coordination 边界。
5. **B9**：补齐 Run、Tool Result、Protocol、Page Runtime、WRITE、Compaction 等核心不变量的确定性测试。
6. **B10**：建立清晰的 AI fresh-install schema 与有序 migration 规则，并把 CI / E2E 切到可验证的安装与升级路径。

本轮最终仍服务于总体产品目标：

> AI 理解真实业务并帮助用户完成业务 → 虚拟员工自主承担业务 → 受治理的持续自我改进系统。

因此本轮关注的是**稳定语义边界、安全边界和可验证性**，不是增加第四阶段功能。

## 3. B4：Page / Action Contract 与 Adapter 基座

### 3.1 目标结构

本轮建立下面这一条统一链路：

```text
真实业务状态 / 规则 / 字典 / options / 既有 handler / API
                ↓
        Page / Action Contract
                +
          Runtime Bindings
                ↓
     Page Capability Adapter
                ↓
          Tool Registry
                ↓
   ruoyi-semantic-page-v1
```

本轮不把 Vue 页面改造成 metadata-driven UI，也不建立第二套业务状态。

### 3.2 新增 Page Contract 基础

前端新增：

- `src/ai/capabilityProtocol.js`
- `src/ai/pageCapabilityContract.js`

`capabilityProtocol.js` 只放最小协议常量与纯校验/身份比较 helper，例如：

- `RUOYI_SEMANTIC_PAGE_PROTOCOL = "ruoyi-semantic-page-v1"`
- active page runtime 是否完整。
- expected runtime 与 current runtime 的 protocol / pageId / route / pageInstanceId / pageVersion 比较。

不做协议协商、版本注册中心或多协议插件机制。

`pageCapabilityContract.js` 提供轻量 `definePageCapabilityContract(...)`，稳定描述：

- `pageId`
- `pageName`
- `route`
- `toolPrefix`
- 标准 query field declaration
- 标准 form field declaration
- standard action / special action semantic declaration

Contract 中可以保存 AI 所需 description / field schema hint，但**不把客户端 risk 当作安全权威**；最终 risk 继续只由后端 Tool Policy 决定。

### 3.3 Contract 与 Runtime Bindings 的分工

Contract 只定义稳定语义。

Runtime Bindings 继续从页面获得真实运行时事实：

- queryParams / dateRange。
- form。
- 当前 rules。
- dicts / departments / posts / roles 等 options。
- rows / total / selectedIds。
- handleQuery / resetQuery。
- openAdd / openEdit。
- set fields。
- submit core。
- delete / status / reset password / auth role / import / export 等真实 handler 或已有 API core。

原则：

- 表单校验规则不复制成第二套。
- options 不手工再维护第二份枚举。
- Tool 执行不能绕过既有业务 API。
- human UI 与 AI 需要不同确认 UI 时，可以共用“真正执行业务副作用”的 core action，而各自保留自己的确认入口。

### 3.4 改造 `createAiCrudPageCapabilities`

继续复用 `src/ai/crudPageCapabilities.js`，不创建第二个 CRUD 框架。

将现有 `createAiCrudPageCapabilities(options)` 内部规范化为：

- 新模式：`contract + bindings`。
- 旧页面现有 flat options 继续通过内部兼容 normalization 使用同一套生成逻辑。

要求：

- 不导出第二套长期并行的 CRUD runtime。
- 兼容分支只为了 P0 不提前批量迁移。
- P1 全量 Page Capability 迁移完成后，删除旧 flat-options 兼容入口。
- P0 结束时必须在文档中明确列出仍使用 legacy declaration 的页面，不能把它变成无限期自然演进。

### 3.5 改造 Tool Registry

`src/ai/toolRegistry.js` 调整为：

- active Page Runtime 明确包含 `capabilityProtocol / pageId / pageName / route / pageInstanceId / pageVersion`。
- 注册时以 Page Contract 的 pageId / route 作为稳定身份。
- Tool invoke 前校验 protocol + pageId + route + instance + version。
- 导航后继续等待新页面重新注册，旧实例仍立即失效。
- `getCurrentPageContext()` 可继续把 Runtime 信息提供给模型，但请求级顶层字段才是后端安全校验所依据的身份字段。
- `app_navigate` 仍是应用级 Tool，不要求存在 active semantic page。

现有 `useAiPageTools` 可做向后兼容的参数 normalization，但内部只保留一个 register/runtime 路径。

### 3.6 用户管理代表页迁移

新增：

- `src/ai/pages/systemUserPageCapability.js`

该文件承载 `/system/user` 的 Page Contract，并提供把页面 Runtime Bindings 交给通用 CRUD Adapter 的薄层。

`src/views/system/user/index.vue` 本轮只保留：

- 真实业务 refs / rules / dicts / options。
- 真实页面 handler。
- 为 AI 提供 Runtime Bindings 的小型 wiring。
- 注册 / 卸载 Page Capability。

需要从页面主体中迁出的内容：

- 重复的 pageId / pageName / route / toolPrefix。
- 大段 AI-only query/form semantic declaration。
- 大段 custom action Tool declaration。
- AI schema 构造细节。
- AI-only options/context 映射 helper，能够安全放到 companion module 的部分。

### 3.7 用户管理业务动作复用

对当前用户页已经存在但 human / AI 各走一段重复执行逻辑的动作，优先抽“业务副作用 core”，再由两种入口调用。例如：

- delete users core。
- change status core。
- reset password core。
- auth role navigation core。
- 已有 `submitFormCore` 继续复用。

human UI 自己的 MessageBox / Prompt 与 AI 宿主的 WRITE Confirm 可以不同，但最终写数据库的业务动作不能复制成两套。

不为此改造整个 RuoYi UI 架构。

### 3.8 `pageCapabilityCatalog` 的 P0 处理

`src/ai/pageCapabilityCatalog.js` 当前只用于 AI 页面治理页展示“注册状态”。

本轮不重做整个治理目录，但要避免给用户代表页继续保存第二份 pageName / route 事实：

- `/system/user` 的 catalog 条目改为从 `systemUserPageContract` 派生。
- 其他未迁移页面继续保留现有 legacy catalog 条目，直到 P1 集中迁移。
- catalog 不参与 Tool schema、risk、permission 或业务执行，不升级为第二套 Capability Registry。
- P1 全量迁移时再把剩余静态 catalog 项逐页转为 Contract 派生，并最终消除 legacy catalog 双形态。

### 3.9 B4 代表页完成条件

用户管理至少证明：

- query / reset / pagination。
- add open / set fields / submit。
- edit open / safe set fields / submit。
- 真实 rules / dynamic options。
- view。
- delete。
- change status。
- reset password。
- auth role。
- import open / export。
- READ / UI / WRITE / DANGEROUS_WRITE 风险语义。
- permission filter。
- WRITE Confirm。
- stale page instance/version 拒绝。
- Tool Result 回到原 Run。
- 页面刷新 / 导航后旧实例失效。

本轮到此停止，不迁移 role / menu / dept / monitor / generator 等其他页面。

## 4. B6：`ruoyi-semantic-page-v1` 正式化

### 4.1 正式线协议字段

对于存在 active semantic page 的请求，前后端统一以下顶层字段：

```text
capabilityProtocol = "ruoyi-semantic-page-v1"
pageId
route
pageInstanceId
pageVersion
pageContext
frontendTools
```

Tool Result 保持最小结构：

```text
callId
success
result
error
```

不增加复杂 envelope、协商机制、协议注册平台。

### 4.2 无 active page 的普通聊天

普通聊天与仅使用 `app_navigate` 的请求继续允许没有 semantic page runtime：

- `capabilityProtocol` 可缺省 / null。
- `pageId / pageInstanceId / pageVersion` 可缺省 / null。
- 当前 route 仍可作为普通 UI 环境信息存在。
- 仅 `app_navigate` 不视为“当前页面 Capability”。

### 4.3 何时必须验证 v1

只要请求出现以下任一条件，就按 semantic page request 验证：

- 存在非 `app_navigate` 的前端 Page Tool。
- 存在 pageId。
- 存在 pageInstanceId。
- 存在 pageVersion。

此时必须满足：

- protocol 精确等于 `ruoyi-semantic-page-v1`。
- pageId 非空。
- route 非空。
- pageInstanceId 非空。
- pageVersion 合法。

不允许“有 Page Tool 但没有正式 Page Runtime”的半协议状态。

### 4.4 后端 DTO / Pending Tool 落点

修改：

- `AiChatTurnRequest`：新增 `capabilityProtocol / pageId`。
- `AiPendingToolCall`：新增 `capabilityProtocol / pageId`。
- `AiPendingToolCallMapper`：持久化和读取两个字段。
- fresh-install schema 与 P0 migration：增加对应数据库列。

新增：

- `com.ruoyi.ai.protocol.AiCapabilityProtocolValidator`

Validator 只做：

- semantic-page request 识别。
- v1 字段完整性。
- 请求 runtime identity 基础合法性。
- Tool Result continuation 与 Pending Tool 快照的 protocol / pageId / route / pageInstanceId / pageVersion 一致性。

不做 Tool Policy、不做业务权限、不做页面业务逻辑。

### 4.5 Pending Tool 为什么必须保存 protocol / pageId

Tool Call 发出后，浏览器可能：

- 刷新页面。
- 跳转页面。
- 重新注册同 route 页面。
- 收到 Steering。
- 在 Tool Result 返回前能力版本发生变化。

因此 Tool Result 校验不能只相信当前 request，也不能从 `pageContext` 反推身份。

Pending Tool 必须持久化 Tool Call 发出时的：

- capabilityProtocol
- pageId
- route
- pageInstanceId
- pageVersion

这五项共同构成 P0 的“原页面实例快照”。

### 4.6 迁移时的旧 Pending Tool

升级数据库时，迁移前已经存在且仍为 `PENDING` 的旧 Tool Call 没有 protocol / pageId 快照，不能安全恢复为 v1。

本轮 migration 明确将这类旧 `PENDING` 记录标记为失效/过期，不尝试猜测补值。

已 RESOLVED / CANCELLED / SUPERSEDED 的历史记录保留原样，不伪造协议事实。

### 4.7 错误语义

P0 不新增复杂错误 DSL / error envelope。

统一规则：

- Protocol 无效、Page Runtime stale、Policy 拒绝、权限变化：走服务端明确的拒绝异常路径，并保持可测试的稳定错误分类/消息。
- 浏览器真实业务执行失败：仍通过 `toolResult.success=false + error` 返回模型。
- 正常业务结果：`success=true + result`。
- 页面失效不能伪装成普通业务返回。

## 5. B5：Tool Policy 轻量职责收敛

### 5.1 最终职责链

```text
AiFrontendToolPolicy
       ↓
ToolPolicyRegistry
       ├─ SystemToolPolicyProvider
       ├─ MonitorToolPolicyProvider
       ├─ GeneratorToolPolicyProvider
       └─ GenericCrudToolPolicyProvider
```

总原则：少量明确 Provider，不做插件系统。

### 5.2 具体类

新增 / 拆出：

1. `ToolPolicyDefinition`
   - server-side riskLevel
   - requiredPermission
   - description
   - inputSchema

2. `ToolPolicyRegistry`
   - 统一 resolve。
   - **Explicit first，Generic second**。
   - 不读数据库。
   - 不维护动态规则。

3. `GenericCrudToolPolicyProvider`
   - 承接当前 `deriveCrudPolicy`。
   - 保留当前 suffix → permission action / risk 映射。
   - 只处理严格 `page_<module>_<resource>_<known-action>` 命名。
   - 保留 resource remap（role_auth_user / dict_data / job_log / gen_edit 等）。

4. `SystemToolPolicyProvider`
   - `app_navigate`。
   - 当前 `page_system_*` 中需要显式 schema / risk / permission 的动作。
   - 用户管理精确策略继续放这里，确保 explicit schema 覆盖 generic flexible schema。
   - profile / role data scope / auth 等特殊系统动作。

5. `MonitorToolPolicyProvider`
   - monitor job / logininfor / online / operlog / cache 等显式高风险或特殊动作。

6. `GeneratorToolPolicyProvider`
   - code generator preview / sync / generate / edit 等特殊动作。

不再继续按每个页面建 Provider。

### 5.3 `AiFrontendToolPolicy` 保留为 Facade

Facade 继续负责：

- 接收浏览器 offered tools。
- 通过 Registry resolve server policy。
- 调用 `PermissionService` 复核当前用户权限。
- 输出 `ApprovedTool`。
- `requirePolicy`。

浏览器的：

- description
- inputSchema
- risk
- permission

都不能覆盖服务端 Policy。

### 5.4 B5 测试重点

必须有确定性测试证明：

- Generic CRUD 合法命名能得到预期 permission / risk。
- 非法命名不被 generic 放行。
- Explicit policy 与 Generic 同名时，Explicit 优先。
- 用户 reset-password 始终是 `DANGEROUS_WRITE`。

### 7.2 Layer 2：真实 Backend + MySQL / Redis 的不变量验收

新增：

- `scripts/ci/ai-phase35-p0-invariants.sh`

通过真实 HTTP + MySQL 验证：

1. **Run Lifecycle legal / illegal transition**  
   单测锁状态图，数据库路径锁 CAS 结果。

2. **WAITING_TOOL + Stop**  
   先得到真实 Tool Call，让 Run 进入 WAITING_TOOL；cancel 后再提交 Tool Result 必须被拒绝，且不能新增第二个 Tool Result / 后续 Tool。

3. **WAITING_TOOL + Steering / Supersede**  
   旧 Run 等 Tool 时发新用户指令，新 Run 建立；旧 Tool Result 返回必须被拒绝。

4. **重复 Tool Result**  
   同一 callId 第一次成功后，第二次提交必须失败；DB 中只存在一个 TOOL message / 一个 RESOLVED pending，不得再次产生副作用。

5. **Tool Result late after stopped / superseded**  
   分别覆盖 CANCELLED / SUPERSEDED。

6. **stale pageInstanceId / pageVersion / pageId**  
   任一身份字段变化都必须拒绝。

7. **protocol 缺失 / 非 v1 / 字段不完整**  
   有 Page Tool 的请求必须拒绝；普通聊天仍正常。

8. **Generic CRUD permission / risk**  
   由单元测试锁算法，HTTP 再抽一个代表工具证明 server approval。

9. **Explicit priority**  
   reset-password / user edit-set-fields 证明 explicit 覆盖 generic。

10. **WRITE / DANGEROUS_WRITE permission**  
    服务端仍返回 authoritative risk；无权限调用被过滤或拒绝。

11. **Compaction Stop / Steering**  
    结合现有 E2E 与新增 Steering-during-compaction 场景，保证旧 Run 不落 orphan checkpoint、不恢复 RUNNING。

12. **clientRunKey retry / 幂等关键行为**  
    本轮锁定的是现有 cancel-by-clientRunKey 重试语义：重复 cancel 返回稳定终态，不产生额外 Run / Tool 副作用；不在 B9 偷渡“HTTP turn response replay”或 B8 RunExecutionManager。

扩展现有 `tests/ai-agent-e2e.mjs`，不新建第二套大 E2E。

必须保留并强化：

- model / reasoning。
- Compaction / Checkpoint。
- Stop / Double ESC。
- Steering。

- audit / permissions。

新增 P0 核心断言：

- `/system/user` request 顶层真实携带 `capabilityProtocol / pageId / route / pageInstanceId / pageVersion`。
- Tool Call 对应 pending row 保存相同 protocol / pageId / runtime identity。
- 用户管理新 Contract / Adapter 仍暴露完整能力集合。
- query → edit_open → edit_set_fields → WRITE confirm → edit_submit → Tool Result → assistant continuation 真实闭环。
- add / edit / query / special action 的现有可逆生命周期继续通过。
- 导航或刷新后 old pageId/instance/version Tool 无法继续。
- WRITE 确认前 Steering：副作用不发生。
- 新增 **WRITE 已确认并真实完成后再 Steering** 的确定性场景：已完成副作用只发生一次，旧 Run 不得再次继续 Tool/WRITE。
