## 2. 从最初诉求回扣到落地结果

### 2.1 稳定性

原问题：

- 编排层直接依赖 Spring AI 技术类型。
- Run 状态转换入口分散。
- Stop / Steering / Tool Result / Compaction 存在被分散状态 SQL 破坏一致性的风险。

落地结果：

- 模型交互被收口到 RuoYi 自己的 `AgentRuntime` 边界。
- `AiAgentLoopService`、`AiContextService`、`AiRunService` 不再依赖 Spring AI chat/message/prompt/model/tool 类型。
- Run 的合法状态转换集中到 `RunLifecycleService`。
- 数据库状态更新统一使用期望前态 + CAS 条件。
- Tool Result 的 `WAITING_TOOL -> RUNNING` 与 Pending Tool resolve 保持同一事务；如果 Pending resolve 失败，显式回滚生命周期转换。
- 已进入 `CANCEL_REQUESTED` 的 Run 不再允许被异常覆盖成 `FAILED`，保持 Stop 优先语义。

### 2.2 可追溯性

原问题：

- `ai_run` 虽记录 `system_prompt_version` / `compaction_prompt_version`，但数据库没有对应历史正文。
- Prompt 仅切 enabled 也递增版本，版本号并不严格表示“正文版本”。

落地结果：

- 新增 `ai_prompt_version`，以 `prompt_type + version_no` 唯一定位完整正文。
- 正文真正变化时才生成新版本；仅启停不生成虚假内容版本。
- restore-default 只有在正文实际恢复时生成新版本。
- 当前 Prompt 更新与历史版本写入处于同一事务并使用行锁。
- Run 继续只记录版本引用，不重复保存完整正文。
- 会话审计详情新增 Runs 实际引用的 `promptVersions`，可从 Run 追到当时正文。
- Prompt 被停用时实际使用默认正文，因此 Run 记录默认正文实际对应的历史版本，而不是错误沿用被停用的自定义版本号。

### 2.3 后续扩展能力

原问题：

- 如果未来增加其他 Runtime 或替换 Spring AI，当前 Agent Loop 会被具体 SDK 类型直接牵制。

落地结果：

- 新增最小 `AgentRuntime` SPI：
  - `AgentRuntimeRequest`
  - `AgentRuntimeResult`
  - `AgentRuntimeMessage`
  - `AgentRuntimeTool`
  - `AgentRuntimeUsage`
  - `SpringAiAgentRuntime`
- Runtime 只负责“如何与模型交互”。
- Conversation、Run、Stop、Steering、Tool Policy、权限、Checkpoint、页面能力治理仍留在 RuoYi 业务层。
- 本轮没有建设动态多 Runtime 平台，也没有引入 Codex Harness / Pi Agent / 独立 Harness。

因此 B1 提供的是可替换边界，不是第二套框架。

## 3. B1 实施明细：代理运行时接口

### 3.1 新增 Runtime 协议

目录：

`ruoyi-ai/src/main/java/com/ruoyi/ai/runtime/`

主要文件：

- `AgentRuntime.java`
- `AgentRuntimeRequest.java`
- `AgentRuntimeResult.java`
- `AgentRuntimeMessage.java`
- `AgentRuntimeTool.java`
- `AgentRuntimeUsage.java`
- `SpringAiAgentRuntime.java`

标准请求表达：

- modelId
- reasoning effort
- prompt cache key
- 标准消息
- 标准工具定义

标准结果表达：

- 实际 modelId / modelCode
- 文本
- Tool Call
- input/cache-read/cache-write/total token usage
- 预留 finish reason

### 3.2 Spring AI 适配职责

`SpringAiAgentRuntime` 负责：

- 标准消息 -> Spring AI Message。
- 标准工具 -> ToolCallback。
- 继续使用现有 `AiAgentModelFactory` 创建模型与 options。
- 单次模型调用。
- `prompt_cache_key` 不支持时安全回退为无 cache key 重试。
- Spring AI `ChatResponse` -> RuoYi Runtime Result。

### 3.3 编排层收口

- `AiAgentLoopService` 只构造 Runtime Request、消费 Runtime Result。
- `AiContextService` 的 Compaction 也通过 `AgentRuntime`。
- `AiRunService.call` 改成通用泛型 Callable，不再绑定 `ChatResponse`。
- usage 记录改为 `AgentRuntimeUsage`。

保留了原有：

- 消息顺序。
- Tool Call / Tool Result continuation。
- 一个响应最多一个页面 Tool Call。
- 页面 Tool Policy。
- WRITE 安全边界。
- reasoning effort。
- prompt cache key 组织方式。
- Compaction 业务语义。

## 4. B2 实施明细：Run Lifecycle

### 4.1 显式状态

新增 `AiRunStatus`：

- RUNNING
- WAITING_TOOL
- COMPACTING
- CANCEL_REQUESTED
- CANCELLED
- SUPERSEDED
- COMPLETED
- FAILED

### 4.2 集中生命周期服务

新增 `RunLifecycleService`，集中处理：

- `RUNNING -> WAITING_TOOL`
- `WAITING_TOOL -> RUNNING`
- `RUNNING -> COMPACTING`
- `COMPACTING -> RUNNING`
- `RUNNING -> COMPLETED`
- `RUNNING / WAITING_TOOL / COMPACTING -> FAILED`
- 可取消运行态 -> `CANCEL_REQUESTED -> CANCELLED`
- 活动 Run / `CANCEL_REQUESTED -> SUPERSEDED`

终态不可被后续状态覆盖。

### 4.3 Mapper CAS

`AiRunMapper` 不再向各业务 Service 暴露一组不同语义的状态更新方法，而是保留生命周期所需的：

- `transition(runId, fromStatus, toStatus, reason)`
- `supersedeFrom(oldRunId, fromStatus, newRunId)`

两者都把期望前态写进 SQL where 条件。

### 4.4 原子性与竞争保护

`AiMessageService` 保持原有事务边界：

- 完成：状态转换 + Assistant Message。
- Tool Call：RUNNING -> WAITING_TOOL + Tool Call Message + Pending Tool。
- Tool Result：WAITING_TOOL -> RUNNING + Pending resolve + Tool Result Message。

实施过程中发现并修复了一个原有竞争隐患：

旧顺序是先 Pending resolve，再尝试 Run 恢复；如果 Stop / Steering 恰好导致 Run 状态转换失败，Pending 可能已经被提交为 RESOLVED。

当前顺序改为：

1. 生命周期 CAS：WAITING_TOOL -> RUNNING。
2. Pending resolve。
3. 追加 Tool Result Message。
4. 如果第二步失败，显式将事务标记 rollback-only，从而回滚第一步。

### 4.5 取消优先级澄清

16 号计划最初使用了“活动状态 -> FAILED”的简写。

实施期对照总体设计后明确：

> 一旦进入 CANCEL_REQUESTED，异常不得把取消流程覆盖成 FAILED。

因此最终规则为：

- RUNNING / WAITING_TOOL / COMPACTING 可 -> FAILED。
- CANCEL_REQUESTED 只允许 -> CANCELLED / SUPERSEDED。

16 号实施计划已经同步修正该表述。

## 5. B3 实施明细：Prompt Version History

### 5.1 表结构

新增：

`ai_prompt_version`

核心字段：

- prompt_version_id
- prompt_type
- version_no
- content
- create_by
- create_time

唯一约束：

`(prompt_type, version_no)`

### 5.2 版本写入规则

`AiPromptService` 现在使用事务 + `select ... for update`：

- 正文变化：当前 Prompt version +1，并写入完整历史正文。
- enabled-only：不新增正文版本。
- restore-default 且正文变化：新增版本。
- restore-default 但正文已经是默认值：只恢复启用状态，不制造重复版本。

### 5.3 初始化 SQL

新增已有环境增量：

`sql/ai_hardening_b1_b3_20260919.sql`

同时更新完整初始化：

`sql/ai_20260918.sql`

原因：

- 增量 SQL 用于已有数据库。
- 完整 SQL 保证新 Runner / 新环境 / 现有真实 GPT workflow 直接初始化时也具备 B3 表。

没有引入 Flyway / Liquibase，也没有定义 B10 的长期迁移框架。

### 5.4 历史迁移真实性边界

迁移只写入能被当前数据库或仓库事实证明的正文：

1. 当前 `ai_prompt` 实际保存的版本与正文。
2. 仓库已知的原始默认基线：
   - SYSTEM version 1
   - COMPACTION version 2

B3 上线前，如果某个中间版本正文已经被后续更新物理覆盖，且数据库/仓库中没有任何副本，则无法真实重建。

本次没有伪造这些已丢失的旧正文。

因此：

- 从本次 hardening 迁移完成后开始，新增 Prompt 版本具备完整可还原历史。
- 迁移前已经丢失正文的个别旧版本仍只能保留 Run 上原有版本号，不能宣称可恢复其正文。

这是历史数据不可逆丢失的事实限制，不是新的架构阻塞。

## 8. 最终回扣

本次工作不是表面代码重构。

稳定性方面：

- 模型 SDK 技术细节与业务编排解耦。
- Run 状态转换从分散更新收敛为显式生命周期 + CAS。
- Tool Result 竞争事务得到修复。
- Stop / Steering / Compaction / Tool / WRITE 主链全栈回归通过。

可追溯性方面：

- Prompt version 从“只有编号”变成“编号可定位完整正文”。
- 新版本正文不可再被下一次编辑覆盖。
- Run 审计可以回查真实 Prompt Version。
- 真 MySQL 验证了版本创建、enabled-only、restore-default、旧 Run/新 Run 引用。

后续扩展能力方面：

- RuoYi 业务编排只依赖自己的 Agent Runtime 协议。
- Spring AI 成为当前 adapter，而不是 Agent Loop 的业务模型。
- 后续如果评估其他 Runtime，可以在现有边界上讨论，而不需要现在就建设多 Runtime 平台。

结论：

> B1、B2、B3 已达到 15 号方案和 16 号实施计划的本轮完成标准；没有越过未决架构边界，并且通过 Backend、Fullstack 与 Real GPT 三层真实运行证明，这次加固确实提升了底座稳定性、可追溯性和后续扩展边界。上述成果已成为 `chatgpt/ai-agent-assistant` 的当前主线基线。
