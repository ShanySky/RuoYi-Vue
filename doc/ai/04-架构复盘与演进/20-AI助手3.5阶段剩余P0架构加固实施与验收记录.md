## 1. 结论

Phase 3.5 剩余 P0 的 B4、B5、B6、C1、B9、B10 已按 14 / 18 / 19 号文档的已确认边界完成落地，并通过真实 MySQL、Redis、Spring Boot、Vue/Vite、HTTP、Playwright Browser、Agent / Tool / WRITE / Stop / Steering / Compaction / Navigation 闭环验收。

本轮形成的核心地基是：

1. Capability Protocol v1 从“前端约定事实”提升为前后端可验证协议。
2. Page / Action Contract 与 Runtime Bindings 建立统一机制，并只迁移 `/system/user` 作为 P0 代表页。
3. Tool Policy 收敛为服务端权威的 Registry + Generic CRUD + 少量 Explicit Provider。
4. `AiAgentLoopService` 保留 Turn Orchestrator，仅抽出 Context Assembler 与 Tool Coordinator。
5. Run / Tool Result / stale runtime / WRITE / Steering / Compaction 等关键不变量具备更确定的测试保护。
6. AI SQL 建立 canonical fresh-install + ordered migration 双路径，并真实验证 fresh / upgrade 关键结构一致。

没有实施 B4/C3 全量页面迁移、C2 全面前端拆分、B7、B8、Streaming、Server Tools、MCP/Skill 产品能力、多 Agent、RAG、多实例执行、Harness、Tool Policy DSL、数据库动态规则、Flyway/Liquibase 或其他第四阶段能力。

## 2. B6：Capability Protocol v1 正式化

### 2.1 顶层协议

对于存在 active semantic page 的 Turn，请求顶层统一并校验：

- `capabilityProtocol = ruoyi-semantic-page-v1`
- `pageId`
- `route`
- `pageInstanceId`
- `pageVersion`
- `pageContext`
- `frontendTools`

普通聊天和仅 `app_navigate` 的请求仍允许没有 semantic-page identity，没有把普通聊天强制升级成页面协议请求。

### 2.2 服务端可信快照

`AiPendingToolCall` 与数据库 `ai_pending_tool_call` 新增并持久化：

- `capability_protocol`
- `page_id`

连同原有：

- route
- page_instance_id
- page_version

共同形成 Tool Call 发出时的原页面实例快照。

`AiCapabilityProtocolValidator` 负责：

- semantic-page request 识别。
- v1 版本校验。
- pageId / route / instance / version 完整性。
- 与数据库可无损持久化边界一致的长度约束。
- Tool Result continuation 与 Pending Tool 原快照一致性。

stale pageId、pageVersion、pageInstanceId 均会被拒绝。

### 2.3 页面 Action 导航语义

审核期间发现一个重要边缘：页面 Action 自身可能通过真实 Vue Router handler 导航，例如用户页的角色分配 Action。

最终规则：

- `app_navigate` 是显式 Navigation Tool。
- 普通 Page Tool 执行期间如果页面被外部切换，仍视为 stale runtime。
- 只有页面 handler 明确返回 `navigated: true`，才允许 Tool Result 使用执行前 source identity 证明“哪个页面实例执行了该 Action”。
- 如果浏览器已经在目标 URL，`app_navigate` 不重复 push，而是等待目标 Page Capability 完成注册后返回当前 runtime。

因此没有把“任意页面变化”误判为合法 Action 导航，也没有让目标页能力冒充源页能力继续同一 continuation。

## 4. B5：Tool Policy 轻量拆分

最终职责链：

```text
AiFrontendToolPolicy
       ↓
ToolPolicyRegistry
       ├─ SystemToolPolicyProvider
       ├─ MonitorToolPolicyProvider
       ├─ GeneratorToolPolicyProvider
       └─ GenericCrudToolPolicyProvider
```

`AiFrontendToolPolicy` 保留为 Facade，负责：

- 接收浏览器 offered tools。
- Registry resolve。
- `PermissionService` 权限复核。
- 输出 ApprovedTool。
- Tool Result 时重新确认当前权限。

安全规则保持：

- 客户端 description 不可信。
- 客户端 inputSchema 不可信。
- Risk 由服务端决定。
- Permission 由服务端决定。
- Explicit policy 优先于 Generic CRUD。

对照重构前主线的 47 个 explicit policy，拆分后一个未丢；另为用户代表页补充了精确策略。

用户页关键精确策略包括：

- edit-set-fields 禁止 userName / password。
- add-set-fields 使用 closed schema，只允许受控新增字段。
- reset-password 固定为 `DANGEROUS_WRITE`。
- delete 固定为 `DANGEROUS_WRITE`。
- change-status / add-submit / edit-submit 等保持服务端权威 Risk / Permission。

没有引入数据库动态规则、DSL 或插件型 Policy 平台。

## 7. B10：fresh-install 与 ordered migration

新增 canonical fresh-install：

- `sql/ai_fresh_install.sql`

新增 ordered migration：

- `sql/ai_migrations/20260920_01_phase35_p0_protocol.sql`
- `sql/ai_migrations/README.md`

规则：

- fresh 环境只使用当前 canonical AI schema，不回放所有阶段脚本。
- upgrade migration 使用稳定可排序命名。
- migration 明确 predecessor、用途、rerun、legacy data、rollback 条件。
- 已发布 migration 不改写历史语义。
- 不引入 Flyway / Liquibase / 自动 migration runner。

本次 migration：

- 增加 `capability_protocol`。
- 增加 `page_id`。
- 通过 `information_schema` guard 支持安全重复执行。
- 升级瞬间仍处于 PENDING 且没有完整 v1 identity 的 legacy Tool Call 标记为 EXPIRED。
- 已 RESOLVED / CANCELLED / SUPERSEDED 历史不伪造协议事实。

`scripts/ci/ai-schema-acceptance.sh` 使用两个独立数据库真实验证：

1. fresh：RuoYi base + Quartz + `ai_fresh_install.sql`。
2. upgrade：P0 前已发布 AI baseline + ordered migration，并重复执行 migration 一次。

最终比较：

- AI 表。

- `ai_prompt_version`。

- legacy PENDING -> EXPIRED。

## 8. 代码审核与修复闭环

代码审核不是形式步骤。实际审核中发现并修复了以下问题：

1. Policy Provider 拆分初版遗漏 `java.util.List` import。
2. Protocol Validator 测试存在 Java lambda 非 effectively-final 编译错误。
3. 用户页迁移初版 runtime bindings 引用了尚未真正共享的 side-effect core。
4. Contract action function 未被 normalization 正确转成 `handler`。
5. legacy page context 的 `pageId: null` 会覆盖 Tool Registry 的真实 runtime pageId。
6. 前后端对 pageId / route / pageInstanceId 可持久化长度约束不完全一致。
7. 导航型 Page Action Tool Result 需要保留 source runtime identity。
8. 普通 Tool 执行期间的外部导航不能被误判为合法 Action navigation。
9. 同目标 URL 的 `app_navigate` 存在目标 Capability 尚未 mounted 的注册时序竞态。
10. 用户 add-set-fields 不能继续落到 generic flexible schema，改为 explicit closed schema。
11. 用户 reset handler 未返回异步 query Promise，Agent 调用可能早于页面刷新结束。
12. 代表页 reset / auth-role 原来只有“注册存在”证据，补成真实执行证据。
13. stale pageId / pageVersion、SUPERSEDED late result 的确定性证据不足，补强真实 HTTP + MySQL 断言。
14. Fullstack workflow 必须记录并使用真实 paired branch / SHA，而不能凭绿色 badge 推断跨仓库配对。

上述问题均进入“修复 -> 针对性测试 -> 再审核”闭环，最终工作分支验收全部通过。

## 13. 阶段结论

从原始诉求回扣，本轮不是为了重构形式而增加层次。

稳定性方面：

- 页面协议身份不再靠松散约定。
- Tool Result 必须对应可信 Pending 快照。
- 页面变化、导航、刷新和 Steering 的 stale 边界更清晰。
- Tool Policy 仍由服务端权威治理。
- Run / WRITE / Compaction 竞争条件拥有更确定证据。

清晰度方面：

- Page Contract 与 Runtime Binding 分工明确。
- Policy Registry / Provider 边界明确。
- Agent Turn Orchestrator / Context Assembly / Tool Coordination 边界明确。
- fresh install 与 upgrade migration 路径明确。

可测试性方面：

- 协议、状态、Policy、Tool Result 有快速 deterministic tests。
- 真实 HTTP + MySQL 锁定服务端不变量。
- Browser E2E 保持用户可见、Agent/Tool/WRITE/Navigation 全链路证据。

因此，在进入历史整理和 AI 主线合入之前，Phase 3.5 剩余 P0 的运行时实现已经达到 18 / 19 号文档要求的工作分支完成标准，并为后续业务助手与虚拟员工阶段提供了更稳定、可治理、可测试的基础。
