## 1. 本轮用户诉求

Phase 3.5 P0 已完成后，不希望剩余 P1 继续以零散、小任务、人工频繁确认的方式拖延，而是希望建立一条可以由 AI 连续自主推进的收口流水线。

这条流水线必须同时满足两点：

1. **能够自主连续推进。**
   - 已确认的方向不反复重新讨论。
   - 方案明确后，由后续 AI 基于当前真实代码形成计划，计划完成后继续实施、审核、验证和收口。
   - 普通实现问题、测试失败和可自动修复的问题由 AI 自主解决，不把可自动完成的工作优先交回用户。

2. **不能因为“自主推进”而跳过工程链路。**
   - 用户诉求约束方案。
   - 方案约束计划。
   - 计划指导实施。
   - 验收必须重新回到原始诉求，不以“代码写完”“CI 变绿”或“计划步骤打勾”代替最终完成判断。
   - 如果真实代码暴露出必须改变本文架构边界的新矛盾，停止对应部分并重新回到方案层，而不是在实施阶段自行扩大设计。

因此，本轮目标不是“尽快把几个 P1 TODO 改掉”，而是**把 Phase 3.5 已确认的 P1 收尾事项一次性、可追溯、可验证地收口，并为进入后续大阶段留下单一、干净、稳定的实现形态。**

- B4 基座 + 用户管理代表页完成。
- B5 Tool Policy 轻量拆分完成。
- B6 Capability Protocol v1 完成。
- C1 Agent Loop 有限职责收敛完成。
- B9 核心不变量测试完成。

- 前后端成果已经进入 `chatgpt/ai-agent-assistant`。

因此 P1 不得重新开发 P0，也不得为了“顺手整理”推翻已经验收的 Protocol、Policy、Agent Loop、SQL Migration 或 Run Lifecycle 设计。

P0 在本轮中的角色只有两个：

1. 作为 P1 的稳定技术基线。

### 3.2 新机制已经存在，P1 的任务是完成迁移而不是重建

P0 已经建立：

- `src/ai/capabilityProtocol.js`
- `src/ai/pageCapabilityContract.js`
- `src/ai/crudPageCapabilities.js` 的 `contract + bindings` 模式
- `src/ai/toolRegistry.js`

`systemUserPageContract` 已证明当前目标边界：

- Contract 保存稳定语义：pageId、pageName、route、toolPrefix、query/form 字段、permission、Action。
- Runtime Bindings 保存真实运行时事实：refs、rules、options、handlers、rows、selection、pagination 等。
- 页面真实业务 handler / API 继续是唯一业务执行路径。
- 后端继续掌握 Tool Policy、Permission 和 Risk 的权威判断。

P1 不创建第二套 Page Capability 框架。

### 3.3 legacy 兼容入口仍存在

当前 `createAiCrudPageCapabilities(configuration)` 会在存在 `configuration.contract` 时走新 `contract + bindings` normalization；没有 contract 时仍接受旧 flat-options。

这条兼容路径是 P0 为避免提前批量迁移而有意保留的过渡机制。

P1 完成后必须：

- 所有现有 Page Capability 页面不再依赖 flat-options。
- 删除“无 contract 仍可作为长期页面声明”的兼容入口。
- 保留通用 CRUD capability 能力本身，但其长期调用形态必须收敛为新契约。
- 测试应能防止未来重新引入 legacy 调用。

### 3.4 catalog 仍存在双形态

当前 `pageCapabilityCatalog.js` 同时包含：

- `systemUserPageContract` 派生项。
- 23 个静态 `legacyPageCapabilities`。

P1 完成后，catalog 必须由正式 Page Contract 派生，不再维护第二份 route / pageName 静态事实。

catalog 仍只承担治理页需要的发现/展示语义，不升级成 Tool schema、risk、permission 或业务执行 Registry。

## 4. P1 总体目标

本轮 P1 收口完成后，应达到下面四个结果。

### 4.1 B4 / C3：Page Capability 单一长期形态

全部 23 个 legacy 页面迁移到统一 Page / Action Contract + Runtime Bindings。

最终状态：

- `/system/user` 不再是唯一新形态样板，而是所有现有 Page Capability 页面的共同模式。
- `pageCapabilityCatalog` 不再存在 legacy 静态清单。
- flat-options 只为 P0 过渡存在的兼容入口被移除。
- 业务页面不再堆大型 AI-only schema / action declaration。
- 页面真实 rules、options、handlers、API、permission 继续复用。
- Tool 名称、服务端 Risk / Permission、安全确认和业务副作用语义默认保持兼容。

### 4.2 C2：按真实热点有限拆分前端职责

本轮不是把 D1 长期架构图机械落成完整目录树。

拆分只围绕 P1 已经真实触及、且边界稳定的热点：

- A1 使键盘交互从 `AiAssistant` 主体中抽出。
- A4 使 History / Restore 相关职责具备更清晰边界。
- A2 使 QuickSettings 与模型 Runtime Settings 的产品职责更清楚。
- Page Capability 批量迁移过程中如果反复出现同一 wiring / adapter 模式，应收敛到现有 `src/ai` 统一层，而不是复制进更多页面。

允许的目标形式包括 Component / Composable / 小型 helper；最终文件名由 22 号计划依据当前代码决定。

完成判断不看“拆了几个文件”，而看：

- 高频变化职责是否有稳定 owner。
- 主组件是否不再继续吸收这些职责。
- 状态 ownership 是否清楚。
- 没有为了拆分重复 store 状态、Run 状态或 Tool 状态。
- 已验证用户体验不因结构调整发生意外变化。

### 4.3 A1 / A2 / A4：低优先级项一次收尾

**A1：统一 AI 快捷键入口**

至少收敛当前 AI 专属键盘行为：

- 双 ESC Stop。
- Composer 发送快捷键及其生效上下文。

目标是一个足够薄的统一入口，例如 composable 或等价模块。

不做：

- 全局 Keyboard Framework。
- 快捷键 DSL。
- 任意用户自定义组合键平台。
- 复杂优先级/冲突解析系统。

双 ESC 原有 overlay/focus guard 和 Stop 安全语义必须保持。

**A2：Runtime Settings UI 轻量产品化**

保留底层模型级 Runtime 设置和现有 API / 数据模型。

产品层完成：

- 使用“Agent 工作上下文预算”术语。
- 推荐模式成为默认认知。
- 自定义模式再显示 Context Budget、Auto Compaction、Threshold。
- 支持恢复当前系统推荐组合。
- reasoning 继续保留为明确模型设置。
- 推荐值如果需要在前端表达，应集中定义，避免散落多个组件；必须与后端当前默认语义保持一致。
- 除非当前 API 无法完成已确认体验，否则不新增数据库结构或复杂后台配置。

**A4：会话继续文案收口**

面向用户统一：

- “恢复上次会话” → “继续上次会话”。
- 自动恢复相关提示改成对应“自动继续”表达。
- 成功/失败/按钮/设置说明保持同一用户心智。

内部历史兼容字段和函数名没有必要为了文案做破坏性重命名。

## 5. Page Capability 迁移策略

### 5.1 以现有样板为基线，不逐页发明模式

`systemUserPageCapability.js` 是当前经过真实 Agent / Tool Loop 验证的代表实现。

其他页面迁移时优先复用：

- `definePageCapabilityContract`
- `createAiCrudPageCapabilities({ contract, bindings })`
- 现有 Tool Registry
- 现有 Capability Protocol v1
- 现有后端 Tool Policy Registry / Provider

如果现有页面不是标准 CRUD 形态，例如监控、缓存、Swagger、表单构建或代码生成等特殊页面，不应为了迁移硬塞进 CRUD 假模型。

允许对**现有统一 Contract / Adapter 层做最小必要扩展**，用于表达已经存在的特殊 Action 或只读能力，但必须满足：

- 仍然只有一套 Contract / Registry 机制。
- 不建立平行 `legacyAdapterV2`、第二套 Tool Registry 或页面专属运行时。
- 不改变 Capability Protocol v1 的长期语义，除非发现当前协议确实无法表达既有页面；这种情况属于方案边界冲突，应先停止对应部分并提出问题。
- 不把业务页面改成 metadata-driven UI。

### 5.2 动态路由必须显式处理

现有 catalog 中包含多个 `/*` 路由。

22 号计划在正式批量迁移前必须重新核对这些页面当前：

- 实际 route。
- pageId。
- pageInstanceId / pageVersion。
- Tool Registry 注册与失效语义。
- catalog route pattern。
- 页面参数与 Context。

如果现有 Contract 的静态 route 字段不足以清晰表达“稳定页面类型 + 运行时具体实例路径”，只允许在现有 Page Contract / Runtime identity 边界内做最小扩展，不允许通过模糊匹配、DOM 猜测或放松 stale runtime 校验绕过去。

### 5.3 Tool 名称与服务端安全语义默认保持兼容

P1 是前端接入形态迁移，不是 Tool API 大改版。

默认要求：

- 已有 Tool name 不变。
- permission 不放宽。
- Risk 不由客户端重新决定。
- DANGEROUS_WRITE 继续由服务端权威策略决定。
- WRITE Confirm 语义不退化。
- 页面 handler 继续调用真实 RuoYi API / Service。
- 不引入第二套业务写路径。

如果某页现有 Tool 定义本身存在明显安全缺陷，可以修复，但必须在计划和验收记录中单独标记为“迁移时发现并修复的缺陷”，不能静默改变行为。

### 5.4 迁移完成后必须删除过渡层

B4 / C3 的完成标准不是“23 个页面都能在新模式下运行，但旧模式还留着以防万一”。

最终必须删除：

- `legacyPageCapabilities` 静态 catalog 双形态。
- `createAiCrudPageCapabilities` 的长期 flat-options 调用兼容入口。
- 已迁移页面中只为 legacy declaration 服务的 AI-only 重复字段/schema/action 定义。

同时增加自动化保护，防止后续新页面再次绕过 Contract。

## 6. 自主推进流水线

整条流水线只允许按下列顺序前进。

```text
用户诉求
  ↓
21 号落地方案
  ↓
22 号实施计划
  ↓
按 Wave 实施 + 每波局部验证
  ↓
代码/架构复核 + 缺陷修复
  ↓
最终真实验收
  ↓
主线合入 + 历史整理 + 分支清理
  ↓
23 号实施与验收记录
  ↓
重新回到用户原始诉求宣布 Phase 3.5 P1 收口
```

### 6.1 方案 Gate

本文是 P1 的上层范围约束。

后续 AI 不需要重新讨论已经确认的：

- P0 设计。
- B4/C3 全量迁移必要性。
- C2 “有限、按热点拆分”原则。
- A1/A2/A4 方向。
- P2 暂不进入本轮。

只有真实代码出现本文没有覆盖、且会改变长期架构边界的矛盾，才重新打开方案层。

### 6.2 计划 Gate

开始实施前必须先创建 22 号实施计划。

22 号计划至少要把本文转换成可执行事实：

- 记录当时前后端 AI 主线与工作分支 SHA。
- 再次枚举实际仍存在的 legacy 页面，不能只照抄本文 23 条。
- 定位每个页面真实文件、当前 capability 声明、真实 handlers / rules / options / permissions。
- 明确页面迁移分组和顺序。
- 明确动态路由处理方式。
- 明确哪些页面用通用 CRUD Contract，哪些需要现有统一机制的最小特殊扩展。
- 明确 C2 实际拆哪些稳定职责，以及为什么这些是“真实热点”。
- 明确 A1/A2/A4 具体文件与 UI 行为。
- 明确每个 Wave 的验证证据。
- 明确最终删除 legacy compatibility 的时点。
- 明确前后端真实配对验证和主线合入顺序。
- 明确非目标和回滚/停止条件。

计划形成后先做一次**方案一致性自检**。只要没有改变本文边界，不需要为了普通实现细节再等待人工确认，可以直接进入实施。

### 6.3 实施 Wave

建议 22 号计划以依赖关系组织为几个连续 Wave；具体页数可以根据真实代码调整，但原则上：

**Wave 1：System / User 页面迁移**

先迁移与 `/system/user` 样板最接近的一组页面，验证 Contract / bindings 在更多 CRUD、动态路由和权限组合下仍成立。

**Wave 2：Monitor / Tool 页面迁移**

处理只读监控、缓存、日志、任务、生成器、构建器等更异构页面；只在真实需要时最小扩展统一 Adapter。

**Wave 3：C2 + A1 / A2 / A4 收尾**

利用前两波已经暴露的真实前端热点做有限职责拆分，并完成快捷键、Runtime Settings UI、会话文案收口。

**Wave 4：删除 legacy 与全局收口**

在全部页面已迁移、测试覆盖稳定后：

- 删除 flat-options 兼容。
- 删除 legacy catalog。
- 清除重复声明。
- 加入 no-legacy invariant。
- 做全局回归。

每个 Wave 结束都做与改动匹配的局部验证并修复问题，但**局部验收不是整轮完成声明**。流水线继续自动进入下一 Wave。

### 6.4 审核 Gate

全部实现后，在最终验收前进行一次针对本轮目标的代码/架构复核。

重点检查：

- 是否还有 legacy Page Capability。
- 是否出现新的双事实来源。
- 是否为了特殊页面造了第二套 Adapter。
- Tool name / permission / risk 是否意外漂移。
- 动态路由 stale identity 是否仍安全。
- C2 是否真正减少热点耦合，还是只是移动代码。
- 是否重复了 store / run / tool 状态。
- A2 是否偷偷引入后端配置平台或数据库变化。
- 是否触及 P2。
- 是否存在只靠 Mock/静态检查没有真实执行证明的关键行为。

发现问题后进入“修复 → 针对性验证 → 再复核”闭环，不把审核发现留到主线。

### 6.5 最终验收 Gate

最终验收必须同时对照：

1. 用户原始诉求。
2. 14 号架构决策。
3. 本 21 号落地方案。
4. 22 号实施计划。
5. 最终真实代码与运行结果。

不能只回答“计划有没有执行完”。

## 7. 验证策略

### 7.1 快速确定性验证

应扩展现有 `tests/ai-capability-contract.test.mjs` 或等价轻量测试，至少锁定：

- 全部当前 Page Capability 均有正式 Contract。
- pageId / route / toolPrefix / Action suffix 唯一且合法。
- catalog 全部由 Contract 派生。
- 不再存在 legacy catalog 条目。
- 不再存在允许长期 flat-options 页面接入的兼容调用。
- 动态路由页面的稳定 contract 与 runtime identity 规则可验证。
- A1 快捷键 guard 不退化。
- A2 推荐/自定义切换的关键状态语义可测试。

### 7.2 页面级验证

不能要求 23 个页面每一个都复制一套巨大 Browser E2E，但也不能只验证“Contract 文件存在”。

应按能力类型建立代表矩阵：

- 标准 CRUD。
- 动态详情/分配路由。
- 只读列表/日志。
- 状态或危险写操作。
- 监控/缓存类特殊页面。
- 生成器/构建器等特殊 Tool 页面。

每个类型至少有真实页面注册 / Tool invoke / Context / handler 证据；关键 WRITE 继续验证确认与权限。

### 7.3 最终全栈闭环

按照当前 `.agents/skills/fullstack-validation/SKILL.md` 和目标分支最新 workflow 做真实验收。

涉及前端 Page Capability / Agent / Tool Loop 的最终证据优先包括：

```text
MySQL
→ Redis
→ 当前 AI schema
→ Backend build/start
→ Frontend install/build/start
→ /dev-api
→ Browser
→ Agent / Tool Loop
→ Page Capability
→ Tool Result continuation
→ WRITE Confirm / Permission
→ Navigation / stale runtime
→ persistence / audit assertions
```

必须记录实际使用的 Backend / Frontend branch 与 SHA。

如果 Backend 本轮没有运行时代码变化，也不能因为“Backend CI 绿色”就默认 Frontend 工作分支被验证；最终 paired acceptance 必须显式 checkout P1 的真实 Frontend SHA。

### 7.4 UI 收尾验证

A1/A2/A4 改变用户交互或文案，因此最终 Browser 验收至少确认：

- 双 ESC Stop 仍按原 guard 工作。
- Composer 发送快捷键仍正确。
- Runtime Settings 推荐/自定义/恢复推荐可实际操作。
- “继续上次会话”相关文案一致。
- 自动继续与 Undo Restore 行为未改变。
- QuickSettings / AiAssistant 的视觉和交互没有明显回归。

如自动 Browser E2E 已能充分证明，不强制创建公网预览；只有人工视觉验收确有额外价值时再建立临时预览。

## 11. 自主推进的停止条件

默认持续自主推进，不因为普通实现选择、测试失败或可修复缺陷中断找用户确认。

只有以下情况需要暂停对应部分：

1. 当前真实代码与本文上层架构结论直接冲突，继续做必须推翻 14 / 21 已确认边界。
2. 某个既有 Page Capability 无法在当前 v1 Contract / Runtime identity 下安全表达，且修复需要改变 Capability Protocol 的长期语义。
3. 需要新增明显属于 P2 / 第四阶段的能力才能完成 P1。
4. 必须进行不可逆数据破坏、扩大权限、弱化 Tool Policy / WRITE 安全边界。
5. 外部环境或权限阻塞导致关键路径无法获得真实验收证据。

除此之外，后续 AI 应自行完成代码定位、计划细化、实施、失败诊断、修复、复核、验证、PR、合入和清理。
