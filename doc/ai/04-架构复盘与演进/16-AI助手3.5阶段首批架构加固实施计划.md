## 1. 目标与当前真实代码判断

本轮只完成：

1. B1：代理运行时接口（Agent Runtime SPI）。
2. B2：运行生命周期（Run Lifecycle）。
3. B3：提示词版本历史（Prompt Version History）。

当前实施分支在计划形成前与 `chatgpt/ai-agent-assistant` 指向同一提交，属于干净隔离起点。

当前真实代码的关键现状：

- `AiAgentLoopService` 直接依赖 Spring AI 的 `Message / Prompt / ChatResponse / ToolCallback / AssistantMessage` 等类型。
- `AiContextService` 的上下文压缩路径也直接构造 Spring AI Prompt 并直接调用模型。
- `AiRunService` 的模型执行与用量统计仍以 Spring AI `ChatResponse` 为接口类型。
- Run 状态转换分散在 `AiRunService`、`AiMessageService` 和 `AiRunMapper`；Tool Call、Tool Result、完成、压缩、停止、纠偏分别走不同入口。
- `AiPrompt` 只有当前正文和 `version_no`；更新时即使只切换 enabled 也会递增版本号，数据库没有历史正文，历史 Run 无法根据版本号还原当时实际 Prompt。

因此本轮应做“边界收敛”，不是重新设计 Agent Loop。

## 2. 上层诉求到本计划的映射

### 2.1 用户核心诉求

本轮最终必须证明：

- 底座稳定性提高：模型调用实现细节与编排解耦，Run 非法状态转换和竞争风险下降。
- 可追溯性提高：历史 Run 能定位并还原其使用的 System / Compaction Prompt 正文。
- 后续扩展能力提高：未来增加 Runtime Adapter 或更强 Agent 能力时，不需要直接侵入当前业务编排层。
- 当前已验证产品行为不退化：聊天、Stop、Steering、Tool Call、Compaction、Reasoning、Prompt Cache 等主链继续工作。

### 2.2 总体设计约束

本计划保持：

- 业务系统仍是权威层。
- 同一 Conversation 最多一个活动 Run。
- Stop、Steering、Tool Result、Compaction 和 WRITE 服从同一 Run 生命周期。
- Prompt 不是权限或运行状态安全边界。
- 沿现有架构演进，不重建第二套 AI 框架。
- 真实运行验证优先于静态检查。

### 2.3 15 号方案约束

- B1 只负责“怎么和模型交互”，不接管 Conversation / Run / Tool Policy / 权限 / 业务能力治理。
- B2 只收敛 Run 状态、转换、前置条件、幂等和竞争保护，不引入工作流引擎、消息队列或分布式执行体系。
- B3 只补真正的 Prompt Version History，不引入审批、发布、多环境、复杂回滚或数据库迁移框架。
- B4～B10、C1～F 及其他待定事项不进入本轮实现。

## 3. B1：代理运行时接口实施计划

### 3.1 新增运行时边界

新增 RuoYi AI 自己的运行时协议，建议位于 `com.ruoyi.ai.runtime`：

- `AgentRuntime`
- `AgentRuntimeRequest`
- `AgentRuntimeResult`
- `AgentRuntimeMessage`
- `AgentRuntimeTool`
- `AgentRuntimeUsage`
- `SpringAiAgentRuntime`

标准请求至少表达：

- modelId
- reasoning effort
- prompt cache key
- 标准化消息列表
- 标准化工具定义

标准结果至少表达：

- 实际模型 ID / model code
- 文本结果
- 标准化 Tool Call
- token usage / cache read / cache write
- 可获取时的 finish reason

### 3.2 Spring AI 适配职责

`SpringAiAgentRuntime` 负责：

- 将标准消息转换成 Spring AI Message。
- 将标准工具转换成 Spring AI ToolCallback。
- 通过现有 `AiAgentModelFactory` 创建 Spring AI 模型与 options。
- 执行一次模型调用。
- 保持现有 prompt_cache_key 不支持时的安全 fallback。
- 将 ChatResponse 转换为标准结果。

`AiAgentModelFactory` 继续作为 Spring AI 构建细节，不扩展成多 Runtime 管理平台。

### 3.3 编排层改造

最小修改：

- `AiAgentLoopService` 改为只构造标准 Runtime Request、消费标准 Runtime Result。
- `AiContextService` 的 Compaction 模型调用也经过 `AgentRuntime`。
- `AiRunService.call(...)` 改为通用泛型 Callable，不再绑定 `ChatResponse`。
- `AiRunService.recordUsage(...)` 消费 RuoYi AI 标准 usage，而不是 Spring AI Usage。

保留：

- 当前 Agent Loop 的消息顺序、Tool Loop、一次一个前端 Tool Call、页面 Tool Policy、WRITE 安全边界。
- 当前 Prompt Cache key 组织方式。
- 当前 Reasoning 配置来源和能力约束。

### 3.4 B1 验证

至少验证：

- 编排层不再 import Spring AI chat/message/prompt/model/tool 类型。
- 普通文本模型调用成功。
- Tool Call 请求与 Tool Result continuation 成功。
- Reasoning effort 原样工作。
- Prompt Cache key 仍发送；Provider 不支持时 fallback 仍成功。
- Compaction 使用同一 Runtime 边界且结果不退化。
- 用量记录仍写入 `ai_run`。

## 4. B2：运行生命周期实施计划

### 4.1 集中状态定义

新增明确的 `AiRunStatus` 枚举，覆盖现有：

- RUNNING
- WAITING_TOOL
- COMPACTING
- CANCEL_REQUESTED
- CANCELLED
- SUPERSEDED
- COMPLETED
- FAILED

新增 `RunLifecycleService`，集中定义：

- 活动状态。
- 终态。
- 合法 transition。
- transition 所需前置状态。
- CAS 式数据库状态更新。
- cancel / supersede 等附加原因和 supersededByRunId 的处理。

### 4.2 状态转换规则

本轮至少明确并覆盖：

- RUNNING -> WAITING_TOOL
- WAITING_TOOL -> RUNNING
- RUNNING -> COMPACTING
- COMPACTING -> RUNNING
- RUNNING -> COMPLETED
- 活动状态 -> FAILED
- 活动状态 -> CANCEL_REQUESTED -> CANCELLED
- 活动状态 / CANCEL_REQUESTED -> SUPERSEDED

非法或重复转换不得静默覆盖终态。

### 4.3 现有调用点收口

- `AiRunService` 负责 Run 创建、Future 管理和对生命周期服务的业务包装，但不再自己散布状态 SQL。
- `AiMessageService.completeWithAssistant`、`persistToolCall`、`resolveToolResult` 在现有事务内调用生命周期服务，保持“状态 + 消息 + Pending Tool”原子性。
- `AiContextService` 的 begin/end compaction 通过生命周期入口。
- Stop、cancel-all、Steering supersede、失败处理统一走生命周期入口。
- `AiRunMapper` 只保留查询、插入、usage 更新及生命周期服务需要的 CAS 状态 SQL，不由其他 Service 直接改变 Run 状态。

### 4.4 竞争与幂等保护

重点保证：

- Stop 后旧 Run 不再完成、不再产生新 Tool Call。
- Steering 后旧 Run 不能继续执行 Tool / WRITE。
- Tool Result 返回时，Run 必须仍处于 WAITING_TOOL；否则事务整体失败。
- 重复 Tool Result 不得再次推进 Run。
- 已进入终态的 Run 不被 fail/cancel/complete 覆盖。
- Compaction 被 Stop/Steering 打断后不能错误恢复为 RUNNING。

### 4.5 B2 测试

新增本轮所需的有限测试，不扩成 B9：

- 状态 transition matrix 单元测试。
- 非法 transition / 终态不可覆盖测试。
- 必要的生命周期 CAS 行为测试或现有真实 E2E 覆盖。

真实回归：

- Stop。
- Steering。
- Tool Call -> WAITING_TOOL -> Tool Result -> RUNNING。
- Compaction。
- Completion / Failure。
- 现有单 Conversation 单活动 Run 语义。

## 5. B3：提示词版本历史实施计划

### 5.1 数据结构

新增 `ai_prompt_version`，最小字段：

- prompt_version_id
- prompt_type
- version_no
- content
- create_by
- create_time

建立 `(prompt_type, version_no)` 唯一约束。

当前 `ai_run.system_prompt_version` 与 `compaction_prompt_version` 继续作为逻辑版本引用；通过 `prompt_type + version_no` 唯一定位历史版本，不在 Run 中重复保存完整正文。

### 5.2 初始化与兼容

新增本轮增量 SQL 文件，保持当前仓库 SQL 组织方式，不引入 Flyway / Liquibase：

- 创建版本表。
- 把当前 `ai_prompt` 的现有版本和正文补入版本表。
- SQL 设计为可在真实 MySQL 8 环境安全执行。

更新当前 AI CI / E2E 初始化链，使新环境真实执行该 SQL。

### 5.3 Prompt 更新语义

`AiPromptService` 使用事务和行锁处理正文更新：

- 只有正文实际变化时才生成新 version_no 和历史正文记录。
- 只切换 enabled 不生成新的内容版本。
- restore-default 只有在正文从当前值变为默认值时才生成新版本。
- 新版本记录与当前 Prompt 更新必须处于同一事务。
- 保留现有模板变量校验、权限和审计日志。

新增：

- `AiPromptVersion`
- `AiPromptVersionMapper`
- 按 type + version 查询历史正文能力。

### 5.4 历史 Run 可还原

在后端审计详情中增加本会话 Runs 实际引用到的 Prompt Version 信息，或提供等价的服务级查询，使审计可以从：

- run.systemPromptVersion
- run.compactionPromptVersion

准确取得对应历史正文。

不保存每次运行渲染后的动态 Prompt 全文。

### 5.5 B3 验证

真实 MySQL 验证：

1. 初始化后 SYSTEM / COMPACTION 当前版本均有历史正文。
2. 修改 SYSTEM 正文后生成下一版本，旧正文仍存在。
3. 仅 enabled 开关变化不新增内容版本。
4. restore-default 在正文发生变化时新增版本。
5. 历史 Run 仍能根据记录的版本号查到当时正文。
6. 新 Run 使用新版本，旧 Run 仍指向旧版本。

## 6. 实施顺序

1. 提交本实施计划。
2. B1：建立 Runtime SPI，并把主模型调用和 Compaction 接入。
3. B2：建立 Run Lifecycle，并收口所有状态转换入口。
4. B3：建立 Prompt Version History、增量 SQL 和审计可还原能力。
5. 增补本轮必要测试。
6. 更新 AI CI / E2E 初始化和断言。
7. 完整编译与测试。
8. 真实 MySQL / Redis / Spring Boot / mock OpenAI-compatible Provider 验收。
9. 条件允许时运行现有全栈 E2E。
10. 条件允许且仓库已配置真实 Provider 凭据时运行 real GPT acceptance。
11. 写实施与验收记录，逐项回扣用户核心诉求、总体设计、15 号方案和本计划。

- B7 TokenEstimator / Checkpoint 新架构。
- B8 Run Execution Manager。

- B10 数据库迁移长期规范。
- C1 `AiAgentLoopService` 大规模职责拆分。
- C2 前端 AI Assistant 大规模拆分。
- C3 页面 AI 适配重构。
- 多 Runtime 管理后台、动态 Runtime 切换平台。
- 独立 Harness、Codex Harness、Pi Agent 集成。
- 工作流引擎、消息队列、分布式 Run。
- Prompt 审批 / 发布 / 多环境 / 复杂回滚平台。
- Skill / MCP / Plugin / 虚拟员工 / 自进化功能实现。

如果实施发现必须先决定上述待定事项才能正确继续，对该部分停止实现并记录阻塞点。

## 9. 计划自检

对照上层设计，本计划没有改变产品语义：

- 没有把会话、运行、权限、Tool Policy 下沉到 Runtime。
- 没有把 B2 扩展成通用工作流系统。
- 没有把 B3 扩展成 Prompt 运营平台或数据库迁移框架。
- 没有拆分 C1/C2/C3。
- 所有变更都直接服务于稳定性、可追溯性和扩展边界。

因此可以进入实施阶段。
