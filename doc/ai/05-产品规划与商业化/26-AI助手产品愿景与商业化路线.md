> 文档类型：产品愿景与商业化母文档  
> 状态：长期有效 / 持续演进  
> 当前基线日期：2026-09-20  
> 适用仓库：`ShanySky/RuoYi-Vue` + `ShanySky/RuoYi-Vue3`  
> 产品开发主线：前后端 `chatgpt/ai-agent-assistant`

## 1. 核心结论

RuoYi AI 助手的目标不是“给 RuoYi 增加一个 AI 聊天窗口”，而是让业务软件的交互方式和生产力模型逐步发生变化：

> **帮助业务 → 承担业务 → 改进业务**

对应三层长期产品愿景：

1. **第一层：AI 业务助手**  
   AI 理解真实业务目标，并在权限和安全边界内帮助人完成业务。

2. **第二层：数字员工**  
   AI 在授权范围内自主承担完整业务任务和岗位职责。

3. **第三层：受治理的自主进化系统**  
   系统持续发现问题、提出改进、实施验证，并在治理、审计和审批机制下优化业务系统和 AI 自身。

商业化不等待第三层实现后再开始。整体收入结构应随着产品成熟度逐步演进：

> **项目收入 → 产品收入 → 经常性数字员工收入 → 平台与生态收入**

同时增加一条横向贯穿前中期的科研 / 科技计划路线：通过国家、省市科技计划、人工智能专项、揭榜挂帅等机制，为真正需要长期投入的前沿能力争取研发资金、示范场景和技术背书。该路线属于**研发融资与成果放大机制**，不能简单等同于销售收入或利润。

核心商业原则是：

> **不是先花几年造完整平台再寻找收入，而是在每一个阶段都形成当期可以收费的价值；对于必须长期投入、短期客户又难以单独买单的前沿能力，则积极利用科研与科技计划资金共同承担研发成本。**

## 2. 我们到底在解决什么问题

传统企业软件通常要求用户先理解系统，再按照系统预先设计的菜单、页面和操作路径完成工作。

用户真正想完成的却不是“点哪个按钮”，而是：

- 查询一批符合条件的数据。
- 核对资料并找出异常。
- 填写或更新一项业务。
- 完成跨页面、跨步骤的业务流程。
- 依据业务规则做出判断。
- 在需要时获得解释、建议或风险提示。

因此，本产品希望把交互方式逐渐从：

> **人学习系统、操作系统**

演进为：

> **人表达业务目标，AI 理解业务并帮助完成**

再进一步演进为：

> **AI 在授权范围内直接承担岗位职责**

最终形成：

> **系统在治理之下持续发现问题并改进业务与自身能力**

这不是单纯的大模型能力问题，而是业务理解、系统能力接入、权限治理、运行可靠性和产品工程共同组成的系统性能力。

## 3. 客户为什么愿意付钱

客户购买的不是“大模型本身”，而是能够落到真实业务结果上的生产力提升。

### 3.1 降低复杂业务系统的学习和使用成本

用户不需要记住大量菜单、查询条件和操作路径，只需要表达“我要完成什么”。

对于功能复杂、人员流动较大、培训成本较高的政企系统，这能够直接降低使用门槛。

### 3.2 减少重复操作和低价值人工工作

AI 可以帮助完成：

- 查询与筛选。
- 信息汇总与解释。
- 填表和表单辅助。
- 跨页面操作。
- 资料核对。
- 规则检查。
- 批量、重复、标准化业务步骤。

价值不只体现为“少点几次鼠标”，而是减少业务人员花在机械操作上的时间。

### 3.3 降低项目实施、培训和长期支持成本

当 AI 能够解释系统、理解当前页面并协助完成业务后，传统项目中大量“教用户怎么用”“告诉用户在哪里操作”的支持工作可以逐步减少。

随着 AI-ready 页面规范和标准 Capability 沉淀，同一套能力还能复用到新项目，进一步降低交付成本。

### 3.4 从软件功能逐步演进为数字生产力

AI 业务助手阶段主要是“让人做得更快”。

数字员工阶段开始变成“系统本身能够承担工作”。

当客户购买的不再只是一个 AI 功能，而是可衡量的岗位生产力，产品的商业价值和持续付费能力都会发生变化。

## 4. 怎么挣钱，以及最快什么时候开始挣钱

### 4.1 第一笔收入不需要等标准化 V1 完成

最快的商业化路径不是先单独打造一个完整 AI 平台，而是利用现有政府 / 企业信息化项目，把 AI 作为可单独报价的增购能力或试点能力出售。

可以形成的收入包括：

- AI 模块增购。
- AI 业务场景实施。
- Tool / Capability 定制。
- 私有化部署。
- 模型接入。
- 年度维护与服务。

因此，**第一笔收入理论上可以发生在标准化 V1 之前**。

商业上可以先签订 AI 增购、试点或专项实施，再按项目推进 Demo 和客户交付。真正能否快速成交仍取决于具体客户、场景、预算和采购流程，本文不把时间判断当作收入承诺。

### 4.2 当前内部时间假设

基于当前已经存在的 AI 底座，如果首批范围控制在 1～3 个高价值完整业务场景，当前内部规划可以暂按以下节奏理解：

- **约 2～4 周**：形成有产品冲击力的业务 Demo。
- **约 4～8 周**：形成第一个可交付客户试点版本。
- **约 2～3 个月**：在真实试点反馈基础上形成相对标准化的 V1。

这些时间是基于当前项目状态的**内部规划假设**，不是对客户的商业交付承诺。后续如果 V1 范围、项目基础或真实试点条件发生重大变化，应重新评估。


### 4.3 科研 / 科技计划：第二条前期资金路线

除客户项目和产品收入外，本项目应正式建立一条长期科研 / 科技计划路线，重点关注：

- 省市级人工智能专项、重点研发计划和揭榜挂帅。
- 工业和信息化等领域的国家级创新任务揭榜挂帅。
- 与项目方向高度匹配的国家重点研发计划、科技重大专项或其他科技计划。
- 企业、高校、科研院所、用户单位组成的产学研联合申报。

这条路线的核心目标不是“为了申报另做一套科研项目”，而是：

> **同一套产品研发，同时形成商业产品资产、科研技术资产和示范应用资产。**

科研 / 科技计划资金主要承担四类价值：

1. 分担前沿能力的研发投入，降低公司完全依靠自有现金投入的压力。
2. 支撑客户短期不容易单独付费、但长期会形成壁垒的底层能力，例如可信执行、长任务、人机协同、Evaluation 和持续优化。
3. 获得示范项目、技术成果和政府 / 行业背书，为后续市场推广、合作和投标提供资产。
4. 建立与高校、科研院所、用户单位的联合创新网络。

财务上必须保持清晰边界：

> **科研项目经费 ≠ 普通软件订单收入 ≠ 可自由支配利润。**

不同科技计划可能存在任务书、预算用途、配套资金、过程检查和验收要求；是否有财政经费、经费比例和企业配套要求，应在实际申报时按当年度指南核实。

当前优先级原则是：

> **先从与真实客户和示范场景结合更紧密的省市级 AI 专项 / 揭榜挂帅切入，再择机参与国家级揭榜挂帅和国家重点研发计划。**

国家级项目早期不强求企业单独牵头。对于基础研究、算法研究或需要高水平科研资质的部分，可以与高校 / 科研院所联合；公司重点发挥真实业务场景、产品工程、系统集成、Agent 运行与产业化能力。

2026 年外部政策环境已经验证这条路径具有现实基础：工业和信息化部等七部门的创新任务揭榜挂帅明确设置人工智能方向，允许境内法人或非法人组织申报，鼓励企业、高校、科研院所等组成联合体，涉及应用示范的项目要求具有明确用户单位或市场前景；工业和信息化部、国家数据局“模数共振”行动也明确推动人工智能应用场景、特色智能体和创新联合体建设，并鼓励地方给予政策和资金支持。

参考：

- 工业和信息化部等七部门《2026年工业和信息化领域创新任务揭榜挂帅工作的通知》：https://wap.miit.gov.cn/jgsj/kjs/wjfb/art/2026/art_e4203ff219444b9783e721afb80f976d.html
- 工业和信息化部、国家数据局《联合实施2026年“模数共振”行动的通知》：https://www.miit.gov.cn/jgsj/kjs/wjfb/art/2026/art_71c830bf78a94f498bd3c187ac8b4778.html

## 5. 技术上是否可行

结论是：**可行，而且当前项目已经不是从零开始的概念验证。**

截至本文形成时，当前 AI 主线已经存在并验证了支撑第一阶段产品化所需的主要底座，包括：

- Provider / Model。
- Conversation / Message。
- Agent Loop。
- Tool Call / Tool Result。
- Run 生命周期、Stop、Steering。
- WRITE 确认。
- Context / Checkpoint / Compaction。
- Page Capability / Tool Registry。
- 当前页面受控操作和跨页面连续操作。
- 用户偏好、会话恢复和审计。
- AgentRuntime 及当前 Spring AI Adapter。
- Tool Policy Registry 及相应策略 Provider。
- 核心 Run 生命周期和 Tool Policy 测试。

Phase 3.5 P1 已完成收口：当前全部已接入的 Page Capability 已迁移到统一 Page / Action Contract + Runtime Bindings 机制，旧的长期双形态已经消除，并完成前后端 AI 主线配对的真实 Fullstack E2E 验收。

因此，当前真正的问题已经不是“能不能让模型调用一个工具”，而是如何把现有底座进一步转化为客户愿意购买的完整业务价值。

## 6. 真正重要的技术重点和难点

### 6.1 业务理解与能力接入

长期不能依赖 DOM、鼠标坐标、任意 JavaScript 或浏览器自动化去“猜”页面怎么操作。

正式方向是通过结构化：

- Page Capability。
- Tool。
- Action。
- API。
- 业务契约。

让 AI 使用明确注册、可理解、可验证的业务能力。

核心原则是：

> **业务事实尽量只定义一次，AI 复用真实业务能力。**

标准业务页面应逐步天然 AI-ready；特殊业务能力再显式扩展。

### 6.2 安全与治理

模型可以决定“想做什么”，但系统代码必须决定“允许做什么”。

不能只靠 Prompt 保证安全。

长期必须继续由系统保证：

- 当前身份和角色。
- RuoYi 权限。
- 数据范围。
- Tool Policy。
- Run 状态。
- WRITE 确认。
- 业务校验。
- 操作日志。
- 审计。
- 高风险动作的人类介入。

这也是政企客户真正愿意把 AI 放进生产系统的前提。

### 6.3 数字员工长任务可靠性

进入数字员工阶段后，任务将从“当前用户正在聊天窗口里等待完成”逐渐扩展为：

- 后台长任务。
- 事件触发。
- 定时 / 计划触发。
- 跨更长时间的任务状态。
- 失败恢复。
- Checkpoint。
- Human-in-the-loop。
- 异常请示。
- 结果评价。

这些能力是真正进入 V2 后才需要逐步建设的运行基础。

当前阶段不提前建设完整 Workflow、分布式任务平台或数字员工 Runtime，只保留清晰演进方向，避免为了未来假设增加当前复杂度。

### 6.4 自主进化必须形成受治理闭环

第三层不是“让 AI 随意改代码并自动上线”。

正确方向应类似：

```text
Observe
  ↓
Evaluate
  ↓
Propose
  ↓
Review
  ↓
Implement
  ↓
Test
  ↓
Approve
  ↓
Release
  ↓
Observe
```

任何 Prompt、Skill、Tool、页面、流程、配置或代码层面的改进，都应该能够记录：

- 问题来源。
- 真实证据。
- 评估结果。
- 改进方案。
- 审核结论。
- 实施变更。
- 测试结果。
- 审批。
- 发布结果。
- 后续效果。

自主程度只能在验证和治理能力成熟后逐步提高。

## 7. 第一个可对外版本：V1 AI 业务助手

V1 不追求做成“大而全的 Agent 平台”。

它只需要证明一件最关键的事情：

> **AI 能理解一个真实业务目标，并安全可靠地帮助用户把事情办完。**

### 7.1 V1 的场景范围

首批选择 **1～3 个真正有业务价值的完整场景**。

每个场景都应该形成完整闭环：

```text
自然语言目标
  ↓
查询 / 分析
  ↓
页面或业务能力调用
  ↓
必要确认
  ↓
完成业务
```

这里强调“完整场景”，而不是堆很多孤立的小功能。

### 7.2 V1 应证明的核心能力

- AI 能理解用户真正想完成的业务目标。
- AI 能获取完成目标所需的业务上下文。
- AI 能选择并调用系统允许的真实业务能力。
- AI 能处理查询、分析、导航和写操作。
- 高风险或写操作能进入确认 / 权限 / 校验边界。
- 跨页面过程能够保持连续上下文。
- 操作结果能够被记录和审计。
- 失败时能够给用户明确反馈，而不是静默产生错误副作用。

### 7.3 V1 的核心衡量标准

第一版最重要的指标不是：

- 做了多少 AI 功能。
- 接了多少模型。
- 有多少 Tool。
- 页面上有多少 AI 按钮。

而是：

> **客户看完以后，是否愿意把它装进自己的系统并付钱。**


### 7.4 V1 场景选择原则

V1 的旗舰场景默认采用“**查 → 判 → 办**”的完整业务闭环，产品体验可以进一步概括为：

> **查得到、判得准、办得了、不越权、有留痕。**

场景筛选优先考虑：

- 客户是否愿意为结果付费。
- 是否存在清晰、可量化的业务价值。
- AI 相比传统交互是否具有明显优势。
- 当前底座能否较快形成稳定闭环。
- 是否可以复制到其他客户或行业。
- 是否具有较强的演示冲击力。
- 是否能够抽象出有价值的科研问题，并形成真实示范场景。

其中**客户价值和付费意愿始终优先于科研包装**。科研价值用于放大一个本来就值得做的产品场景，而不是为了申报项目人为制造产品需求。

理想状态是：

> **一个真实客户场景，同时形成商业试点 + 科研示范 + 可复制产品能力。**

### 7.5 首批市场验证与候选示范方向

产品长期仍面向政企客户，但 V1 的首批市场验证优先从**已有的大中型企业客户和现成业务系统**切入，以利用既有信任、真实数据和较短的反馈链路，尽快验证客户是否愿意为 AI 业务助手付费。

这不意味着产品定位转为单一行业产品。当前产品形态仍是：

> **通用政企业务 AI 助手底座 + 行业 / 客户场景落地。**

当前已确认三个不同层次的候选验证方向：

1. **小程序场地预约：第一块试验田**  
   目标不是证明复杂行业价值，而是用低风险、规则清晰、闭环完整的小场景，最快验证“自然语言目标 → 查询 → 判断 → 操作 → 确认 → 完成”的真实办事体验。

2. **码头运营结算：旗舰场景候选**  
   重点用于证明 AI 在复杂、高价值、规则和审计要求较强的企业业务中，仍能够安全、可靠地完成“查 → 判 → 办”闭环。

3. **区域日用品贸易 / 商超供货：第二验证方向**  
   重点用于验证同一套 AI 业务助手底座能否迁移到高频商贸经营场景，证明跨行业可复制性。

以上只确定方向，不在本文替代业务团队定义具体流程、规则、数据范围和试点任务；具体业务场景由后续专项方案确定。

### 7.6 V1 与 V1.5 的边界

V1 的目标不是一开始就成为高度标准化的通用 Agent 平台，而是成为：

> **可收费、可部署、可交付的客户试点版。**

V1 至少应具备：

- 一个真实业务闭环能够端到端跑通。
- 权限、数据范围、WRITE 确认、后端校验和审计等安全边界完整。
- Provider / Model、系统级 AI 管理、用户偏好、基本运行诊断等交付所需能力可用。
- 交互已经达到真实产品水平，而不是只停留在技术演示。
- 允许针对首批客户做适度 Capability / Tool / Prompt / 业务规则适配，但不能为每个客户重新建设一套 AI 架构。

V1 明确不以以下能力为完成前提：

- Multi-Agent 平台。
- 数字员工后台自主运行。
- 通用 Workflow 平台。
- Skill / MCP / Plugin 市场。
- 完整知识库平台。
- 全站所有页面 AI 化。
- 自动修改代码或自主进化。
- 复杂审批引擎。
- 多租户 SaaS 平台。

如果某个真实场景确实需要 RAG、OCR、文档解析、报表分析等专项能力，可以作为**场景能力**接入，但不因此扩大为 V1 的平台建设任务。

V1 与 V1.5 的判断边界统一为：

> **V1 证明“第一个客户愿不愿意付钱”；V1.5 证明“第二、第三个客户是否不需要重新做一遍”。**

### 7.7 早期产品交互：让用户看得见 AI 在工作

早期用户面对 AI 代替自己执行真实业务时，除了效率，还需要建立信任和掌控感。因此 V1 在适合的场景中应优先让用户能够**直观看见 AI 正在替自己工作**。

可见过程可以包括：

- AI 主动导航到相关页面。
- 查询条件自动填写并执行。
- 页面内容随任务推进发生真实变化。
- 表单逐步填写。
- 关键判断和下一步动作可见。
- 写操作或高风险动作进入显式确认。
- 完成后明确展示结果与留痕。

这种体验既服务用户信任，也具有明显的客户演示和投资展示价值：

> **用户说出目标后，不只是聊天框返回答案，而是整个业务系统开始在 AI 的驱动下发生变化。**

但“可见执行”是一项**产品体验原则**，不等于把底层技术路线锁死为模拟鼠标点击或脆弱的 DOM 自动化。

底层可以根据场景采用：

- 受控 Page Capability / Action 驱动页面真实变化。
- 受控后端 API / Tool / 业务能力直接执行。
- 两者组合的混合模式。

选择标准是业务风险、执行效率、可解释性、用户信任和场景成熟度。随着用户信任和自动化成熟度提高，部分低风险、高频动作可以逐步从“可见式执行”过渡到更高效的直接执行。

因此 V1 的重要演示原则是：

> **Demo 不应只证明“AI 回答正确”，还应让人明显感受到“AI 正在替我工作”。**

---

## 8. V1.5：AI 原生业务系统能力

V1 解决“第一个客户场景能不能成立”。

V1.5 解决“这套能力能不能复制”。

核心突破是：

> **把第一个项目里的 AI 能力逐渐沉淀成可复制能力。**

重点方向包括：

- AI-ready 页面规范。
- 标准 Page / Action Capability。
- 标准业务能力契约。
- 代码生成支持。
- 通用场景模板。
- 行业场景模板。
- 更低成本的项目接入方式。
- 合作伙伴可复用的实施方法。

商业价值从“做一个项目”逐渐转变为“同一套能力可以反复交付”。

---

## 9. V2：数字员工

V2 的核心突破是：

> **从“用户叫它做”发展到“它知道自己的职责并主动完成”。**

数字员工逐渐拥有：

- 独立身份。
- 岗位。
- 角色。
- 职责范围。
- 权限。
- 任务。
- 事件触发。
- 计划 / 定时触发。
- 后台执行。
- 长任务状态。
- 异常请示。
- Human-in-the-loop。
- 工作记录。
- 结果评价。
- 可追责审计。

数字员工不是超级管理员，也不是无限制后台 Agent。

它应像真实员工一样：

> **有身份、有岗位、有权限、有职责、有记录、有评价、有需要请示的边界。**

---

## 10. V3：受治理的自主进化系统

V3 的核心突破是：

> **系统不仅完成业务，还持续发现怎样才能做得更好。**

改进对象可以逐步扩展到：

- Prompt。
- Skill。
- Tool。
- Capability。
- 页面。
- 业务流程。
- 配置。
- 模型策略。
- 上下文策略。
- Agent 工作方式。
- 必要时的代码实现。

但所有改进都必须处于可治理闭环中。

V3 的目标不是追求“完全无人控制”，而是让越来越多已经成熟、可验证、低风险的改进环节能够自动化，同时把高风险决策继续留在人类审批边界内。

## 11. 各阶段如何持续挣钱

### 11.1 AI 业务助手阶段：卖功能和项目能力

主要收入：

- AI 模块增购。
- AI 场景实施。
- Tool / Capability 定制。
- 私有化部署。
- 模型接入。
- 年度服务。

这一阶段最适合依托现有政企软件客户和已有项目快速形成第一批真实收入和案例。

### 11.2 V1.5：卖复制能力

逐渐增加：

- AI 增强版产品授权。
- 行业解决方案。
- 场景模板。
- AI 开发框架能力。
- 合作伙伴实施支持。
- 标准化升级和维护服务。

这个阶段的目标是降低“每来一个客户都重新做一遍”的比例。

### 11.3 数字员工阶段：卖生产力

收入结构逐渐转向：

- 数字员工订阅。
- 按岗位收费。
- 按 Agent 收费。
- 按任务量 / 执行量收费。
- 数字员工平台授权。
- 托管服务。
- 持续运营和优化服务。

此时客户购买的是持续可用的数字生产力，而不再只是一个软件功能。

### 11.4 自主进化阶段：卖平台与持续优化能力

长期可能形成：

- 企业 AI 平台授权。
- Agent Runtime。
- Governance。
- Evaluation。
- Skill / Tool / Agent 生态。
- 高级私有化版本。
- 持续优化服务。
- 行业级 AI 运行与治理平台。

### 11.5 科研 / 科技计划：贯穿 V1～V3 的研发融资与示范路径

科研路线不替代客户收入，而是与商业化并行：

- **V1 / V1.5**：优先围绕真实业务智能体、可信执行、AI-ready 业务系统和示范场景，争取省市级 AI 专项、重点研发和揭榜挂帅。
- **V2 数字员工**：围绕长任务、事件驱动、人机协同、岗位职责与可信治理等关键问题，争取更高层级技术攻关项目。
- **V3 自主进化**：围绕 Evaluation、运行反馈、持续优化、安全发布和治理闭环等前沿问题，选择性参与国家级重大或重点科研任务。

科研项目形成的通用能力必须回到产品主线，反哺客户项目和标准产品；不能形成与商业产品长期分叉的“科研专用代码”。

因此公司前中期可以形成三种相互促进的投入 / 回报机制：

> **客户项目提供现金流 → 科研项目分担前沿研发并形成背书 → 产品化把成果复制到更多客户。**

最终收入结构逐步演进为：

> **项目收入 → 产品收入 → 经常性数字员工收入 → 平台与生态收入**

## 12. 技术路线与商业路线如何互相约束

产品不能因为长期愿景很大，就提前建设当前客户不会付钱的平台能力。

每一阶段都应同时满足两个问题：

1. **这一阶段客户愿意为什么价值付钱？**
2. **这一阶段沉淀的能力是否能成为下一阶段的真实基础？**

因此推荐的节奏是：

```text
真实客户场景
    ↓
形成可收费价值
    ↓
验证技术和产品假设
    ↓
沉淀可复制能力
    ↓
扩大可收费范围
    ↓
进入下一阶段
```

技术演进必须由真实业务和商业验证推动，而不是反过来为了架构完整创造需求。

### 12.1 两套 Roadmap，一套研发

产品路线和科研路线可以采用不同语言表达，但底层只维护一套真实研发主线。

产品 Roadmap：

> **AI 业务助手 → AI 原生业务系统能力 → 数字员工 → 受治理的自主进化系统**

科研 Roadmap 可以对应为：

> **业务智能体语义理解与可信执行 → 复杂任务持续执行与人机协同 → 数字员工自主任务与治理 → 基于运行反馈和 Evaluation 的持续自优化**

重要能力以后尽量同时回答两个问题：

- **产品问题**：它为客户解决什么、为什么值得付钱？
- **科研问题**：它解决什么可验证的技术问题、能形成什么指标和示范成果？

这种“双重定义”用于帮助筛选科研课题和沉淀技术成果，不意味着每一个普通产品功能都必须包装成科研项目。
