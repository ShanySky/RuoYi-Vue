# RuoYi AI 助手第二阶段推进目标与验收计划

> 状态：待实施  
> 日期：2026-09-18  
> 适用分支：`ShanySky/RuoYi-Vue:chatgpt/ai-agent-assistant` 与 `ShanySky/RuoYi-Vue3:chatgpt/ai-agent-assistant`  
> 关联文档：`06-AI助手与Agent集成方案.md`、`07-AI助手第一阶段实施计划.md`、`08-AI助手第一阶段实施与验收记录.md`

## 1. 用户诉求

第一阶段已经完成 AI Provider、模型同步、Agent Tool Loop、页面 Tool、WRITE 确认和全栈闭环。第二阶段不重做基础架构，重点把 AI 助手从“可运行的第一版”完善成更适合长期使用的交互和配置体验，同时修复已发现的稳定性问题。

本阶段核心诉求：

- 修复同一 Conversation 多轮 Tool Calling 时可能发生的重复 callId 冲突。
- 明确 `userName` 与 `nickName` 的语义边界，避免 AI 误操作或误解释。
- 将当前右侧模态 Drawer 改成“右下角小窗 + 右侧 Dock”两种非模态工作形态。
- AI 打开时不遮罩业务页面，用户可以一边看 AI，一边继续操作当前页面。
- 聊天窗口内直接提供常用 AI 配置入口，不要求跳到独立管理页。
- 支持多个模型、模型实时联想搜索、默认模型、默认思考档位。
- 同一会话允许按后续轮次切换模型和思考档位。
- 正式产品始终调用用户配置的真实 OpenAI-compatible Provider；mock 只用于 CI、自动测试和临时演示。
- 保持第一阶段已经通过验收的权限、安全、日志、Tool Loop 和业务 API 复用能力不回退。

## 2. 第二阶段总目标

完成一套稳定、非模态、可快速配置、多模型可切换的 AI 助手交互。

最终用户应能够：

1. 在任意业务页面右下角打开 AI 小窗。
2. 在不离开当前业务页面的情况下聊天、查看 Tool 执行状态、快速配置 Provider 和模型。
3. 需要更多空间时，把 AI 小窗展开成右侧 Dock；主业务页面被压缩但仍完整显示且可操作。
4. 使用多个已配置模型，并通过实时联想搜索快速找到目标模型。
5. 设置默认模型和默认思考档位；高级用户可在模型二级菜单中调整 reasoning effort。
6. 在同一个 Conversation 中按后续轮次切换模型/档位而不丢失上下文。
7. 使用真实 Provider 完成普通聊天和 Tool Calling。
8. 多轮 Tool Calling、异常 Provider、模型切换和 Tool Result 恢复都保持稳定，不向用户暴露数据库或框架内部异常。

## 3. 已确认产品决策

以下内容视为第二阶段已确认的产品行为，实施过程中不得无故改变。

### 3.1 AI 窗口形态

AI 助手有三种显示状态：

- 收起：右下角 AI 入口按钮。
- 小窗：右下角浮动聊天窗口。
- 展开：右侧 Dock 工作区。

要求：

- 小窗和 Dock 都是非模态。
- 不显示页面遮罩。
- 业务页面始终允许查看、点击和编辑。
- Dock 不是覆盖层；它占据右侧真实布局空间，主业务区域同步变窄但完整参与布局。
- Dock 建议默认宽度约 520–560px，并允许合理范围内拖动调宽/调窄。
- 收起、小窗、Dock 之间切换不得重建 AI 会话。

### 3.2 会话状态保持

显示形态切换时必须保留：

- conversationId。
- 消息历史。
- 当前模型。
- 当前 reasoning effort。
- Tool 执行状态。
- pending WRITE 确认状态。
- 当前未发送的输入内容。

UI 状态和 Agent 会话状态必须分离。

### 3.3 输入快捷键

默认模式：

- Enter：发送。
- Shift + Enter：换行。

允许切换为：

- Ctrl + Enter：发送。
- Enter：换行。
- Shift + Enter：换行。

快捷键偏好保存到浏览器本地，下次继续沿用。

### 3.4 AI 快捷配置入口

小窗和 Dock 两种形态的标题区域都必须提供快捷设置入口。

快捷设置不能强制跳离当前业务页面，至少支持：

- Provider Base URL。
- Token。
- 测试连接。
- 同步模型。
- 查看/搜索/启用模型。
- 设置默认模型。
- 设置默认思考档位。

现有完整 AI 配置页继续保留，用于完整管理和后续复杂 Provider 能力。快捷配置和完整配置必须使用同一套后端数据，不维护两份状态。

### 3.5 多模型与模型选择

系统允许配置和启用多个模型。

聊天输入区域右下角显示当前模型选择器，但不直接常驻显示思考档位。

模型选择要求：

- 输入即实时过滤，不要求完整输入后按回车。
- 前缀匹配优先。
- 包含匹配其次。
- 支持类似 `gpt`、`5.6`、`sol` 的部分输入。
- 做轻量 debounce。
- 可高亮匹配部分。
- 空输入时不要一次性列出全部模型，只显示默认模型、最近使用或少量常用项。
- 配置页和聊天窗口共用同一套模型搜索/排序逻辑。
- 优先从已经同步到本地的数据中过滤，不要每输入一个字符就请求远端 Provider。

### 3.6 默认模型与思考档位

允许设置：

- 默认模型。
- 默认 reasoning effort。

新会话默认采用该组合。

思考档位属于高级选项：

- 不在输入框旁常驻显示。
- 从模型选择菜单进入二级入口后再设置。
- 不同 Provider/模型只展示实际支持的档位。
- 能力未知时使用 Provider 默认行为，不强行传递 reasoning 参数。

同一 Conversation 中允许切换模型和 reasoning effort，新选择从下一轮开始生效。

### 3.7 正式 Provider 与 mock 边界

正式运行流程必须是：

`Base URL + Token → /models → 同步模型 → 启用/默认 → Agent 调用真实 Provider`

要求：

- 产品代码不能写死 `mock-agent-model`。
- 产品代码不能依赖 `localhost:18080`。
- 配置真实 Provider 后，聊天和 Tool Calling 都直接使用真实模型。
- Provider 调用失败时返回可理解的真实错误，不静默回退到 mock。
- 未配置 Provider 时明确提示用户先配置 AI 服务。

mock 只允许用于：

- CI。
- 自动测试。
- 临时公网演示。

## 4. 必须修复的 Bug

### 4.1 Tool Call ID 重复

当前临时演示 mock 曾使用固定 `call_preview_1/2/3/4`，导致同一 Conversation 第二轮 Tool Calling 时触发 `ai_pending_tool_call` 唯一键冲突。

需要同时修复两层：

1. mock 每次 Tool Call 生成真正唯一的 Provider callId。
2. Agent Runtime 不完全信任外部 Provider callId。

Runtime 应保证：

- 外部 Provider 返回重复或异常 callId 时，不直接向用户暴露 SQL 唯一键异常。
- Provider callId 与数据库内部唯一标识的职责清晰分离。
- 需要时使用内部唯一 ID 保存 pending Tool Call，同时保留原 Provider callId 用于消息协议关联。
- 错误应转换成可诊断的 Agent 级错误。
- 同一 Conversation 连续多轮 Tool Calling 必须稳定执行。

必须加入自动回归测试。

### 4.2 `userName` / `nickName` 语义边界

RuoYi 当前：

- `userName` = 登录账号。
- `nickName` = 用户昵称。

当前正常编辑流程不支持修改已有用户的 `userName`。

因此：

- AI 不得把“修改登录账号”偷偷映射成修改昵称。
- 用户明确要求修改已有 `userName` 时，应告诉用户当前系统不支持该操作。
- 用户要求修改“昵称”时才调用 `nickName` Tool。
- Tool 描述、System Prompt、Page Context、mock 规则都要避免“用户名/昵称”混淆。
- 不允许绕过 RuoYi 原业务规则直接更新数据库。

## 5. 后端需要完善的能力

### 5.1 每轮模型与 reasoning 记录

Conversation 不再视为永久绑定一个模型。

每次实际模型调用至少需要可追溯：

- modelId。
- modelCode。
- reasoningEffort。

历史消息要能够知道由哪个模型、哪个档位生成。

Conversation 可以保存当前/默认选择作为便利状态，但不能成为唯一事实来源。

### 5.2 Tool Result 恢复时模型一致性

一个模型产生 Tool Call 后，即使用户在 UI 中切换了模型，当前 pending Tool Call 恢复时也必须继续使用产生该 Tool Call 的那一轮模型/档位，避免跨模型恢复。

新模型选择只影响下一轮新的用户消息。

该行为必须有自动测试。

### 5.3 Provider/模型能力兼容

需要明确：

- 模型是否支持 Tool Calling。
- 模型是否支持 reasoning effort。
- 如果支持，支持哪些档位或参数格式。

不要假设所有 OpenAI-compatible Provider 都支持完全一致的参数。

第一阶段已有 Tool Calling capability 测试继续保留并扩展能力描述。

## 6. 前端需要完善的能力

### 6.1 AI Assistant 组件重构

将当前 Drawer 型实现拆成更清晰的状态和视图结构，至少包括：

- Launcher。
- Floating Chat Window。
- Dock Panel。
- Shared Conversation Content。
- Quick Settings。
- Model Selector。
- Composer。

避免为小窗和 Dock 分别复制一套聊天逻辑。

### 6.2 Dock 布局

展开时由 Layout 层为 AI Dock 预留实际宽度。

目标是：

- 右侧 AI 占布局空间。
- 主区域重新计算宽度。
- 表格、表单、弹窗等业务内容仍能正常响应。
- 不用遮罩。
- 不靠简单 absolute/fixed 覆盖实现“假 Dock”。

### 6.3 模型搜索组件

抽成可复用模型选择能力，用于：

- 快捷设置。
- 完整 AI 配置页。
- 聊天输入区模型选择。

排序建议：

1. 当前默认。
2. 最近使用。
3. 前缀匹配。
4. 包含匹配。
5. 其他结果。

### 6.4 快捷设置

聊天窗口内部提供常用设置，不离开当前路由。

设置完成后返回聊天：

- Conversation 不丢。
- 页面 Tool Registry 不丢。
- 页面上下文继续可用。

## 7. 已有基线不得回退

第二阶段实施时，以下第一阶段能力必须继续有效：

- OpenAI-compatible Base URL + Token。
- Token AES/GCM 加密。
- Token 不回显。
- Provider 保存日志不记录明文 Token。
- 模型同步。
- 多模型启用/默认。
- Tool Calling capability 测试。
- HTTP Turn Agent Loop。
- Tool Call pause / Tool Result resume。
- 服务器权威 Tool allowlist/schema/risk/permission。
- 用户管理四个 Page Tools。
- WRITE 操作确认。
- RuoYi 原 `@PreAuthorize`、数据范围、业务 API 和操作日志继续生效。
- pending Tool Call 超时和权限二次检查。
- 日志单文件大小、历史天数、总容量限制和 gzip。
- AI 默认 INFO、Spring AI 默认 WARN。
- 产品运行不依赖 Playwright。

## 7.1 数据库升级方式

- 新环境：直接使用最新版 `sql/ai_20260918.sql` 初始化 AI 表。
- 已经部署第一阶段 AI 表的环境：在现有数据库上额外执行一次 `sql/ai_phase2_20260918.sql`。
- 增量脚本会补充 reasoning 和每轮模型追溯字段，并把无法安全恢复的第一阶段遗留 PENDING Tool Call 标记为 EXPIRED。
- 不要在已经包含第二阶段字段的新环境上重复执行增量脚本。

## 8. 日志与安全要求

第二阶段新增功能不得为了调试默认记录完整：

- Prompt。
- Model Response。
- Token。
- Authorization。
- 敏感 Tool Arguments。

需要调试时使用受控 DEBUG，并确保敏感信息脱敏。

应用层现有日志容量边界继续保持。

如果未来采用 Docker/systemd 部署，部署层还需单独配置 stdout/journald 日志轮转；该要求属于部署基线，不由 Logback 替代。

## 9. Harness 后续方向

本阶段不以 Harness 为前置条件。

如果未来需要：

1. 首选 SDK 内嵌式 Harness，直接集成到 `ruoyi-ai`，由 Spring Boot 托管生命周期，实现“后端启动即 Harness 可用”。
2. 如果没有合适的内嵌 SDK、又确实需要独立 Harness，优先考虑 Pi Agent。
3. 不接 Codex Harness。
4. AgentRuntime 抽象继续保持通用，不把业务层绑定到具体 Harness。

## 11. 最终验收标准

### 11.1 Bug 验收

- 同一 Conversation 连续多轮 Tool Calling 无重复 callId 冲突。
- 重复/异常 Provider callId 不直接暴露数据库异常。
- `userName` 与 `nickName` 行为符合 RuoYi 业务规则。

### 11.2 UI 验收

- 默认使用右下角小窗。
- 页面无遮罩。
- AI 打开时业务页面仍可操作。
- 可以展开成右侧 Dock。
- Dock 展开后主页面被压缩但完整显示。
- Dock 宽度可合理调整。
- 小窗/Dock/收起切换不丢会话和 pending 状态。

### 11.3 输入验收

- Enter 发送。
- Shift+Enter 换行。
- 可切换 Ctrl+Enter 发送。
- 快捷键偏好持久化。

### 11.4 配置验收

- 小窗和 Dock 都可快速进入 AI 设置。
- 不离开业务页面即可配置常用 Provider/模型项。
- 完整 AI 配置页继续可用。
- 两处配置状态一致。

### 11.5 Provider 验收

使用用户填写的真实 Base URL + Token + Model 时：

- 普通聊天直接调用真实 Provider。
- Tool Calling 直接调用真实 Provider。
- 不依赖 mock。
- Provider 错误不会静默切到 mock。

### 11.6 模型验收

- 可启用多个模型。
- 模型输入实时联想。
- 不要求完整输入或按回车才搜索。
- 空输入不铺满所有模型。
- 默认模型生效。
- 同一 Conversation 后续轮次可以切换模型。

### 11.7 Reasoning 验收

- 可设置默认 reasoning effort。
- 普通输入区不常驻显示档位。
- 档位通过模型二级入口调整。
- 同一 Conversation 后续轮次可改变档位。
- 不支持 reasoning 的模型不会收到非法参数。
- pending Tool Call 恢复时仍使用原轮次正确模型/档位。

### 11.8 数据与追溯

每次实际模型调用可以追溯：

- modelId/modelCode。
- reasoningEffort。

历史消息不会因后续切换模型而被改写。

### 11.9 回归验收

第一阶段以下能力继续通过：

- Provider Token 加密和脱敏。
- 模型同步。
- Tool Calling。
- Page Tools。
- WRITE 确认。
- RuoYi 权限和数据范围。
- pending 状态机。
- 日志磁盘保护。

### 11.10 真实运行验收

至少实际完成：

- MySQL。
- Redis。
- Maven package。
- Spring Boot 真正启动。
- npm / production build。
- Vite 页面。
- Agent API。
- Chromium E2E。
- 临时公网预览。

最终必须提供可人工访问的预览环境。

## 12. 推进原则

本阶段按“目标模式”持续推进。

每个阶段采用：

`实现 → 自动测试 → 发现问题 → 修复 → 再验证 → 继续下一阶段`

不要因为完成某一个子阶段、某一个页面或某一次 CI 绿色就提前结束整个第二阶段。

普通技术问题，例如：

- 编译失败。
- 测试失败。
- Selector 失效。
- CI 问题。
- mock Bug。
- Provider 兼容问题。
- 页面布局 Bug。

应自行诊断、修复并继续推进，不视为暂停理由。

## 13. 允许暂停的条件

只有以下情况允许暂停并询问用户：

1. 所有第二阶段最终验收标准已经满足。
2. 发现必须改变本文件“已确认产品决策”的重大产品方向冲突。
3. 必须依赖用户提供的真实凭据、权限或外部资源，且没有安全替代方案。
4. 发现继续实施会明显破坏现有业务兼容性，需要用户选择取舍。

除上述情况外，应持续推进至最终验收。
