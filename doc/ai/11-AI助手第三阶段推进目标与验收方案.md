## 1. 文档定位与最高原则

第三阶段不再把 AI 助手当作 Demo 功能继续“补按钮”，而是围绕真实长期使用中的几个核心问题，完善运行控制、上下文生命周期、模型调用成本、交互体验和页面业务能力边界。

本阶段所有方案、计划、实施和验收必须遵守一条最高原则：

> **用户诉求是唯一主线。每项技术设计都必须说明它解决哪一条用户诉求；每项实施任务都必须回指对应诉求；最终验收必须重新回到用户真实使用场景验证，而不能只因为编译通过、接口返回 200、数据库有记录或某个技术指标达标就宣布完成。**

因此本阶段采用“需求追踪链”：

`用户诉求 → 方案决策 → 实施任务 → 自动验证 → 人工场景验收 → 最终结论`

任何一环断开，都不能视为该需求完成。

对于已经整体讨论并获得用户认可的方案，如果用户只针对其中部分条目提出修改或补充，则未被明确否定、撤回或替换的其他条目继续视为已确认基线；不能因为用户没有逐条回复“同意”就把其余内容自动降级为待定。后续以用户明确提出的新意见覆盖对应旧内容，未被修改的部分继续有效。

## 2. 第三阶段用户诉求清单

以下编号是第三阶段后续所有文档、代码提交和验收记录的统一追踪 ID。

### R3-01 聊天字体可调整

用户可以在 AI 设置中调整聊天窗内字体大小。

要求：

- 只影响 AI 聊天相关内容，不改变 RuoYi 全局字号。
- 至少提供“小 / 标准 / 大 / 特大”。
- 小窗与 Dock 共用同一设置。
- 字体属于用户级 AI 偏好，以账号侧配置为主数据；浏览器本地仅作为缓存/设备级补充。
- 刷新、重新登录后继续生效，换设备登录时也能恢复账号偏好。
- 标题栏、按钮和布局不应因为正文放大而失衡。

### R3-02 明确的“停止当前执行”

AI 开始执行后，发送按钮位置切换为清晰可见的“停止”操作。

停止不是简单隐藏 Loading，而是终止当前 Agent run 的后续行为：

- 前端立即停止继续等待旧 run。
- 后端标记当前 run 为取消/停止。
- 能取消上游模型 HTTP 请求时尽量取消。
- 如果上游结果已经在路上，结果返回后也不得继续执行新的 Tool。
- 尚未开始的 WRITE 不得继续执行。
- 已经提交完成的不可逆业务写入不伪装成回滚。

### R3-03 双击 ESC 中断，且严格限定焦点范围

除停止按钮外，支持连续两次 `Esc` 中断当前 AI 执行。

要求：

- 只有焦点位于 AI 聊天窗口内部时有效。
- 焦点在 RuoYi 业务页面、表格、编辑弹框、其他输入框时，不得影响 AI run。
- 两次 ESC 使用短时间窗口，第一版建议约 700ms。
- 第一次 ESC 仅进入“等待第二次 ESC”的提示状态，不直接停止。
- 如果 AI 内部正打开模型下拉、思考档位菜单、设置弹层等，第一次 ESC 只关闭内部控件，且不计入“双 ESC”序列。
- 目的不是追求快捷键本身，而是让熟练用户能快速、安全地回收错误指令，同时降低误触风险。

### R3-04 AI 工作中继续补充指令（Steering）

AI 正在执行时，输入框仍保持可编辑和可发送。

用户可以连续补充、纠偏或改变要求，而不是被迫等待上一条指令完整结束。

核心语义：

- 同一个 Conversation 同时只允许一个真正执行中的 Agent run。
- 新补充指令立即作为新的用户消息写入会话，不能丢失。
- 当前旧 run 被标记为 superseded。
- 旧规划在安全边界停止。
- 新 run 基于完整会话和所有最新补充重新规划。
- 不允许两个 Agent 并行执行同一会话中的 Tool 或 WRITE。
- 尚未执行的旧 Tool 不再继续。
- 已经完成的 READ/WRITE 作为真实历史保留，新规划必须基于真实结果继续。
- 如果旧 run 正等待 WRITE 确认而用户发来纠偏，应取消旧待确认规划，重新生成符合最新意图的操作。

目标体验是“用户可以边看 AI 做事边继续说”，而不是“每条消息必须串行等待整个 Agent 流程结束”。

### R3-05 GPT Prompt Cache / 缓存成本优化

当前 GPT 测试环境中需要实际利用模型侧 Prompt Cache，降低长会话重复输入成本。

方案原则：

- 实施前重新核对当前 OpenAI/GPT 与 Spring AI 实际支持方式，不根据旧文档写死参数。
- 优先支持 GPT 系列；如果 OpenAI-compatible Provider 能通用支持，则抽象成通用能力。
- 固定 System Prompt、稳定 Tool schema 等可复用内容保持稳定前缀。
- route、Page Context、临时页面状态等高变化信息尽量后置，避免破坏缓存前缀。
- 保持多轮消息追加式组织，不无必要重写历史。
- 在 Provider 支持时使用合适的 prompt cache key / cache 参数。
- 增加缓存可观测性，至少能看到输入 Token、缓存读取 Token、缓存写入 Token或 Provider 能提供的等价数据。
- 不把“传了某个 cache 参数”视为完成；必须尽可能通过真实 GPT 调用确认第二轮及后续请求出现缓存读取。

技术指标只是证明，真正目标是：**相同长会话继续进行时，不再每轮都按全部重复前缀支付完整输入成本。**

### R3-06 Reasoning Effort 修正与中文化

思考档位显示不再使用英文，且必须与实际模型能力一致。

GPT-5.6 当前目标映射：

- `none` → 无
- `low` → 低
- `medium` → 中
- `high` → 高
- `xhigh` → 极高
- `max` → 最高

原则：

- 前端显示中文。
- 后端/API/数据库继续保存 Provider 原始枚举值，避免协议层混乱。
- `minimal` 不能与 `none` 混为一谈。
- 如果未来其他模型真实支持 `minimal`，再作为独立能力显示，不人为假设所有模型一致。
- 能力探测逻辑必须覆盖当前模型真实支持档位，不得继续漏掉 `none` / `max` 或探测无效档位。

### R3-07 自动上下文压缩与压缩后自动续跑

会话达到一定上下文占用后，Agent 自动进行上下文压缩，并在压缩完成后继续当前任务，不要求用户重新发送指令。

第一版默认：

- 工作上下文预算：64K tokens。
- 自动压缩：开启。
- 压缩阈值：75%。
- 即约 48K tokens 左右开始进入压缩流程。

注意：64K 是我们给 Agent Runtime 的工作预算，不等同于 Provider 模型物理最大上下文。

压缩不能删除数据库完整历史；数据库仍保存原始 Conversation。发送给模型时使用：

`稳定系统指令 + 最新 Checkpoint 摘要 + 最近未压缩消息 + 当前指令`

压缩必须发生在安全点：

- Tool Call 与对应 Tool Result 不能被拆开。
- pending Tool / WRITE 状态必须保留。
- 正在执行不可逆业务写入时不能粗暴切断并制造虚假状态。

压缩后的 Checkpoint 至少必须保留：

1. 当前主题。
2. 最终目标。
3. 用户已经确认的决策。
4. 已完成的工作和关键结果。
5. 当前正在进行到哪一步。
6. 尚未完成的任务。
7. 下一步应该继续做什么。
8. 已发现但尚未解决的问题。
9. 已执行的 Tool 和重要 Tool Result。
10. 已经发生的 WRITE / 不可逆操作。
11. pending Tool / WRITE / 用户确认状态。
12. 用户最新一次补充、纠偏或覆盖旧规划的要求。
13. 继续执行需要的关键 ID、字段、配置值、文件、接口和页面状态。
14. 哪些内容是事实，哪些仍是暂定方案。
15. 压缩后需要重新检查或确认的事项。
16. 明确说明不要重复已经完成的工作。

目标是“可继续工作的 Agent Handoff / Checkpoint”，不是普通聊天摘要。

### R3-08 每模型上下文与压缩高级设置

上下文窗口和自动压缩参数放在系统模型的高级设置中。

第一版至少包括：

- 工作上下文窗口：默认 64K。
- 自动压缩：默认开启。
- 压缩阈值：默认 75%。
- 默认思考档位。

原则：

- 不把这些参数全部挤在系统模型表格主行。
- 从“高级设置”进入。
- 不同模型可分别配置。
- `/models` 无法可靠返回上下文窗口时允许人工设置。
- 后续可以维护已知模型默认值，但不得把静态默认值冒充 Provider 的权威声明。

### R3-09 模型选择器视觉与聊天 UI 继续精修

聊天左下角模型选择器必须重新整理视觉。

要求：

- 不再使用文本字符模拟下拉箭头。
- 使用 Element Plus 图标或正规 SVG Chevron。
- 调整按钮高度、左右间距、模型名截断、Hover/Selected 状态。
- 思考档位继续作为二级入口。
- 与 RuoYi / Element Plus 主题、颜色、圆角和组件密度保持一致。
- 本阶段新增停止、Steering、压缩状态等交互也必须延续相同视觉语言。

已确认的 HTML 交互原型作为实现参考，但原型是本轮重点局部展示，不能因此删除第二阶段已经存在的 Provider、模型管理和快捷设置功能。

### R3-10 页面能力从 Demo Tool 扩展到完整语义化页面能力

当前 AI 只能看到和操作用户管理页面的一小部分字段和功能，第三阶段要越过 Demo 边界。

目标：

> 当前登录用户在 RuoYi 业务页面上正常可见、可通过原业务流程完成的字段和动作，应尽可能通过语义化页面能力提供给 AI，而不是继续人为只暴露四五个 Demo Tool。

能力范围至少包括：

- 页面查询条件。
- 表格列、分页、排序、当前选中记录。
- 表单业务字段。
- 字典/下拉选项。
- 字段校验规则。
- 新增、编辑、保存、取消。
- 查询、重置、刷新。
- 启用、停用。
- 批量操作。
- 导入、导出。
- 重置密码。
- 分配角色/岗位等页面已有业务动作。
- Dialog / Drawer 中的字段和动作。
- 当前页面真实存在且当前用户有权执行的其他业务按钮。

实现原则：

- 不把“完整开放”理解成任意 DOM/JavaScript 执行。
- 不绕过 RuoYi 原 Service/API 直接更新数据库。
- 权限控制继续以当前 RuoYi 用户权限、数据权限和原业务规则为基础。
- AI 特有安全策略可以在后续收紧，但第三阶段不再使用 Demo 白名单人为隐藏大量正常业务能力。
- 页面能力层应走通用协议/注册机制，避免每个页面长期手写大量完全不同的 Tool。
- 对当前代码仓库中的业务页面建立能力覆盖清单；不能静默漏掉页面或功能，暂时无法语义化的能力必须明确记录原因和后续处理方式。



### R3-11 System Prompt / Compaction Prompt 数据库化与可配置

当前 System Prompt 与压缩/Checkpoint Prompt 不再长期硬编码在 Java 代码中，而是作为系统级 AI 配置持久化到数据库，并由有权限的管理员在 AI 管理中维护。

要求：

- 至少区分 System Prompt 与 Compaction / Checkpoint Prompt 两类。
- 保存当前内容、启用状态、版本、修改人、修改时间。
- 提供“恢复系统默认”能力，避免管理员误改后无法回退。
- 支持必要的模板变量，例如 route、pageContext、availableCapabilities、checkpoint 等。
- 保存前校验关键占位符和模板结构，避免配置一保存就导致运行时不可用。
- Prompt 内容变化需要明确版本，便于排查某次会话实际使用了哪个版本。
- 安全规则不能只依赖 Prompt。权限、数据范围、WRITE 确认、Run 状态、Tool/Capability 服务端校验继续由代码和后端安全边界保证。
- Prompt 管理属于系统全局 AI 配置，普通用户不可修改。

### R3-12 其他业务页面全面接入 AI Page Capability

第三阶段不能只把“用户管理”做完整后停下，而要把当前 RuoYi 其他业务页面按同一套语义化 Page Capability 方式纳入 AI。

要求：

- 先从当前前端真实路由和页面源码建立页面清单。
- 每个页面盘点查询条件、表格上下文、表单字段、字典/选项、校验规则、Dialog/Drawer、按钮、批量动作、导入/导出及特殊业务动作。
- 每个页面都进入页面能力覆盖矩阵，标明已覆盖、部分覆盖、暂不可覆盖及原因。
- 不允许只完成协议抽象就宣称“所有页面已经接入”。
- 页面能力继续服从当前用户 RuoYi 权限和数据权限。
- 管理员可在系统级 AI 管理中控制“哪些页面允许接入 AI”。
- 第三阶段先完成页面接入管理和真实能力覆盖；复杂的可配置 WRITE/高风险确认策略、全局 Tool/Capability 策略编辑器暂不做成复杂 UI，继续使用固定、可靠的服务端安全规则，后续阶段按真实需求再开放策略配置。

### R3-13 AI 跨页面导航与连续业务操作

AI 不再只能操作当前页面，而应能为了完成一个业务目标主动跨页面连续工作。

目标示例：

`用户管理 → 角色管理 → 用户授权页面 → 部门管理`

要求：

- 提供应用级的语义化导航能力，不使用浏览器坐标或 Playwright 控制。
- AI 可以查询当前系统中可到达且当前用户有权限访问的页面。
- 导航通过 Vue Router 正常跳转。
- 目标页面加载完成后重新注册 Page Capability，并返回“页面已就绪 + 当前页面上下文”。
- Agent 在新页面能力 ready 后继续原 Run，不要求用户重新发送指令。
- 跨页面过程中的 Conversation、模型、reasoning、Checkpoint、Run、Steering 状态持续保持。
- 页面跳转后旧页面未执行的 Page Tool 必须失效，不能拿刷新/跳转前的页面实例继续执行。
- Page Capability 需要带 route/page instance/version 等快照信息，Tool 执行前确认仍属于当前有效页面实例。

### R3-14 Conversation / Run / UI 状态应用级持久化与刷新恢复

Conversation 不是页面对象，也不是 Vue 组件内存对象，而是后端持久化的应用级业务对象。

必须明确四层状态：

1. 后端数据库：Conversation、Message、Run、Checkpoint、Pending Tool 等权威状态。
2. 前端全局 AI Store：后端状态的当前镜像，不再把关键会话状态锁死在 AiAssistant 组件局部 ref 中。
3. sessionStorage：保存当前浏览器 Tab 的 activeConversationId、未发送 Draft 等恢复入口。
4. localStorage / 本机存储：只保存适合设备级持久化的 UI 偏好，例如 Dock 宽度。

要求：

- 正常 Vue Router 页面切换，会话不丢。
- AI 主动跨页面，会话不丢。
- 用户 F5 / Ctrl+R 刷新后，自动恢复当前 Conversation 和聊天历史。
- 刷新时如果 Run 仍 RUNNING，前端重新加载当前 Run 状态。
- pending Tool / WRITE 不因为刷新变成孤儿；需要按真实状态恢复、取消或重新确认。
- 刷新后旧 Page Capability Instance 失效，新页面加载后注册新的实例。
- 不同浏览器 Tab 使用 sessionStorage 隔离 activeConversationId，避免两个 Tab 被强制绑成一个当前会话。
- 同一个 Conversation 无论从几个 Tab 打开，仍坚持“最多一个活动 Run”的服务端规则。
- 后端数据库始终是 Source of Truth，前端缓存不能覆盖服务器事实。

### R3-15 用户级持久化会话历史与历史会话管理

Conversation 属于用户账号，而不是浏览器会话。用户退出登录、关闭浏览器、第二天重新登录后，仍可找到自己的历史会话。

第一版至少支持：

- 查看自己的最近会话。
- 按最后更新时间排序和按时间分组。
- 简单搜索会话标题。
- 切换/恢复某个历史 Conversation。
- 新建会话。
- 自动生成可读的会话标题，并允许用户重命名。
- 按系统策略允许归档/删除自己的会话。
- 重新打开历史会话后可以继续工作，加载历史 Message、Checkpoint、模型/reasoning 等需要恢复的上下文。
- 历史列表默认不作为新手用户的一级强曝光界面。

重新登录默认进入新会话状态，但用户可以主动选择“恢复上次会话”或从历史列表切换。

退出登录时：

- 当前 RUNNING Run 安全取消。
- pending Tool / pending WRITE 取消或过期。
- 完整历史仍保留。
- 下次打开旧会话时明确显示上次执行因退出登录而中断，不自动恢复未确认的危险操作。

### R3-16 用户 AI 偏好、历史入口、自动恢复与撤销恢复

用户级 AI 偏好与系统级管理员配置分离，并绑定用户账号。

用户偏好至少包括：

- 我的默认模型。
- 我的默认 reasoning 档位。
- 聊天字体大小。
- Enter / Ctrl+Enter 发送方式。
- 双 ESC 中断是否开启。
- 是否显示“会话历史”入口。
- 是否登录后自动恢复上次会话。
- AI 助手默认打开方式，例如默认小窗、默认 Dock，或恢复上次使用模式。
- 其他不会改变系统安全边界的个人体验设置。

设备相关偏好，例如 Dock 宽度，可采用“账号默认 + 本机优先”或直接本机优先，避免不同屏幕尺寸互相污染。

会话历史入口：

- 默认关闭/隐藏，保持新手用户界面简洁。
- 用户开启后，AI 标题区域出现低干扰的历史入口。
- 历史列表是按需打开，不常驻占据业务界面。

恢复上次会话：

- 默认提供显式“恢复上次会话”操作。
- “登录后自动恢复上次会话”默认关闭，由高级用户自行开启。
- 自动或手动恢复后提供短时“撤销恢复”。
- 撤销要恢复 previousConversationId、Draft、模型/reasoning 选择等恢复前状态。
- 撤销只在短时间窗口内且用户尚未在恢复后的会话产生新的 Agent 行为时有效。
- 一旦用户发送新消息或触发新 Run，撤销入口立即失效，避免误导成“回滚已经发生的业务操作”。
- 即使撤销入口失效，用户仍可通过历史列表切换回其他会话。

### R3-17 系统级 AI 配置与用户级 AI 设置分层，建立 AI 管理一级模块

建立一个清晰的一级“AI 管理”模块，收纳管理员级 AI 能力；普通用户的个人 AI 设置继续放在 AI 助手内，不把管理员概念暴露给普通用户。

最终信息架构明确分为三个入口：

1. **AI 管理**：管理员级系统配置与审计能力。
2. **我的 AI 设置**：普通用户自己的默认模型、reasoning、字体、快捷键、双 ESC、历史入口、自动恢复等个人偏好。
3. **会话历史**：普通用户查看自己的历史会话；默认入口可隐藏，高级用户按需开启。管理员查看全员会话不从这里进入，而是走“AI 管理 → 会话审计”。

用户级 AI 偏好以服务器账号配置为主数据，localStorage/sessionStorage 只承担设备级缓存和当前 Tab 恢复入口。这样用户换设备重新登录后，个人模型、reasoning、字体、快捷键、历史入口等偏好仍可恢复；Dock 宽度等明显受屏幕影响的设置可继续本机优先。

系统级（管理员）AI 管理建议包括：

- AI 服务：Provider Base URL、Token、启用状态。
- 模型管理：远端模型加载、加入系统、哪些模型允许用户使用、系统默认模型、模型上下文/自动压缩默认参数、能力检测。
- 提示词管理：System Prompt、Compaction Prompt、版本、恢复默认。
- 页面能力：哪些页面接入 AI、页面能力覆盖状态。
- 会话管理策略：会话保留天数、是否允许用户归档/删除自己的会话、其他系统级保留策略。
- 会话审计：有独立审计权限的管理员只读查看所有用户会话。
- 运行与用量：后续可以承载 Token / cache usage 等可观测信息，但不为了第三阶段强行做成复杂运营平台。

Prompt Cache 的产品边界：

- Prompt Cache 是 Runtime 默认应该利用的能力，不在管理员界面提供“是否开启缓存”开关。
- 当前阶段也不暴露“Cache Key 策略”给管理员配置。
- 后端自动保持稳定前缀、按 Provider 能力使用合适 cache key / cache 参数，并记录 usage/cache 命中证据。
- 以后只有在真实多租户、复杂路由或特殊 Provider 场景需要时，再考虑把缓存策略升级为高级系统配置。

Agent 安全配置边界：

- “哪些页面接入 AI”本阶段纳入系统级管理员配置。
- 服务端权限、数据范围、WRITE 确认、Tool/Capability 校验本阶段继续做完整可靠实现。
- 复杂的“不同风险动作如何确认”策略编辑器、全局 Tool/Capability 规则编辑器暂不作为第三阶段必须 UI；等后续真实业务需要再开放，避免过度设计。

系统默认模型与用户默认模型严格分离：

- 管理员定义系统允许模型和系统默认模型。
- 用户只能从系统允许且当前可用的模型中选择“我的默认模型”。
- 用户默认模型仍有效时优先使用用户默认。
- 用户默认模型被管理员下线/禁用后自动回退到系统默认，并给予合理提示。
- reasoning 同理，只能从所选模型实际支持并由系统开放的档位中选择。

### R3-18 管理员只读 AI 会话审计

管理员可以在“AI 管理 → 会话审计”中查看全系统用户 AI 会话，但该能力与 AI Provider/模型配置权限分离。

权限建议独立，例如：

- 用户只能查看自己的会话。
- 会话审计使用独立权限，例如 `ai:conversation:audit`。
- 能配置 Provider 的管理员不因为配置权限自动获得查看员工对话内容的能力。

管理员审计页至少支持：

- 按用户筛选。
- Conversation ID。
- 时间范围。
- 模型。
- 状态。
- 标题。
- 是否发生 Tool / WRITE / Stop / Steering / Compaction。
- 打开会话详情，只读查看用户消息、AI 消息、Tool Call/Result、WRITE 确认、Checkpoint 等审计信息。

明确禁止：

- 管理员在其他用户 Conversation 上继续发送消息。
- 管理员重试、继续或接管其他用户 Run。
- 管理员从审计页触发页面 Tool 或 WRITE。

管理员查看他人会话本身应进入操作审计/访问日志，避免敏感业务对话被无痕查看。

## 3. 总体产品与技术方向

第三阶段整体采用“应用级 Agent + 页面级能力提供者 + 后端持久 Conversation”的运行模型。Conversation 不再属于某个 route 或 Vue 组件；页面只是当前工作环境。

第三阶段整体采用以下运行模型：

```text
用户消息
   ↓
创建/更新 Conversation
   ↓
Run（同一会话最多一个活动执行）
   ↓
模型调用 ← 稳定缓存前缀
   ↓
Tool / 页面能力
   ↓
安全边界
   ├─ 正常继续
   ├─ Stop → CANCELLED
   ├─ Steering → SUPERSEDED → 新 Run
   └─ Context 达阈值 → Checkpoint → 压缩后继续
```

核心不是引入更多状态名，而是确保四种用户体验：

1. 用户能随时停。
2. 用户能边执行边继续说。
3. 长会话不会因为上下文膨胀突然断掉或失忆。
4. GPT 长会话能尽量命中缓存，避免无意义重复成本。

## 4. Run 生命周期与安全边界

建议为一次 Agent 执行引入明确 run 状态，最终命名可在实施中结合现有表结构确定：

- RUNNING
- CANCEL_REQUESTED
- CANCELLED
- SUPERSEDED
- COMPLETED
- FAILED

要求：

- 同一 Conversation 只能存在一个活动 Run。
- Stop 和 Steering 都必须能阻止旧 Run 在状态改变后继续发起新的 Tool。
- Tool Result 回来后再次检查 Run 是否仍允许继续。
- WRITE 执行前和确认后都要检查 Run 状态。
- 不能仅靠浏览器 AbortController 作为唯一取消机制。
- 前端取消、后端状态和上游 HTTP 取消能力相互配合。

## 5. 上下文压缩数据模型原则

建议区分三类数据：

1. **原始消息历史**：完整持久化，不因压缩删除。
2. **Checkpoint/Compaction Summary**：用于后续模型调用的接手状态。
3. **Runtime Context View**：某一轮真正发送给模型的裁剪/组合结果。

压缩后不能覆盖原始事实，也不能把摘要当成唯一审计来源。

需要记录：

- Checkpoint 对应到原始消息范围。
- 压缩时所用模型。
- 生成时间。
- 估算/实际 Token 范围。
- Checkpoint 状态。
- 如果压缩失败，不应破坏原会话继续能力。

## 6. Prompt Cache 方向

缓存优化首先解决“稳定前缀”问题，再考虑参数。Prompt Cache 默认作为 Runtime 应该利用的能力，不提供管理员“关闭缓存”或手工选择 Cache Key 策略的普通配置项。

建议 Prompt 组织顺序：

1. 长期稳定 System Rules。
2. 稳定的 Tool schema / 页面能力协议。
3. 当前 Checkpoint（如存在）。
4. Conversation 近期消息。
5. route / Page Context / 当前页面动态状态。
6. 最新用户消息或 Tool Result。

实施阶段需根据当前 Spring AI 和 Provider 实际序列化结果验证真实前缀是否稳定，而不是只看 Java 代码逻辑。

需要增加缓存 usage 记录或可观测字段。对于当前 GPT 测试环境，至少要能回答：

- 本次 input tokens。
- 本次 cache read tokens。
- 本次 cache write tokens（Provider 有数据时）。
- 当前会话累计缓存命中。
- 缓存未命中时是否因为前缀发生变化。

## 7. 页面语义能力层方向

第三阶段不继续扩大“一个功能一个手写 Tool”的模式，而是抽象统一页面能力协议，并将该协议扩展到当前 RuoYi 其他业务页面与跨页面导航。

建议至少区分：

- Page Metadata。
- Query/Form Fields。
- Table/Data Context。
- Available Actions。
- Validation Rules。
- Permission/Visibility。
- Action Invocation。
- Result / Error。

前端页面按统一协议注册当前能力，后端继续作为权限与安全权威层。

最终 AI 看到的是“这个页面有哪些业务字段和动作”，而不是 CSS Selector、DOM 坐标或任意 JS。

## 8. UI 方案

本阶段新增交互以已经确认的 HTML 原型为方向：

- 发送后显示停止。
- 运行中输入框保持可编辑。
- 补充指令产生 Steering 状态提示。
- 双 ESC 第一次给轻量提示，第二次停止。
- 自动压缩时显示“正在整理较早的会话上下文”，不弹模态框打断。
- 压缩完成自动继续。
- 模型选择器改正规 Chevron。
- 字体设置进入 AI 设置。
- 上下文/压缩参数进入模型高级设置。

同时继续保留第二阶段已有：

- Base URL / Token。
- 保存连接配置。
- 测试模型加载。
- 远端模型选择。
- 系统模型。
- 启用/移除。
- 默认模型星标。
- 自动能力检测。
- 单模型测试连接。
- 默认 reasoning。
- 快捷设置与完整 AI 配置页。

第三阶段 UI 是叠加和精修，不是删掉旧功能重新做一套。

第三阶段只有同时满足以下条件才可以宣布完成：

1. R3-01 ~ R3-18 每项都有对应实现。
2. 每项都有自动验证或明确说明无法完全自动化的部分。
3. 每项都完成面向用户场景的验收，而不是只做技术断言。
4. 不因为新增功能破坏第二阶段已完成的 Provider、模型选择、Tool Loop、WRITE 确认、Dock、快捷键、多模型与安全基线。
5. 页面能力扩展有覆盖清单，不能以“框架已抽象”替代实际页面能力验收。
6. Prompt Cache 必须尽量有真实 GPT 命中证据，不能用“代码已设置 cache 参数”替代。
7. 自动压缩必须实际验证压缩后继续工作且不丢当前任务主线。
8. Stop / Steering 必须验证不会导致重复 Tool、重复 WRITE 或旧 Run 死灰复燃。

10. `13-AI助手第三阶段实施与验收记录.md` 中逐项回填 R3-01 ~ R3-18 的最终证据和结论。

## 11. 不在本阶段偷换的目标

以下行为不能算“实现了用户诉求”：

- 只在 UI 上增加停止图标，但后端旧 Run 仍继续执行。
- 只让前端可以继续输入，但消息要等旧 Run 完成才真正生效。
- 只生成一段普通摘要，就声称实现了上下文压缩。
- 只传入某个 cache 参数，没有任何真实缓存命中证据。
- 只做一个通用 Page Tool 抽象，但实际页面仍只能操作 Demo 四个字段。
- 只通过 CI，就跳过真实页面和用户场景验收。
- 只把 Conversation 保存在前端内存，F5 后仍然丢失上下文。
- 只做历史列表，却无法真正恢复后端 Conversation / Checkpoint / Run 状态。
- 把管理员全局配置和普通用户偏好继续混在一个无权限边界的设置页里。
- 管理员审计可以继续他人会话，破坏只读审计边界。
- 把 Prompt Cache 做成一个可随意关闭的普通 UI 开关，反而增加成本和误配置风险。
- 为追求技术完备引入大量用户不需要的复杂功能，反而偏离已确认主线。

第三阶段所有实现都以“用户真实用起来是否解决问题”为最终判断标准。
