# Git 工作流规则

> 类型：项目级 Rule
>
> Canonical source：`ShanySky/RuoYi-Vue/.agents/rules/git-workflow.md`
>
> 前端仓库 `ShanySky/RuoYi-Vue3` 保留同路径 mirror；项目级语义以后端本文件为准。

本规则适用于 RuoYi AI 项目的架构讨论、专项开发、测试修复和主线合并。

## 1. 分支职责

- `master` 是干净基线，日常 AI 开发不要直接落到 master。
- `chatgpt/ai-agent-assistant` 是已经成熟、已经验收成果的稳定 AI 开发主线。
- 较大的架构讨论、专项实现、迁移和高风险改造应从最新 AI 主线创建独立工作分支。
- 跨前后端任务需要修改两个仓库时，优先在两个仓库使用语义一致的工作分支名称。

原则：

> 工作分支可以保留开发过程，稳定主线只保留长期有意义的历史。

## 2. 实施分支允许细粒度提交

实施过程中可以为了开发、调试、回滚和验证进行小步提交，例如：

- 初始实现。
- 局部重构。
- Bug 修复。
- 测试补充。
- CI 修复。
- 验收记录。

不要为了让过程历史“漂亮”而减少必要的安全检查和中间提交。

## 3. 合入 AI 主线前整理历史

专项实施完成并通过验收后，进入 `chatgpt/ai-agent-assistant` 前应按照长期有意义的功能边界整理历史。

一个自然实施里程碑通常保留少量语义清晰的提交，例如：

1. `feat(ai): implement <goal>`
2. `test(ai): validate <goal>`
3. `docs(ai): record <goal>`

提交数量不是硬指标。判断标准是每个提交是否代表值得长期保留的完整目的。

历史整理可以使用标准 Git 的 rebase、squash、fixup、reset 或按 hunk 拆分等方式；不要为了整理 commit 重新开发已经验收通过的业务代码。

## 4. 改写已推送历史的安全要求

如果确实需要改写已经推送的共享历史：

1. 先确认目标分支没有出现新的未知提交。
2. 先保留可恢复的旧历史，例如 archive 分支或 tag。
3. 在安全分支完成历史整理。
4. 如果目标只是整理历史，应验证整理前后的最终代码树等价。
5. 重新确认测试和验收结论仍适用于最终代码树。
6. 使用带保护的强制更新机制，不无保护覆盖共享分支。
7. 所有基于旧主线继续工作的分支都要同步到新主线。

## 5. 合并前检查

进入 AI 主线前至少确认：

- 工作分支基于当前最新 AI 主线，或已经处理主线的新变化。
- 实施范围与已确认架构边界一致，没有顺手带入未批准的大改造。
- 必要的编译、测试、真实运行或端到端验收已经通过。
- 提交历史已经整理到适合长期维护的粒度。
- 没有 Token、密码、临时调试文件或无关改动。
- 文档、代码和验收记录不存在明显互相矛盾的状态。

## 6. 主线历史原则

`chatgpt/ai-agent-assistant` 应让后来的人或 AI 通过 Git 历史快速理解：

- 这一轮解决了什么问题。
- 哪些是主要功能或架构目标。
- 哪些提交负责测试 / 验收。
- 哪些提交记录最终状态。

不要让长期主线变成调试过程日志。

## 7. 分支生命周期与清理

专项实施、架构讨论或临时治理分支在完成使命后应及时清理；明确标记为 `archive/*` 或其他长期保留用途的分支除外。

删除工作分支前必须确认：

- 有效成果已经完整进入目标主线。
- 分支没有仍需保留的独立成果。
- 没有其他进行中工作依赖该分支。
- 清理动作不会改变主线内容。

优先使用仓库自动删除已合并 PR head branch；未自动删除时使用标准 Git / GitHub 分支删除能力完成清理。
