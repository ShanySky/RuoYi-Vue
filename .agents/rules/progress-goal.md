# 推进目标编写规则

> 类型：项目级 Rule
>
> Canonical source：`ShanySky/RuoYi-Vue/.agents/rules/progress-goal.md`

## 1. 何时使用

当用户要求编写、整理或生成“推进目标”，包括为新的 ChatGPT / Codex 会话准备任务目标时，使用本规则。

推进目标的作用是让 AI 在长流程中不丢主线，不是替代需求、方案或实施计划。

## 2. 核心主线

复杂工作保持：

```text
用户诉求
  ↓
方案
  ↓
计划
  ↓
实施
  ↓
验收重新回到用户诉求
```

含义：

- 诉求约束方案。
- 方案约束计划。
- 计划指导实施。
- 验收不能只检查计划是否执行完，还要确认最终结果真正解决原问题。

## 3. 推进目标只写六类信息

### 3.1 最终目标

用一小段说明这次最终要达到什么结果。

### 3.2 用户核心诉求

说明用户真正关心什么。不要只复述技术任务名称。

### 3.3 工作依据

列出必须读取的关键文档、目标分支和必要事实源，并说明各自职责。

例如：

- 总体设计：长期方向和核心原则。
- 落地方案：本轮范围和边界。
- 实施计划：具体执行步骤。
- 当前代码：实现状态最终事实。

### 3.4 阶段关系

说明上一阶段产出如何成为下一阶段输入。

例如：

- 先依据落地方案和当前代码形成实施计划。
- 计划确认后，以计划作为直接执行依据实施。
- 实施完成后按方案、计划和原始诉求验收。

### 3.5 关键边界

只写最容易偏航的约束，例如：

- 不实施仍待讨论事项。
- 不自行扩大架构范围。
- 发现必须改变已确认方案时，停止该部分并提出问题。

如果这些内容已完整存在于指定方案中，直接引用方案，不重复抄写。

### 3.6 完成标准

至少回答：

- 目标事项是否完成。
- 必要验证是否通过。
- 实现是否符合方案 / 计划。
- 是否越过范围边界。
- 最终是否真正满足用户核心诉求。

## 4. 不要复制已有文档

原则：

> 推进目标是导航，不是方案副本。

如果删除某段后，AI 仍然可以通过指定文档获得完整信息，那么这段通常不需要重复写进推进目标。

已有完整方案和计划时，推进目标应偏短，只负责：

- 指向文档。
- 串起阶段。
- 强调用户核心诉求。
- 明确不能越过的边界。
- 定义真正的完成标准。

## 5. 长度

默认使用中等长度。

只有以下情况才增加背景：

- 没有现成方案可以引用。
- 任务边界或风险很高。
- 多阶段依赖复杂。
- 新会话缺少必要背景会明显误解任务。

不要为了形式完整把推进目标写成第二份落地方案。

## 6. 推荐骨架

```text
推进目标：完成 XXX，最终达到 XXX。

用户核心诉求：XXX。

使用 XXX 分支。开始前检查 GitHub 当前真实状态，并阅读：
- XXX 总体设计
- XXX 落地方案

第一阶段依据落地方案和当前代码形成 XXX。
上一阶段产出作为下一阶段的直接输入和约束。

实施阶段严格遵从已确认计划，同时继续受上层方案和用户诉求约束。
若实际情况要求改变方案边界，或依赖尚未确认的架构决策，停止该部分并提出问题。

完成后做必要真实验证，并重新回到用户最初诉求验收。

完成标准：XXX 已按方案和计划完成，关键路径验证通过，无越界实施，文档与实际状态一致，并能证明用户核心诉求得到满足。
```

根据任务实际删减，不机械填满模板。

## 7. 自检

提交推进目标前只检查：

1. 最终目标是否明确？
2. 用户核心诉求是否明确？
3. 必须先读什么是否明确？
4. 当前阶段主要受哪份文档约束是否明确？
5. 阶段之间的输入输出关系是否明确？
6. 什么情况下不能自行继续是否明确？
7. 什么状态才算真正完成是否明确？
8. 是否重复抄写了已有方案？

第 8 项如果答案是“是”，优先删减。
