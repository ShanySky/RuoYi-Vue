# 推进目标编写规则

> 类型：项目级 Rule
>
> Canonical source：`ShanySky/RuoYi-Vue/.agents/rules/progress-goal.md`

## 1. 定位

当需要编写、压缩、修订或审查“推进目标”时，使用本规则。

推进目标的作用是：

> **让一个没有前文的新执行者，迅速知道要解决什么、依据什么继续、哪些边界不能越、做到什么程度才算完成。**

推进目标是导航和完成约定，不是需求文档、方案副本、实施计划副本或测试清单。

复杂工作仍应保持：

```text
用户诉求
  ↓
方案
  ↓
计划
  ↓
实施
  ↓
验收重新回到用户诉求
```

如果方案、计划或验收要求已经有可靠文档承载，推进目标只负责准确引用和串联，不重新展开其内容。

## 2. 先复用材料，再补正文

编写前先判断当前已有材料是否已经可靠承载：

- 用户核心诉求。
- 已确认方案。
- 已获准实施计划。
- 当前进展与恢复点。
- 关键边界。
- 验收依据。

已经有清楚、有效、可访问的材料时：

1. 写出准确路径或索引。
2. 简短说明该材料在本任务中的作用。
3. 只补充材料中没有、但继续工作必须知道的信息。

如果删除推进目标中的某段后，新执行者仍能通过已引用材料可靠获得同样信息，这段通常应该删除。

## 3. 正文优先保留五类信息

### 3.1 最终目标和核心诉求

说明最终要解决什么问题，以及用户真正关心的结果是什么。

### 3.2 当前起点和工作依据

只写继续工作必须知道的：

- 目标仓库 / 工作区 / 分支。
- 当前阶段或已经完成到哪里。
- 必须读取的少量关键材料及其职责。
- 哪个事实源负责核实最新真实状态。

不要罗列“可能有用”的所有文件。

### 3.3 推进重点或子目标

子目标写“要达到的结果”，不展开已有方案中的普通实施步骤。

只有以下内容才需要写成顺序：

- 用户明确要求不可改变的顺序。
- 前后阶段存在真实硬依赖。
- 跳过会造成明显失败、返工或安全风险。

### 3.4 关键边界和授权

只保留最容易导致偏航、越权或错误重做的约束，例如：

- 不重新讨论已经确认的架构结论。
- 不扩大到未授权范围。
- 不覆盖并行工作线已经进入共同主线的成熟成果。
- 只有发生真正改变方案边界的事实时才暂停并重新讨论。

### 3.5 完成标准

完成标准只回答本任务真正需要证明的结果和证据：

- 目标结果是否真实实现。
- 必要验证是否足以支持结论。
- 是否符合已确认方案 / 计划和关键边界。
- 是否真正解决用户最初的问题。

## 4. 阶段关系

推进目标需要保持“诉求 → 方案 → 计划 → 实施 → 验收”的约束关系，但不等于把每个阶段内容重新写一遍。

已有完整方案和计划时，一小段说明阶段关系即可。

## 5. 篇幅控制

推进目标默认追求高信噪比。

已有完整、可靠方案或计划可引用时，优先控制在约 1,500～2,500 个中文字符；明显超过时应专门检查是否重复抄写方案、计划、测试或文件清单。

不能为了满足长度删除真实必要的授权、安全边界、关键依赖或完成标准。

## 6. 推荐组织方式

通常优先使用：

```text
推进目标：最终结果和用户核心诉求。

工作依据与当前起点：
- 当前分支 / 工作区。
- 必须读取的少量关键材料。
- 需要重新核实的最新事实。

推进重点：
- 结果型子目标。
- 必要阶段关系。
- 真正重要的授权边界和暂停条件。

完成标准：
- 最终结果。
- 必要证据。
- 是否回到用户原始诉求并证明问题解决。
```

## 7. 输出前自检

提交推进目标前检查：

1. 新执行者能否一眼看出最终要解决什么？
2. 是否准确指出当前起点和最重要的依据？
3. 子目标写的是结果，还是把计划步骤重新抄了一遍？
4. 是否把已有方案、计划、测试清单重复写进正文？
5. 是否保留了真正不能丢的授权、安全、权限和范围边界？
6. 完成标准是否足以判断“用户原始问题真的解决了”？
7. 是否无意中扩大了未授权工作？

核心判断：

> **推进目标应让执行者抓住主线，而不是让主线淹没在细节里。**
